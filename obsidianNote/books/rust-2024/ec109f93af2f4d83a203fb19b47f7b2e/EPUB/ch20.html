In the last chapter, we explained how to use threads in Rust to spread compute-intensive work across multiple processor cores, putting the entire machine to work. In this chapter and the next, we’ll present an alternative to threads, offering more efficient concurrency for I/O-bound programs.

For CPU-bound programs, like our Mandelbrot example, the performance hinges entirely on efficient use of the available CPU time. The job requires so much processing that no other resource is under load. Threads are very good at putting CPUs to work.

A network service, though, has very different performance characteristics. If it spawns a thread to handle each incoming request, that thread will spend almost all of its time blocked, waiting for I/O. The amount of CPU needed is so small that a single server can serve thousands or even hundreds of thousands of concurrent requests. Performance then depends on efficient use of memory and efficient task creation and switching. Threads use a lot of memory. Even a thread that’s doing nothing weighs around twenty kilobytes on most platforms (including kernel and user space memory), and once the thread starts doing real work, its call stack can soak up many times that. And creating threads can be slow.

Rust’s asynchronous code is a cooperative multitasking system that offers the expressiveness of threaded code with lower overhead—sometimes much lower. The asynchronous counterpart of a thread is called a task. Asynchronous tasks in Rust are like tasks in C#, “goroutines” in Go, or “virtual threads” in Java. Those languages’ facilities provide a smoother developer experience than Rust’s asynchronous code, but they also require complex support from their language runtimes. Asynchronous Rust, in contrast, works well on servers and microcontrollers alike.

Without asynchronous code, each thread does one thing at a time. For example, consider a single-threaded program that calls reqwest::blocking::get("https://red-bean.com") to make an HTTP request. Figure 20-1 shows a simplified view of the function call stack as that program runs, from left to right. Each function call is a box, placed atop its caller. Obviously, the get function runs throughout the entire execution. It calls functions from the Rust standard library like TcpStream::connect and TcpStream’s implementations of write_all and read_to_string. These call other functions in turn, but eventually the program makes system calls, requests to the operating system to actually get something done, like open a TCP connection, or read or write some data.

The darker gray backgrounds mark the times when the program is waiting for the operating system to finish the system call. This function spends almost all of its time waiting for the operating system; if we had drawn these times to scale, the execution of the actual Rust code would be narrow slivers of white between the system calls.

While this function is waiting for system calls to return, its single thread is blocked: it can’t do anything else until the system call finishes. It’s not unusual for a thread’s stack to be tens or hundreds of kilobytes in size, so if this were a fragment of some larger system, with many threads working away at similar jobs, the thread overhead alone could become quite expensive.

Asynchronous code lets a single thread do more than one thing. Figure 20-2 shows three asynchronous tasks, each running its own HTTP request using the asynchronous version of reqwest::get. In the top half of the figure, we see each task’s perspective on its own execution. Each one looks a lot like Figure 20-1. However, instead of blocking, asynchronous code is designed to take turns. The resulting interleaved execution pattern is shown at the bottom of the diagram.

Each request takes just as long as it would have in the synchronous version, but the periods during which the thread would simply be waiting for the network in the synchronous version instead get filled in with other work. This diagram still isn’t to scale; you could fit many times more requests in before this thread fully occupied a single CPU core.

If you’re doing compute-intensive work, you’ll need to use threads to exploit your machine’s parallelism. But for a given budget of memory and processor time, asynchronous code can handle many more I/O-bound tasks simultaneously. This is why most popular I/O-related crates in the Rust ecosystem provide asynchronous interfaces. But threads and asynchronous code are often used in combination, to handle workloads that have a mix of interactive and computationally intensive tasks.

This chapter approaches asynchronous code from user’s point of view: how to write it, how to use published crates with asynchronous interfaces, and how to work through common problems. The next chapter explains how asynchronous code works: exactly how it is suspended, scheduled, and resumed. You’ll need those details in order to understand how asynchronous code will perform, and extend the system with your own primitives. But in this chapter, we’re only concerned with making stuff work.

What Asynchronous Code Looks Like

Although asynchronous code shows its value best in applications that create many tasks, its essential features are easiest to understand in simpler situations. So while we’ll see highly concurrent code later in the chapter, this section shows an example that offers fewer distractions.

Here’s a program that uses the reqwest crate to fetch a web page:

use anyhow::Result;

async fn make_request() -> Result<String> {
    let url = "https://rust-lang.org/";
    let response = reqwest::get(url)
        .await?
        .text()
        .await?;
    Ok(response)
}

fn main() -> Result<()> {
    let runtime = tokio::runtime::Runtime::new()?;

    let response = runtime.block_on(make_request())?;
    println!("{response}");
    Ok(())
}

Here’s our program’s Cargo.toml file:

[package]
name = "reqwest-example"
version = "0.1.0"
edition = "2024"

[dependencies]
anyhow = "1.0.102"
reqwest = "0.13.4"
tokio = { version = "1.52.3", features = ["full"] }

When we run this, it writes the unprocessed HTML of the response to its standard output:

$ cargo run -p reqwest-example
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.31s
     Running `target/debug/reqwest-example`
<!doctype html>
<html lang="en-US">
  <head>
    <meta charset="utf-8">
    <title>
            Rust Programming Language
        </title>
...

This program’s code doesn’t look terribly different from ordinary Rust. And that’s the idea: asynchronous code generally resembles classic, synchronous Rust, with a few additions to make the cooperative multi-tasking possible:

  • An asynchronous function, defined with async fn, is one whose execution can be suspended while it waits for I/O or other blocking operations to complete. In our program, make_request is an asynchronous function. It calls reqwest::get, an asynchronous function provided by reqwest, a popular HTTP client crate.

  • Within an asynchronous function, we can use await expressions to wait for asynchronous operations to complete. An await expression is written as .await, following the operation we want to wait for. (Although this looks like we’re accessing a struct field named await, .await is actually a postfix operator built into Rust’s grammar.)

    The make_request function uses await expressions to wait for the result from reqwest::get, and then for the result of calling the text method on its success value. The calls to get and text typically need to wait for the network, and when they do, the await expression suspends the execution of make_request itself, to be resumed when it can make progress again.

  • In any program that uses asynchronous code, you must specify the runtime that will run your asynchronous tasks. An async runtime is Rust’s analogue of the operating system’s thread scheduler: it maintains a queue of runnable tasks, and tracks tasks that are blocked on operations like I/O, waiting for a timer, or acquiring a mutex. When an await expression suspends an asynchronous function call, it is the runtime that resumes it later.

    Our program uses the tokio crate’s runtime. We create a Runtime value, and then call its block_on method to start an asynchronous task running the call to make_request. When the task is done, block_on returns make_request’s result, which we then print.

In addition to the Runtime type, the tokio crate provides asynchronous versions of the standard library’s I/O and synchronization primitives, and various frequently needed utilities. Tokio is by far the most widely used asynchronous support crate, so almost any other crate you find will be ready to work with it.

That said, Tokio is just an ordinary third-party crate, not part of the Rust language. There’s nothing about implementing a runtime that entails using internal, unstable, or non-portable Rust features. In fact, the next chapter shows how to implement several of a runtime’s core features yourself.

It’s nearly universal for programs that use asynchronous code to start, as we do here, by creating a runtime and then immediately using it to call some asynchronous function that does all the real work. This gets tedious, so Tokio provides an attribute macro, #[tokio::main], to package up all the boilerplate:

#[tokio::main]
async fn main() -> Result<()> {
    let url = "https://rust-lang.org/";
    let response = reqwest::get(url)
        .await?
        .text()
        .await?;
    println!("{response}");
    Ok(())
}

This is equivalent to our original code, but the runtime creation has been hidden away, and main itself has become an asynchronous function, so it can use await expressions itself. We don’t need the make_request function any more, since main can now call reqwest::get directly. Tokio’s interface is designed such that you rarely need to refer the runtime explicitly, so using #[tokio::main] is usually fine.

Futures

In the first reqwest example, the call to block_on may look a little strange:

runtime.block_on(make_request())

As we said, calling block_on creates an asynchronous task to run the call to make_request, and waits for it to complete. But hasn’t make_request already returned? If it were an ordinary function, the work would already be done, and there would be nothing left to block on.

But make_request is not an ordinary function: it’s asynchronous. When you call an asynchronous function, its body does not even begin execution. Instead, the function immediately returns a future, a Rust value that represents an asynchronous call in progress. A freshly created future just records the call’s arguments, but it has space for whatever local variables and temporaries the function body will need as it executes. Passing this future to runtime.block_on drives the asynchronous call to completion. Once it’s done, block_on passes along the call’s final return value—in this case, the body of the HTTP response.

Once you know that calling an asynchronous function produces a future, you can make better sense of code like this:

reqwest::get(url).await?

Here, too, the call to reqwest::get returns a future. The await expression takes ownership of that future and waits for it to produce a value. In this case, that’s a Result to which the ? operator is applied to see if the get succeeded.

Futures themselves are passive values; they don’t do anything until you await them or pass them to some sort of task-starting function like block_on. For example, consider the following program:

async fn announce(message: &str) {
    println!("{message}");
}

#[tokio::main]
async fn main() {
    let bonnie = announce("Bonnie");
    let clyde = announce("Clyde");

    println!("Starring:");
    clyde.await;
    println!("and");
    bonnie.await;
}

This produces the output:

Starring:
Clyde
and
Bonnie

Each call to announce returns a future, without executing the function’s body, so the program’s first output is "Starring:". Only when we await the futures do the function calls they represent begin execution, so the two calls to announce run in the order we await them, not the order we created them: "Clyde" is printed before "Bonnie". If, instead of awaiting a future, we simply drop it, the call that it represents never runs. (Rust prints a warning at compile time if you completely ignore the future of an asynchronous function call, so this rarely happens by mistake.)

Concretely, a future is any value that implements the standard library trait Future. The Future trait is generally not used directly, and doing so is tricky, so we’ll put off examining its definition until the next chapter. For now, what matters is that a type that implements Future can be polled to let the computation it represents run for as long as it can without blocking. If the computation finishes, the future provides its final return value. Otherwise, the future saves its current state, and the blocking operation that halted its progress arranges to notify the runtime when it is ready, so that the runtime can poll the future again to let it progress further.

The term “polling” is often associated with inefficient implementation techniques like busy waiting. That is not how asynchronous Rust works. Futures are polled only when there is actual progress to be made.

This is a good time to pin down a bit of terminology. Although calling an asynchronous function returns a future, that future is just an intermediate step towards what we really care about: the final return value produced by running the function’s body to completion. In this book, when we talk about an asynchronous function’s “return value”, we mean this final return value, emphasizing the parallel with ordinary, synchronous functions. When we do need to talk about the future itself, we’ll refer to “the future of the call”, or say something similarly explicit.

Asynchronous Function Future Types

The exact type of the future returned by an asynchronous function is anonymous and unique to that function. All you can say about it is that it implements the Future trait. This is analogous to the way Rust handles closures: each closure has its own anonymous, unique type, implementing some subset of the Fn, FnMut, and FnOnce traits. Like the closure traits, the Future trait has an associated type, Output, indicating the type of the future’s final value.

Since asynchronous functions’ futures’ types are anonymous, if you want to write a function that accepts such a future as an argument, you must give it a generic type, and let type inference supply the details:

async fn credits(
    star: impl Future<Output = ()>,
    costar: impl Future<Output = ()>,
) {
    println!("Starring:");
    star.await;
    println!("and");
    costar.await;
}

This function permits star and costar to have any types that implement Future, as long as their return types are (): since credits only awaits them for their side effects, it doesn’t expect them to return an interesting value.

You can return a future from a function like this:

fn star(star_index: usize) -> impl Future<Output = ()> {
    let name = match star_index {
        0 => "Bonnie",
        1 => "Clyde",
        2 => "Mephistopheles",
        _ => "some minor character",
    };
    announce(name)
}

Note that star is not an async fn: it’s an ordinary, synchronous function that just happens to return a future, the one produced by calling the asynchronous function announce. Since we return the future immediately, announce’s body doesn’t run here.

We can use credits and star like so:

#[tokio::main]
async fn main() {
    let bonnie = star(0);
    let clyde = star(1);

    credits(bonnie, clyde).await;
}

async Blocks

In addition to asynchronous functions, Rust also has async blocks. The value of an async block is a future.

let my_future = async {
    println!("Starring:");
    bonnie.await;
    println!("and");
    clyde.await;
};

The code in the body of the async block does not run right away. Instead, the async block produces a future that will run that code when awaited. Like a closure, it can capture variables from the surrounding code. You can even write async move { ... } to force the block to take ownership of the variables it refers to, just like writing move in front of a closure.

This gives us a way to rewrite any asynchronous function into a synchronous function that just happens to return a future:

fn credits(
    star: impl Future<Output = ()>,
    costar: impl Future<Output = ()>,
) -> impl Future<Output = ()> {
    async {
        println!("Starring:");
        star.await;
        println!("and");
        costar.await;
    }
}

This version of credits uses different syntax to get the same effect as the original definition. A caller can’t tell the difference between the two. But this one is a synchronous function that returns the future of an async block. (We could write async move { ... }, but Rust can infer from the await expressions that star and costar must be captured by moving, so it’s not necessary.)

Future lifetimes

This all looks very neat. But to keep these examples simple, we’ve been avoiding some details that real-world code needs to worry about. Recall the definition of announce:

async fn announce(message: &str) {
    println!("{message}");
}

Like any asynchronous function, rather than using its arguments immediately, this returns a future that will use them later. Since that future holds the value of message, it must not outlive the str that message borrows. For example, the following is no good:

let future = {
    let credits = format!("{star} and {costar}");
    announce(&credits)
};
future.await;

The future produced by announce holds a reference to credits, but credits goes out of scope at the end of the block, so the String it owns gets dropped at that point. When we try to use that future outside the block, Rust has concerns:

error: `credits` does not live long enough
   |
8  |     let future = {
   |         ------ borrow later stored here
9  |         let credits = format!("{star} and {costar}");
   |             ------- binding `credits` declared here
10 |         announce(&credits)
   |                  ^^^^^^^^ borrowed value does not live long enough
11 |     };
   |     - `credits` dropped here while still borrowed

As an exercise, if we rewrite announce as a synchronous function with an async block, we can see what’s going on a little better.

fn announce(message: &str) -> impl Future<Output = ()> {
    async move {
        println!("{message}");
    }
}

This returns a future that contains a copy of the reference message and perforce inherits its lifetime. If we fully wrote out all the lifetimes in the type signature, it would look like this:

fn announce<'m>(message: &'m str) -> impl Future<Output = ()> + 'm

The meaning is unchanged. The extra bound + 'm on the return type declares that the result can’t outlive the lifetime of message. This is the default in Rust, though. Recall that impl SomeTrait in the return type means “some type implementing SomeTrait, but we’re not saying which one”. This can be a type that depends on the function’s generic parameters, in this case 'm.

When Rust’s defaults aren’t what we want, we can spell things out with an explicit lifetime bound. Here’s a variant of announce that makes a copy of its argument so that it can return a 'static future:

fn copying_announce(message: &str) -> impl Future<Output = ()> + 'static {
    let owned_message = message.to_string();
    async move {
        println!("{owned_message}");
    }
}

The bound + 'static declares our goal here: the future’s type “lasts as long as 'static“. That is, the type itself doesn’t have a lifetime, so callers may keep the future around as long as they like. We achieve this by using to_string to turn the &str into a String, and then use async move to ensure the future takes ownership of the String.

These examples have been a bit trite, to keep the explanations focused, but in the next section, we’ll look at a more developed, realistic example, and show how asynchronous code helps manage highly concurrent code.

Spawning Asynchronous Tasks

With the basics out of the way, we’re ready to put asynchronous Rust to work, running highly concurrent code without wasting resources.

In this section, we’ll write another program using reqwest, this time to find all the pages reachable from a given starting page within a given number of links. There are lots of ways to do this, but asynchronous code makes a simple design perfectly feasible: we simply spawn a fresh asynchronous task for every web page we visit. This can easily result in thousands of tasks running simultaneously—but because they’re asynchronous tasks, not threads, our program’s peak resource consumption is reasonable, not much different from a hand-written breadth-first traversal.

Here’s the Cargo.toml file we’ll be using:

[package]
name = "spider"
version = "0.1.0"
edition = "2024"

[dependencies]
anyhow = "1.0.102"
reqwest = "0.13.4"
tokio = { version = "1.52.3", features = ["full"] }
netiquette = "0.1"
scraper = "0.27.0"

Most of these crates we’ve mentioned before. The error-handling crate anyhow was introduced in Chapter 7. We’ve been using tokio and the reqwest HTTP client in this chapter. The newcomers are netiquette, which we will use to crawl the web politely, limiting our program to a request per second per domain; and scraper for parsing HTML.

Listing a Web Page’s Outgoing Links

First, we’ll take care of a bit of supporting code. The following function fetches a web page, finds the links in it, and returns them as vector of absolute Urls:

use reqwest::{Client, Result, Url};
use scraper::{Html, Selector};

pub async fn page_links(client: &Client, url: &Url) -> Result<Vec<Url>> {
    let body = client
        .get(url.clone())
        .send()
        .await?
        .error_for_status()?
        .text()
        .await?;

    let doc = Html::parse_document(&body);
    let link_selector = Selector::parse("a[href]").unwrap();
    Ok(doc
        .select(&link_selector)
        .flat_map(|a_elem| {
            let href = a_elem.attr("href").unwrap();
            url.join(href)
        })
        .collect())
}

The first half of this function uses reqwest to fetch the web page from the given url, returning an error if anything goes wrong. We will not dwell on the details of reqwest’s API, except to say that a reqwest::Client contains a connection pool, so it is better to use a Client than the plain reqwest::get function when you’ll be doing more than one HTTP request.

A successful call to client.get(url.clone()).send() returns a reqwest::Response representing the HTTP response from the server, which may still be in the process of transmission. We check for HTTP error responses by calling error_for_status. If that succeeds, we call text() to fully receive the response body and check that it is valid UTF-8. At each point where an error could occur, we use the ? operator to bail out.

The second half of the function uses scraper::Html to parse the response as HTML, finds all <a href=> tags in the document, uses url.join to resolve relative URLs to absolute URLs, and collects the URLs in a vector. A real spider program should honor a few more HTML features, such as the nofollow attribute on links, but this will do for an example.

Note that Html::parse_document does not return a Result. The HTML standard specifies how every possible parse error in an HTML document can be handled (acknowledging the reality that finding botched markup on the web is like finding water in an especially wet ocean). Therefore the only errors that can happen in this code are from url.join(&href), which returns a Result<Url, url::ParseError>. There is, it turns out, such a thing as a broken URL. Rather than treat them as fatal, we use the flat_map iterator method to keep the Ok results and ignore the errors.

If all goes well, page_links returns a vector of absolute URLs.

In the next section, we’re going to use page_links as the workhorse in a concurrent traversal of the Internet. But if you’d like to try it out in isolation, here’s a possible main function you could use:

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let Some(url) = std::env::args().nth(1) else {
        anyhow::bail!("Usage: list-links URL");
    };
    let url = Url::parse(&url)?;

    let link_urls = links::page_links(&Client::new(), &url).await?;
    for link in link_urls {
        println!("{link}");
    }
    Ok(())
}

Spidering the Web Concurrently

As we mentioned before, we’ll be using the simple strategy of spawning a task per web page. These tasks will share a few resources. Here’s the struct that holds the common state for the traversal:

use std::collections::HashSet;
use std::sync::Mutex;

use netiquette::Limiter;
use reqwest::Client;

/// A traversal of the Internet, starting from a given page.
struct Traversal {
    /// HTTP client.
    client: Client,

    /// Set of all URLs we have seen so far. Note: `#fragment`s are
    /// stripped, so that URLs pointing to two sections of the same page
    /// aren't treated as different pages and fetched twice.
    seen: Mutex<HashSet<Url>>,

    /// Self-imposed rate limiter.
    limiter: Limiter,
}

We’ll create an instance of this struct when we begin a traversal, and give each asynchronous task its own Arc reference-counted pointer to it. It has three fields:

  • client is the reqwest connection pool, which we will use every time we want to fetch a web page.

  • seen is a set of all the pages we’ve visited so far. If we encounter a link to a page that’s already in seen, we assume that some other task is taking care of enumerating its links, and move on.

  • limiter is used to avoid overloading web sites by bombarding them with many requests concurrently or in rapid succession.

Since Tokio uses a thread pool to put all your processor cores to work running asynchronous tasks, we must assume that the fields of Traversal could be accessed by several different threads simultaneously. This means that seen needs to be protected by a Mutex. Although Tokio defines its own Mutex type, we don’t need to use that here; the standard library’s std::sync::Mutex will do fine, and is slightly preferable. We’ll discuss the difference between the two later in this chapter.

To create a fresh Traversal value, we provide a new function:

impl Traversal {
    fn new(client: Client, user_agent: String) -> Self {
        Self {
            seen: Mutex::new(HashSet::new()),
            client: client.clone(),
            limiter: Limiter::new(client, user_agent),
        }
    }
}

The code for the traversal itself is as follows:

use std::sync::Arc;
use tokio::task::JoinSet;

/// Visits all pages reachable from `page` within `depth` links.
async fn visit(traversal: Arc<Traversal>, mut url: Url, depth: usize) {
    url.set_fragment(None);
    if !traversal.seen.lock().unwrap().insert(url.clone()) {
        return;
    }
    if depth == 0 {
        return;
    }

    // Rate limiting; and bail out if robots.txt prohibits crawling this URL.
    let permit = match traversal.limiter.acquire(&url).await {
        Ok(permit) => permit,
        Err(err) => {
            eprintln!("Skipping <{url}>: {err}");
            return;
        }
    };

    // Fetch the document and find links.
    let links = match links::page_links(&traversal.client, &url).await {
        Ok(links) => links,
        Err(err) => {
            eprintln!("Error visiting <{url}>: {err}");
            permit.note_error(&url, err);
            return;
        }
    };
    drop(permit); // done: allow crawling other URLs on this domain

    // Crawl web pages linked from this document, recursively.
    let mut join_set = JoinSet::new();
    for link in links {
        spawn_visit(Arc::clone(&traversal), link, depth - 1, &mut join_set);
    }
    join_set.join_all().await;
}

fn spawn_visit(
    traversal: Arc<Traversal>,
    url: Url,
    depth: usize,
    join_set: &mut JoinSet<()>,
) {
    join_set.spawn(visit(traversal, url, depth));
}

We pass visit a URL and the number of links outwards from that page we would like to explore. First we strip any #fragment from the end of the URL, so that the spider correctly handles links that point to different sections of the same web page. The call to HashSet::insert records that this traversal has seen url. Conveniently, insert returns false if that page was already present in the set, indicating that some other task has already visited this page, so in that case our work is done. If depth is zero, then we are not responsible for exploring any further; again, our work is done.

Otherwise, the calling task is the first to reach this page, and is thus responsible for enumerating its outgoing links. We call page_links to find them, and record an error should one arise.

Now that we have our list of links, we have reached the moment where asynchronous code lets us do something that we cannot (or at least should not) do with threads: we simply spawn off a new asynchronous task for every one. If the page has a thousand outgoing links, this will spawn a thousand new asynchronous tasks.

Remember that an asynchronous task is nothing more than a future that the runtime is driving to completion. The future need only be large enough to save the computation’s state at each await expression, including those in the callees like page_links and reqwest::get. In this case, that’s a little over a kilobyte. The runtime itself adds only a small amount of overhead. And an asynchronous task requires no dedicated kernel resources. This is an order of magnitude less memory than needed for a thread that does nothing—and our asynchronous task does quite a bit more than nothing: it opens an HTTP connection, makes a request, and parses the HTML response body.

The upshot is that it is perfectly feasible to fire off a separate asynchronous task for every web page we want to visit. This frees us to write code that directly reflects the natural structure of the activity we’re trying to carry out.

Of course, the exponential nature of the job eventually poses problems for any implementation approach. The Internet is big. It’s worth thinking about what resource would run out first if we ran our spider with a high depth, and how you might redesign the program to scale up further. That’s beyond the scope of our example, though.

The spawning loop uses a Tokio collection called a JoinSet, which is simply a collection of tasks with a convenient join_all method for waiting for them all to complete. JoinSet::spawn starts a new asynchronous task on the same runtime as the caller, and adds it to the set. We call Arc::clone to give each new task its own Arc pointer to the Traversal.

Ideally, spawn_visit would not need to be a separate function; there’s no good reason that visit should not simply recurse to obtain a future that visits link, and call join_set.spawn itself. However, as of this writing, there is a bug in the Rust compiler that causes it to believe that the future of Traversal::visit’s return value is not safe to move between threads if we do so. Isolating the recursive call to visit in its own synchronous function works around this bug.

Extracting The Traversal’s Results

Here’s a main function that can set this all in motion:

#[tokio::main]
async fn main() -> Result<()> {
    let Some(url) = std::env::args().nth(1) else {
        anyhow::bail!("Usage: spider URL");
    };
    let start_url = Url::parse(&url)?;

    let client = Client::builder().user_agent(USER_AGENT).build()?;
    let traversal = Arc::new(Traversal::new(client, USER_AGENT.to_string()));
    visit(Arc::clone(&traversal), start_url, 2).await;

    let traversal = Arc::into_inner(traversal).unwrap();
    let seen = traversal.seen.into_inner().unwrap();

    let mut sorted = Vec::from_iter(seen.into_iter());
    sorted.sort();
    for page in sorted {
        println!("{page}");
    }

    Ok(())
}

This creates a fresh Traversal, and prints all URLs reachable within two links from the provided starting URL. (For example, we discovered that starting from Rust’s Wikipedia article, in two clicks you can reach articles for “Urediniospore”, “Cranberry jelly”, or “Hubble Space Telescope”; or any of 150,000 other URLs across 7,000 domains.)

It’s interesting to observe that this function is able to display the contents of the Traversal without locking any Mutexes. This is possible because we know that, since each call to Traversal::visit waits for all the tasks it has spawned to complete, by the time it returns, the Arc owned by traversal is the only Arc referring to that object in the entire program. Since no other thread has a clone of it, its reference count cannot increase without our knowledge. Arc::into_inner takes ownership of an Arc, verifies that its reference count is one, and then returns its referent by value. We effectively “unwrap” the Arc from around the Traversal, and take full ownership of it.

A similar argument follows for Mutex: if one has ownership of a Mutex, not just a reference to it, then there must not be any other thread that can access it, so we can unwrap the Mutex from around the value it protects, giving us full ownership of the seen and errors tables.

Waiting Vs. Blocking

As written, our spider program calls Html::parse_document directly from async code. Parsing a web page often takes a few hundred milliseconds, and that’s a problem. To understand why, we must dig a little deeper into how Tokio works.

The spider program can spawn thousands of tasks at once, but Tokio uses only a handful of system threads, by default one per CPU core, to run all asynchronous code. Fortunately, our tasks spend a fraction of their time running on a thread. The rest of the time, they are stopped at an .await point: either in netiquette, waiting for a polite interval before contacting a server, or in reqwest, waiting for network I/O.

When a task reaches an .await point and can’t immediately proceed, it relinquishes control back to the runtime. Tokio sets the waiting task aside. If you could look inside the Tokio runtime while this program runs, you would see a small number of tasks actually running on system threads; a large number of tasks that are set aside, waiting; and possibly some tasks in queue, ready for a worker thread to pick them up and run them. This last set includes tasks for which data has just arrived from the network. (If you’ve ever peeked inside an operating system, this will be a familiar sight. An asynchronous runtime often acts like an operating system in miniature, managing your program’s tasks the way an operating system manages threads and processes.)

This arrangement works smoothly as long as each task is well-behaved. If enough tasks run on a worker thread for long enough without an .await, they will hog all of Tokio’s threads and prevent other tasks from running, degrading the responsiveness of the system.

In an excellent blog post, “Async: What is blocking?”, Tokio maintainer Alice Rhyl wrote:

To give a sense of scale of how much time is too much, a good rule of thumb is no more than 10 to 100 microseconds between each .await. That said, this depends on the kind of application you are writing.

When Html::parse_document(body) runs for 100 milliseconds, we are exceeding the high end of this rule-of-thumb limit by a factor of 1,000. The program will run, and as written it has no need for Tokio to stay responsive. But if we added, say, a graphical visualization of the spider’s progress, also running in Tokio worker threads, this could cause dropped frames. If we added a terminal-based user interface, it might be slow to respond to keystrokes. In a production network service, the effect on response times would be even worse: a few bad tasks can crowd out thousands of other requests.

One partial fix is to use a blocking task, created with tokio::task::spawn_blocking. The second half of page_links can be replaced with this:

// Spawn a blocking task (not actually the best fix; see below)
let url = url.clone();
tokio::task::spawn_blocking(move || {
    let doc = Html::parse_document(&body);
    let link_selector = Selector::parse("a[href]").unwrap();
    Ok(...)
})
.await
.expect("HTML parsing task panicked")

Note that spawn_blocking takes a non-async closure as its argument. Tokio runs that closure on a separate thread, so it won’t interfere with Tokio’s responsiveness. spawn_blocking returns a future so that the async caller can wait for the blocking work to finish. The return value is an error if the task panicked.

However, there’s a problem with this plan. Tokio spawns a system thread for each blocking task, up to a limit of several hundred by default. This design is meant for code that uses blocking system calls, such as writing to a slow disk. But the work we’re doing here is CPU-intensive; it would be counterproductive to spawn more threads for this work than the number of CPUs in the system.

We should, therefore, use a thread pool designed for CPU-intensive work:

use tokio::sync::oneshot;

// Spawn a Rayon task (the correct fix)
let (sender, receiver) = oneshot::channel();
let url = url.clone();
rayon::spawn(move || {
    let doc = Html::parse_document(&body);
    let links = ...;
    sender.send(links).unwrap();
});
Ok(receiver.await.unwrap())

The function rayon::spawn() runs a closure on Rayon’s thread pool. However, this function doesn’t support returning a value to the caller, so we must build that for ourselves, using Tokio’s oneshot channel. Like the std::mpsc::channel and sync_channel functions we used in the previous chapter, tokio::oneshot::channel() returns a sender and a receiver, but a oneshot channel is designed to be used only once. The send method takes self by value, so that the sender value is consumed when used; and instead of calling receiver.recv(), we simply use receiver.await to wait for a value to be delivered, consuming the receiver.

Oneshot channels often solve minor problems like this. Since the receiver is a future, and the sender is a way to directly provide the receiver’s value, oneshot::channel() can be used to turn any computation into a future.

This completes our spider program. The lesson to take away is this: In an asynchronous program, there are several kinds of work, and getting the best performance requires implementing and running these workloads in different ways.

  • CPU-light, nonblocking work only needs a fraction of a thread’s time. It is written with async and await and runs on the Tokio worker pool.

  • Code that uses blocking system calls should run in Tokio blocking tasks.

  • CPU-intensive computation should run in a separate thread pool, such as Rayon.

spawn_blocking, rayon::spawn, and oneshot channels are the bridges that allow programs to span these different worlds.

Asynchronous Versions of Blocking Tools

The rule, then, is that asynchronous code must avoid blocking the thread it runs on. That’s easy to say, but the restriction cuts surprisingly deep. Many familiar APIs, such as std::thread::sleep and std::net::TcpStream::connect, block the calling thread. In asynchronous code, you must use the asynchronous equivalents, which are generally designed to work the same, except for needing extra .awaits here and there.

For example, pausing for a second in regular blocking code looks like this:

std::thread::sleep(Duration::from_secs(1));

This asks the operating system to suspend the calling thread and wake it up after a second has passed.

Tokio offers a straightforward asynchronous equivalent:

tokio::time::sleep(Duration::from_secs(1)).await;

This asks Tokio to suspend our async code at the .await point and wake it up a second later.

Table 20-1 lists common features of the standard library and some other useful crates that have direct equivalents in Rust’s async ecosystem. Tokio provides the async versions, with a few exceptions.

Despite all our warnings, in two cases we recommend using blocking APIs instead of the asynchronous APIs listed in Table 20-1.

First, tokio::fs is not like the other APIs listed in this table. The default implementation actually uses the blocking APIs from std::fs, wrapping each call in spawn_blocking. That imposes overhead on every operation. For large chunks of disk I/O work, you can get better performance by doing a single spawn_blocking of your own and using std::fs in the blocking task. For smaller jobs, like reading a configuration file, it’s not unreasonable to call std::fs directly from async code.

Second, std::sync::Mutex and RwLock are better than their asynchronous equivalents for locks that are never held across an .await point, as long as contention is low. This is the case for most locks in practice.

This second recommendation is so counterintuitive that we will take a moment to explain. There are two major differences between std locks and Tokio locks. One is that std locks and the operating system primitives they rely upon have been heroically fine-tuned over the course of decades. They use almost no memory, and the uncontended path through a mutex is a few machine instructions. The other difference is that Tokio’s locks are designed for async code. Tokio’s Mutex::lock method returns a future which the calling task must .await; if someone else is holding the mutex, the task is suspended like any other waiting task, without blocking the worker thread. A std mutex would block the thread. That’s a severe performance hazard if the lock is unobtainable for a long time, and that’s why contention is the deciding factor.

Whatever your use case, holding a std lock across an .await point is usually a mistake, likely to cause other worker threads to block, and even deadlock, when they try to acquire the same lock. (Clippy, the Rust linter, can detect the most common forms of this bug.)

It’s a little odd that tokio::sync is the name of the module that provides an async version of the std::sync toolkit. Both modules are named sync because they provide “synchronization primitives”, tools for coordination and communication across multiple tasks or threads. This use of “synchronization” dates back to the 1970s, if not earlier. Meanwhile “asynchronous I/O”, the basis of async Rust, dates back to the 1980s, so the two similar-sounding but mostly-unrelated terms were on a collision course for some 30 years before they met in tokio::sync! In any case, there’s no contradiction in saying that async tasks need synchronization primitives. They need to coordinate.

Tasks and ’static

Let’s look at the type signature of Tokio’s spawn function:

// in tokio::task
fn spawn<F>(future: F) -> JoinHandle<F::Output>
where
    F: Future + Send + 'static,
    F::Output: Send + 'static,

How does this compare to the standard library’s function for spawning threads?

// in std::thread
fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: FnOnce() -> T + Send + 'static,
    T: Send + 'static,

The async version takes a future instead of a closure, but otherwise these are very similar. The future or closure must be Send and 'static, so that it is safe to run on another thread for as long as it takes to finish. The return type must be Send and 'static so that it’s safe to transfer the return value back again when the JoinHandle is joined.

We keep stressing these similarities between async code and threads because it’s easy to forget how similar they are. Again and again, when we have trouble with asynchronous code, we’ve found it illuminating to ask: What if we were using threads? Very often, the answer is that we ⁠’d have the same problem, for the same reasons, and can solve it the same way.

For instance, if you try to spawn a future that borrows a local variable, Rust complains:

let hosts = vec!["example.com", "example.org"];
tokio::task::spawn(async {
    // error: async block may outlive the current function, but it
    // borrows `hosts`, which is owned by the current function
    for &host in &hosts {
        let result = reqwest::get(format!("https://{host}/")).await;
        ...
    }
});

You’d get similar errors if you tried the same thing with std::thread::spawn, and the fix is similar: use an async move block to move the data into the new task instead of borrowing it. Like a thread, a task needs to own its data.

If you can’t move the value, because the parent task still needs it, you must clone it. Then you can move the clone. This is a very common technique; often the few lines of code leading up to an async move are local variables cloning data owned by the parent task. If a full copy is too expensive, wrap it in an Arc<T>, which is cheaply cloneable. (And if that sounds familiar, it’s because you were paying attention in “Sharing Immutable Data Across Threads”, where we solved a thread-spawning problem using the same technique.)

Tasks and Send

In addition to 'static, a future spawned with Tokio must implement the Send marker trait. As we discussed in “Thread Safety: Send and Sync”, types that implement Send can be safely moved from one thread to another. When a single task spawns a few hundred child tasks, Tokio distributes them among its worker threads. The futures must be Send to make this safe. (Tokio workers also practice work-stealing, moving tasks from thread to thread to balance load. This too requires Send.)

But how can you tell if your future implements Send? We said in Chapter 19 that a struct or enum implements Send if all its fields are Send. Closures and futures follow the same intuition, although the “fields” of those types aren’t explicitly written down anywhere in your code. Each closure in your code has its own custom type. This type is Send if all the values the closure captures are Send.

Futures created by async code work the same way. They act as though they have private fields containing all the data they will need to run. A future created by an async move block contains each variable it captured, just like a move closure. Futures created by calling an async fn contain all the function arguments. And all async futures have additional private fields for storing the state of the async code at each .await point: all local variables in scope, and even anonymous temporary values in flight at the .await. If all these values are Send, the future is Send.

This list of types is never spelled out in code, so the Send restriction is easy to trip over by accident. For example, the following code looks innocent enough:

use std::rc::Rc;

async fn reluctant() -> String {
    let string = Rc::new("ref-counted string".to_string());

    some_asynchronous_thing().await;

    format!("Your splendid string: {string}")
}

tokio::spawn(reluctant());

In this case, reluctant’s future must use string after the await, so the future will, at least sometimes, contain an Rc<String> value. Since Rc pointers cannot be safely shared between threads, the future itself cannot be Send. And since spawn only accepts futures that are Send, Rust objects:

error: future cannot be sent between threads safely
    |

    |                  ^^^^^^^^^^^ future returned by `reluctant` is not `Send`
    |
    = help: within `impl Future<Output = String>`, the trait `Send` is not
            implemented for `Rc<String>`
note: future is not `Send` as this value is used across an await
    |
14  |         let string = Rc::new("ref-counted string".to_string());
    |             ------ has type `Rc<String>` which is not `Send`
...

                                              maybe used later

    |
174 |     pub fn spawn<F>(future: F) -> JoinHandle<F::Output>

    |                     ^^^^ required by this bound in `spawn`

This error message is long, but it has a lot of helpful detail:

  • It explains why the future needs to be Send: tokio::spawn requires it.

  • It explains which value is not Send: the local variable string, whose type is Rc<String>.

  • It explains why string affects the future: it is in scope across the indicated await.

To fix the error, we just need to avoid holding an Rc<String> across an await point.1

One way to do this is to restrict the scope of the non-Send value so that it doesn’t cover any await expressions and thus doesn’t need to be saved in the function’s future:

async fn reluctant() -> String {
    let return_value = {
        let string = Rc::new("ref-counted string".to_string());
        format!("Your splendid string: {string}")
        // The `Rc<String>` goes out of scope here...
    };

    // ... and thus is not around when we suspend here.
    some_asynchronous_thing().await;

    return_value
}

Another solution is simply to use std::sync::Arc instead of Rc. Arc uses atomic updates to manage its reference counts, so Arc<String> is Send.

Although eventually you’ll learn to recognize and avoid non-Send types, they can be a bit surprising at first. (At least, your authors were often surprised.) For example, older Rust code sometimes uses generic result types like this:

// Not recommended!
type GenericError = Box<dyn std::error::Error>;
type GenericResult<T> = Result<T, GenericError>;

This GenericError type uses a boxed trait object to hold a value of any type that implements std::error::Error. But it doesn’t place any further restrictions on it: if someone had a non-Send type that implemented Error, they could convert a boxed value of that type to a GenericError. Because of this possibility, GenericError is not Send, and a future that holds this kind of error value across an .await point isn’t Send either.

This problem doesn’t come up if you use stricter generic error types, like the ones we suggested in “Working with Multiple Error Types”:

type GenericError = Box<dyn std::error::Error + Send + Sync + 'static>;
type GenericResult<T> = Result<T, GenericError>;

This dyn type explicitly requires the underlying error type to implement Send, so it is Send too, and it won’t cause problems in async code.

For your own trait definitions, you can avoid this kind of trouble by writing trait MyTrait: Send { ... }, forcing all types that implement your trait to be Send. Then code using dyn MyTrait won’t need to add + Send. And, of course, you can extend this to trait MyTrait: Send + Sync + 'static, if needed.

You might be wondering why Rust lets you write non-Send code in the first place, if it isn’t going to let you run it! But it’s Tokio’s multithreaded runtime that imposes the Send requirement, not Rust itself. In fact, Tokio’s Runtime::block_on method does not require a Send future, because it doesn’t use Tokio’s thread pool. In general, though, if you use Tokio, most of your futures will need to be Send.

Asynchronous Closures

There is not too much to say about async closures. They are just what you’d expect. They look like regular closures, but with an async keyword stuck on the front. Like an async fn, an async closure returns a future.

// spawn a task per user
let tasks = users
    .into_iter()
    .map(async |user| {
        add_to_group(user, group).await
    })
    .collect::<JoinSet<_>>();

let results = tasks.join_all().await;

In this example, we use the iterator .map method to call an async closure for each user in the vector users, producing a sequence of futures. Then we collect those futures into a JoinSet, which spawns one task per future. This is an easy way to run some tasks concurrently.

Just as ordinary closures are often used with iterators, asynchronous closures are often used with the asynchronous analogue of iterators: streams. The futures crate provides Stream and StreamExt traits. These traits are similar to Iterator, but they produce items asynchronously: the next method of a stream is an async method. StreamExt offers a smorgasbord of familiar methods (map, filter, fold, collect, and so on), many of which take asynchronous closures as arguments. However, StreamExt also includes a few astonishing features that add an element of concurrency over what regular iterators can do. For example, StreamExt::for_each applies an asynchronous closure to each element of a stream, one at a time; but there’s also StreamExt::for_each_concurrent, which processes multiple elements concurrently, up to a limit, which you specify as an argument.

// Rolling reboot of a set of servers, 8 at a time
futures::stream::iter(&servers)
    .for_each_concurrent(8, async |server| {
        server.reboot_and_wait_until_started().await;
    })
    .await;

This example creates a stream from an ordinary iterator using futures::stream::iter. Then it uses for_each_concurrent to call an asynchronous closure on each value, with up to 8 closure calls running asynchronously at a time.

AsyncFn

Analogous to Fn, FnMut, and FnOnce, there are three built-in traits for asynchronous closures: AsyncFn, AsyncFnMut, and AsyncFnOnce. These traits cover anything callable that returns a future: so, async fns and async closures, certainly; but also regular closures and functions that return futures, like the announce and copying_announce examples earlier in this chapter.

Unfortunately, the AsyncFn traits do not promise to return a Send + 'static future. This means they can cause problems when you want to use a closure with tokio::spawn in generic code:

async fn kick_off_task<F>(closure: F)
where
    F: AsyncFn() + Send + 'static,
{
    tokio::spawn(async move {
        ...
        closure().await;  // error: awaits a future which is not Send
        ...
    });
}

How can we work around this? We need to require the future type—not only the closure type F, but the type of future it returns—to be Send + 'static.

It’s possible to write a function signature that does this, but not by using AsyncFn(). Use the trait Fn() -> Fut instead. This makes the future type explicit:

fn kick_off_task<F, Fut>(closure: F)
where
    F: Fn() -> Fut + Send + 'static,
    Fut: Future<Output = ()> + Send + 'static,

Once we’ve given the future’s type a name in our code, Fut, we can easily spell out the requirements that will satisfy tokio::spawn in our function’s where clause.

Asynchronous Functions In Traits

Traits can include async functions, but by default those functions can’t be run in Tokio’s multithreaded runtime. There isn’t an idiomatic way to declare an async fn type signature that says “this must return a future that is Send“.

Two crates offer fixes for this problem:

  • The trait-variant crate provides an attribute, #[trait_variant::make], that you can use on a trait to declare a Send “variant” of that trait. The variant is like the original, but with its async fns rewritten to return Send futures.

  • The async-trait crate provides its own attribute, #[async_trait::async_trait]. This also rewrites your async fn signatures, but in a way that additionally makes your trait dyn-compatible.

The Future trait itself is dyn-compatible, so you can declare boxed dyn future types, similar to what we’ve seen earlier for closures and errors:

type BoxedFuture<T> = Box<dyn Future<Output = T> + Send>;

The async-trait crate works by transforming all your async methods’ type signatures to return boxed futures like this. This imposes virtual method call overhead when the futures are polled, but that’s necessary in order to make async methods dyn-compatible.

Cancellation

There is no safe way to kill a single thread of a process. Safe cleanup is simply impossible, given that there’s no way to tell precisely what the thread is doing. It might be holding locks, panicking, in the midst of dropping a large data structure, or even running non-Rust code, such as a system library. But async code is designed to yield frequently, at .await points, and every time it does so, all its variables and local state are neatly stored in the future. As a consequence, async code can be safely cancelled.

This capability has several uses:

  • Killing a single running task (tokio::task::JoinHandle::abort and JoinSet::abort_all);

  • Applying a timeout to an any future at all (tokio::time::timeout);

  • Running any number of futures until we decide to cancel them (tokio_util::sync::CancellationToken::run_until_cancelled);

  • Letting multiple futures race and handling whichever is ready first, cancelling the others (tokio::select!).

In the remaining pages of this chapter, we’ll touch on each of these features. To begin with, here is what a timeout looks like in Rust:

let result = tokio::time::timeout(
    Duration::from_secs(5),
    reqwest::get("https://example.com/"),
).await;

This snippet runs the reqwest::get future for up to 5 seconds. If the request finishes in time, the result will be an Ok wrapping the reqwest::Result produced by get, a nested Result. If time runs out, result will be Err(Elapsed), a Tokio error type just for expired timeouts.

When you tokio::spawn or await a future, or pass it by value to tokio::time::timeout, you’re handing over ownership of that future. Later, if the Tokio runtime needs to cancel that future, it simply drops it. This in turn drops any local variables or other values wrapped up in the future, so any memory or resources it was using are cleaned up, a bit like panic unwinding.

This cleanup scheme is good and bad. Aborting a task is safe and won’t normally leak memory. In the case of reqwest::get, drop methods inside reqwest will make sure the network connection is appropriately closed or returned to its connection pool. But in other cases, stopping your code at a random .await point can leave work half-done, and that can cause bugs. In general, you shouldn’t cancel asynchronous code unless you have some sense of what it’s doing.

For example, if you abort a network server task, it won’t gracefully stop accepting new requests, finish up serving the few in-flight requests, and then exit. Clients will get errors: their network connections will be closed with no response.

Cancel safety

Cancellation is like panic unwinding in another regard: if you’re not careful, it can cause your code to break its invariants. Consider a function that reads a message from a channel, then updates a data structure. The code is naturally expected to maintain the invariant that the data structure reflects all messages received so far. Now, between the moment a message is received and the moment the update is complete, the invariant does not quite hold. One message is in flight. This momentary discrepancy is unavoidable, and harmless as it’s only for the duration of the function. Since mut access to the data structure is exclusive, Rust can even guarantee that no other code can observe the discrepancy. But if the task panics or is cancelled at an await point before the update is complete, the invariant stays broken permanently.

The term for proper behavior in case of cancellation is “cancel safety”. Making sure your code’s invariants are intact at each .await point is the first step in making it cancel safe. But ultimately cancel safety is not a precisely defined term. The questions it poses are: If someone cancels this code, are they in for an unpleasant surprise? Have I treated not only ? but every .await as a possible early exit point, throughout this code?

If that sounds like too much work, don’t do it. Plenty of asynchronous code makes no claim to be cancel safe. Just don’t use abort, timeout, and so on to cancel that code. Don’t leave the code running when you exit the program, either: the Tokio runtime cancels all remaining asynchronous tasks when it shuts down.

As with panic safety, enforcing cancel safety is beyond what Rust’s type system can do for you. We therefore resort to documentation. Many asynchronous methods in Tokio have documentation with an explicit “Cancel safety” section. For example, AsyncReadExt::read promises not to consume any bytes in case of cancellation. Canceling code with no documented cancel safety guarantees is risky.

Racing futures with tokio::select!

So far, we’ve seen futures combined in sequence with .await and in parallel with JoinSet. There’s one more common way to combine futures: racing them. This is not as scary as the name’s association with data races and race conditions might make it sound, but it does capture the same idea: racing futures means running several at once and responding only to the first one that completes. This pattern pops up all over the place. Any operation that can be cancelled by sending a message to a oneshot channel or a timeout is racing two futures against each other, and a server handling incoming connections on different ports or different protocols can be expressed as racing futures from each one.

Despite being a common pattern, writing code that actually drives futures this way by hand is pretty complicated, so Tokio provides a macro to help out, called select!. A select! invocation looks similar to a match statement:

tokio::select! {
    response = reqwest::get("http://ftp.se.debian.org/debian/ls-lR.gz") => {
        println!("Sweden was faster. (Status {})", response?.status());
    }
    response = reqwest::get("http://ftp.ca.debian.org/debian/ls-lR.gz") => {
        println!("Canada was faster. (Status {})", response?.status());
    }
}

Each arm of the select! consists of a variable name (response), a future, and then some code. All of the futures are polled until one of them completes; then, the code associated with that future is run, with the future’s output bound to the provided name. The other futures are simply dropped, and thus cancelled.

The futures in each arm of a select! invocation can have different Output types. This makes it possible to wait on all kinds of things at the same time. For instance, an asynchronous timeout function could be implemented like this:

async fn timeout<T, F>(future: F, t: Duration) -> Option<T>
where
    F: Future<Output = T> + Send + 'static,
{
    tokio::select! {
        _ = tokio::time::sleep(t) => None,
        value = future => Some(value)
    }
}

If the sleep duration elapses before the provided future completes, the function returns None, and the future the user passed in is cancelled.

Racing futures can be useful at a higher level, too. Many servers are essentially a single loop that spawns a task to deal each request and then goes back to listening for incoming connections. As long as all the futures involved are cancel-safe, select! makes this pattern simple to write:

use std::io;

use futures::channel::oneshot;
use tokio::net::{TcpListener, TcpStream, UnixListener, UnixStream};

async fn serve(mut shutdown: oneshot::Receiver<()>) -> io::Result<()> {
    let tcp_listener = TcpListener::bind("127.0.0.1:9889").await?;
    let unix_listener = UnixListener::bind("/tmp/mysocket.sock")?;
    loop {
        tokio::select! {
            tcp_result = tcp_listener.accept() => {
                let (stream, addr) = tcp_result?;
                println!("TCP connection from {addr:?}");
                tokio::spawn(handle_tcp(stream));
            }
            unix_result = unix_listener.accept() => {
                let (stream, addr) = unix_result?;
                println!("Unix domain socket connection from {addr:?}");
                tokio::spawn(handle_unix(stream));
            }
            _ = &mut shutdown => {
                break;
            }
        }
    }
    handle_shutdown().await
}

When the select! is reached, the accept() futures from each listener and the shutdown future are all run concurrently. select! picks which branch to poll first at random, to prevent a branch with a future that often completes immediately from hogging the available CPU time.

If one of the listeners receives a new connection, the other’s future is cancelled. The winning branch spawns a new task to handle the incoming connection, and the loop starts over, calling accept() again to produce a new future for each listener. The shutdown channel, on the other hand, is passed to select! by mutable reference. The reference is dropped at the end of the loop, but the shutdown receiver itself is still available to be awaited again in the next iteration.

Each of the futures used in this select! loop explicitly documents its cancel safety. Without a guarantee that each one is designed with cancellation in mind, messages could be lost when the other branches’ futures are dropped. This is a classic mistake in asynchronous code that is very likely to lead to frustrating and difficult to diagnose problems.

Shutdown

To close out this chapter, a few words on the subject of winding things down.

In general, programs that use threads should shut them down before exiting. Otherwise, when the program exits, every thread is instantly terminated, likely leaving some work half-finished.

The same goes for asynchronous programs. We won’t fully describe Tokio shutdown here, but Tokio does cancel all tasks when you drop a tokio::Runtime or return from a main function marked #[tokio::main]. It drops those futures in an unspecified order. If a task tries to spawn more tasks while Tokio is trying to shut down, it panics. If any blocking tasks don’t finish promptly, Tokio leaves them running. So there are plenty of things that could go somewhat wrong if you don’t shut down all tasks before exiting.

Calling tokio::spawn and ignoring the JoinHandle makes correct shutdown difficult. It’s better to use tokio::task::JoinSet and call .join_all().await before exiting.

That alone is sufficient for programs like our spider, which has a finite amount of work to do and shuts down only when it’s done. Other programs need to shut down on demand. In the remaining pages of this chapter, we’ll cover a few ways to do this: aborting tasks, shutdown signals, and cancellation tokens.

Aborting Tasks

The simplest way to stop a task is to call the abort method on the handle that spawn returns.

let handle = tokio::spawn(play_fugazi_forever());
tokio::time::sleep(ONE_HOUR).await;
// ...that's enough of that
handle.abort();
let result = handle.await;
assert!(result.unwrap_err().is_cancelled());

When this code calls handle.abort(), Tokio stops the spawned task and drops the future.

There are a few caveats to keep in mind:

  • Consider the cancel safety of the code being aborted. If play_fugazi_forever() is implemented via an audio library with drop methods that stop playback and leave the system in a reasonable state, this will behave as desired. Otherwise, you may be left listening to post-hardcore punk rock for some time.

  • If the task is running on another CPU at the moment you abort it, Tokio will let it run until it yields before dropping it. This means the task may still be running when abort() returns! To ensure the task has been fully cleaned up, we use handle.await on the next line.

  • Aborting a task does not automatically abort any child tasks it spawns. However, when a JoinSet is dropped, any remaining tasks in the set are aborted. If you consistently use local JoinSets for spawning child tasks, then aborting one task will recursively tear down its descendants as well. However, all the tasks had better be cancel safe, since you’re arranging for them to be automatically cancelled!

  • Blocking tasks created with tokio::task::spawn_blocking are basically threads. They can’t be aborted.

If we need to cancel a blocking task, or we have any task at all that wants to run some code other than drop methods during shutdown, we need another plan.

Shutdown Signals

Back in Chapter 2, we created an HTTP server using the actix-web crate:

let server = HttpServer::new(...);

println!("Serving on http://localhost:3000...");
server
    .bind("127.0.0.1:3000")
    .expect("error binding server to address")
    .run()
    .await
    .expect("error running server");

This server runs forever. The only way to stop it is to kill the process, which we did during development by running it in our terminal and hitting Ctrl+C.

A real web service should shut down gracefully when the operating system tells it to. Actix offers a couple of methods for configuring server shutdown:

...
server
    .shutdown_signal(shutdown_signal)
    .shutdown_timeout(5)  // seconds
    .bind("127.0.0.1:3000")
    ...

The shutdown_signal method specifies that in addition to serving requests, Actix should await the given argument, which must be a future satisfying Future<Output = ()> + Send + 'static. When the shutdown signal resolves, the server begins to shut down. Any requests in flight are allowed to run for a time, specified by shutdown_timeout, so they have a chance to finish normally. Requests that don’t finish in time are aborted. (Methods like shutdown_timeout should take std::time::Duration arguments. Actix’s use of an integer here is a minor API botch.)

For example, if we were to run this service in production, we might want it to react to the SIGTERM signal, the standard way for a Unix system to tell a service to shut down. Tokio provides a Unix-only Signal type that supports this use case:

use tokio::signal::unix::{self, SignalKind};

let mut sigterm = unix::signal(SignalKind::terminate())
    .expect("error installing signal handler");
let shutdown_signal = async move {
    // Wait for the first SIGTERM to be delivered.
    let _ = sigterm.recv().await;
};

println!("Serving on http://localhost:3000...");
server
    .shutdown_signal(shutdown_signal)
    .shutdown_timeout(5)
    .bind("127.0.0.1:3000")
    ...

Shutdown signals don’t necessarily have anything to do with Unix signals, though. Any future that waits for the desired shutdown-triggering event will do.

Other Rust server implementations, such as Axum and Tonic, also provide APIs that follow this pattern. It’s sometimes called “graceful shutdown”.

Cancellation tokens

Now we have dispensed with all the easy shutdown cases. Cancellation tokens are for the more complicated ones.

In “Atomics”, we showed how an Arc<AtomicBool> can be used to request cancellation across threads. Any thread can set the shared boolean value to true, and other threads can periodically check the value and exit if it’s set. The CancellationToken type, supplied by tokio-util crate, is the deluxe version of Arc<AtomicBool>, with extra features for cancelling all kinds of code.

A cancellation token is like a boolean variable: it either is or isn’t cancelled. CancellationToken::new() creates a new token. Cloning a CancellationToken, like cloning an Arc<AtomicBool>, creates another reference to the same boolean. Anyone holding one clone of a token can mark them all as cancelled by calling token.cancel(). This doesn’t invasively stop any code from running; the idea is that you’ll pass clones of a cancellation token to all your code that needs to shut down on demand. Different kinds of code will use the token to implement shutdown in different ways:

  • Blocking or CPU-intensive code can periodically call token.is_cancelled() and exit when it returns true.

  • A cancel-safe future f can be run using token.run_until_cancelled(f).await, which returns an Option. If the token is cancelled before the future completes, it returns None.

  • Code that needs a shutdown signal can use token.cancelled_owned(). This returns a future that resolves to () when the token is cancelled.

  • Other asynchronous code can wait for cancellation by calling token.cancelled().await. A task might use select! in its main loop to wait for a cancellation as one of several possible events:

    loop {
    tokio::select! {
        // handle other events...
        tcp_result = tcp_listener.accept() => ...
        unix_result = unix_listener.accept() => ...

        // handle cancellation
        () = token.cancelled() => {
            eprintln!("canceled, exiting");
            break;
        }
    }
}

In addition, CancellationToken supports a hierarchy of “child tokens” to represent a hierarchy of chunks of work to be cancelled. The variety of features here makes cancellation tokens especially useful for adding cancellation to an existing codebase that already has a lot going on.

Conclusion

Asynchronous code is ubiquitous in the Rust ecosystem; it’s pretty much the way Rustaceans write servers or I/O-heavy code of any kind. To that end, we’ve built this chapter around Rust’s asynchronous language features, the crates that work with them, and the tricks of the trade to make it all work. We’ve left the matter of how any of this is actually implemented completely untouched. In the next chapter, we’ll look under the hood and see how asynchronous Rust actually works.
