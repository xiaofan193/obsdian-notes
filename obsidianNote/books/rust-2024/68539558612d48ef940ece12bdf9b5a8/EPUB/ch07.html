Rust 处理错误的方式非常独特，因此值得用一整章来介绍。这里并没有什么复杂的概念，只是一些可能对你来说比较新的知识。这一章将介绍 Rust 中两种不同的错误处理方式：panic 和 Result s。


普通的错误是通过 Result 类型来处理的。 Result 这类错误通常是由于程序外部的因素导致的，比如错误的输入、网络故障或权限问题等。这种情况的发生并不在我们能够控制的范围之内；即使是一个没有漏洞的程序，也偶尔会遇到这类问题。本章的大部分内容都是关于这类错误的。不过，我们首先会讨论“恐慌”这种错误，因为它比 Result 类型更简单一些。


恐慌是针对另一种错误，那种本就不应该发生的错误。

恐慌/惊慌失措


当程序遇到如此严重的错误时，程序就会陷入恐慌。这种情况就像是：

  • 超出数组边界的访问行为

  • 整数除以零的运算

  • 在恰好是 Err 的 Result 上呼叫 .expect()

  • 断言失败


此外，还有宏 panic!() ，用于处理那种由代码自身检测到出现错误的情况。在这种情况下，你需要直接触发恐慌操作。 panic!() 支持可选的 println!() 格式参数，用于构建错误信息。

这些问题的共同点是：它们都可以归结为——不用说得那么精确——程序员的过错。一个不错的经验法则是：“不要惊慌。”

但我们都可能会犯错。当这些本不该发生的错误真的发生时，该怎么办呢？令人惊讶的是，Rust 提供了一种选择：在出现恐慌情况时，Rust 可以选择是恢复堆栈的操作，还是直接终止进程。恢复堆栈的操作是默认设置。

解开


当海盗们分配一次袭击所得的战利品时，船长会得到一半的财富。普通船员则分得另一半的公平份额。（海盗们不喜欢分数，所以如果分配结果不公平，那么会向下取整，剩余的部分则归船上的鹦鹉所有。）

fn pirate_share(total: u64, crew_size: usize) -> u64 {
    let half = total / 2;
    half / crew_size as u64
}


这种方法在几个世纪内或许都能正常工作，直到有一天被发现，那个船长其实是那次袭击中唯一的幸存者。如果我们向这个函数传递一个零值，那么就会引发除以零的错误。在 C++中，这种行为会被视为未定义行为。而在 Rust 语言中，这种情况会引发恐慌行为，具体表现通常如下：

  • 终端上显示了一条错误信息：

    thread 'main' panicked at pirates.rs:3780:9:
attempt to divide by zero
note: Run with `RUST_BACKTRACE=1` for a backtrace.

    如果你设置了 RUST_BACKTRACE 环境变量，那么根据消息中的提示，Rust 在此时也会输出堆栈内容。


  • 当前函数所使用的所有临时值、局部变量或参数都会被释放。释放这些资源意味着要清理相关状态：程序中使用的所有 String 资源都会被释放，所有打开的 File 资源也会被关闭，等等。用户自定义의 drop 方法也会被调用；详情请参阅“释放”部分。在 pirate_share() 的情况下，无需进行任何清理工作。


    当当前的函数调用被处理完毕后，我们就会继续处理它的调用者，以同样的方式释放其变量和参数。然后我们继续处理该函数的调用者，如此循环下去，一直追溯到函数的创建者。

  • 最终，该线程结束执行。如果引发恐慌的线程就是主线程，那么整个过程就会结束（并会返回一个非 0 的退出代码）。


或许，所谓的“恐慌”其实是一个具有误导性的名称，因为它描述的是一种有序的过程。恐慌并非是一种无序的行为。它更像是 Java 中的 RuntimeException 或 C++中的 std::logic_error ——一种定义明确的行为，只是这种行为本就不应该发生而已。


恐慌是安全的。它不会违反 Rust 的任何安全规则；即使你在标准库方法的执行过程中突然陷入恐慌，也绝不会造成悬空的指针或内存中未初始化的值。Rust 能够在发生任何不良情况之前捕获那些无效的数组访问或其他错误。继续操作是不安全的，因此 Rust 会释放栈上的资源。但其余的操作仍然可以继续进行。


恐慌是发生在单个线程中的现象。一个线程可能处于恐慌状态，而其他线程则继续正常运行。在第十九章中，我们将展示如何让父线程能够检测到子线程的恐慌情况，并妥善地处理这一错误。


还有一种方法可以捕获堆栈逆向操作的情况，从而使线程能够继续运行。标准库函数 std::panic::catch_unwind() 就实现了这一功能。我们不会详细讲解如何使用它，但 Rust 的测试框架在测试中出现断言错误时就是使用这种机制来恢复程序的正常运行的。（在编写可以从 C 或 C++调用的 Rust 代码时，这种机制也是必要的，因为跨非 Rust 代码的逆向操作可能会导致程序立即终止；详见第 24 章。）


你可以使用线程和 catch_unwind() 来处理恐慌情况，从而让程序更加健壮。不过有一个重要注意事项：这些工具只能捕获那些能够重新连接堆栈的恐慌情况。并不是所有的恐慌情况都会以这种方式处理。

终止操作


堆栈的撤销是 Rust 的默认 panic 行为，但在某些情况下，Rust 不会尝试撤销堆栈操作。

堆栈溢出问题


当一个程序出现递归失控的情况时，最终会耗尽堆栈空间。这种情况是致命的。Rust 语言会输出一条消息，然后终止整个程序。


例如在 Linux 系统上，Rust 会安装一个 SIGSEGV 处理程序，该程序能够检测程序是否试图将数据写入堆栈末端附近的保护页面。对于那些需要异常大堆栈帧的函数来说，普通的变量访问可能会跳过保护页面，因此编译器会生成“堆栈探测”代码，以确保这种技术仍然有效。

内存不足


这种情况通常不在 Rust 的控制范围内。当程序请求内存时，大多数操作系统都会同意分配内存，即使实际可用的物理内存不足以满足需求。如果内存不足，系统会寻找那些占用大量内存的进程并将其终止。如果程序使用了过多的内存，那么程序就会被终止。Rust 对此无能为力。


在极少数内存分配失败的情况下，Rust 会终止该进程。如果您的程序中有一些地方需要处理内存分配失败的情况，您可以使用像 Vec::try_reserve 这样的可失败方法，相关内容可以在“增长和缩小向量”一文中找到。

双重恐慌

如果在一个 .drop() 方法中，在 Rust 仍在尝试处理第一次 panic 的情况下，又触发了第二次 panic，那么 Rust 会终止该过程。

panic=abort


Rust 的恐慌行为是可以自定义的。如果你使用 -C panic=abort 选项进行编译，那么程序中的第一次恐慌会使程序终止。（使用这个选项后，Rust 无需知道如何恢复堆栈的状态，因此这样可以减小编译后的代码大小。）

恐慌之钩


在恐慌性帖子在展开或中止之前，首先会调用一个恐慌处理函数。这个函数的配置可以通过调用 std::panic::set_hook() 来实现。默认的恐慌处理函数会将其消息以及（根据 RUST_BACKTRACE 的配置）堆栈跟踪信息写入到 stderr 中。

如果您的程序有一个日志文件，那么最好设置一个 panic 钩子函数，以确保所有关于 panic 的消息都被记录下来。否则，panic 事件可能会因疏忽而未被记录到日志中，尤其是在非主线程和异步任务中发生的 panic 事件。在一个使用 tracing 包进行日志记录的项目中，panic 钩子函数可能如下所示：

use std::backtrace::Backtrace;
use std::panic::PanicHookInfo;

/// Panic hook to log panic info using the `tracing` crate,
/// instead of the default behavior of printing to stderr.
fn report_panic(panic_info: &PanicHookInfo) {
    let stack = Backtrace::force_capture();
    tracing::error!("{panic_info}\n\n{stack}");
}

fn main() {
    setup_logging();
    std::panic::set_hook(Box::new(report_panic));
    ...
}

标准类型的 Backtrace 能够捕获调用栈。它支持 Display 和 Debug 格式，除此之外没有其他特殊功能。需要注意的是，Rust 并不保证回溯信息的完整性和准确性。实际捕获到的信息可能会受到你的构建配置、硬件平台以及许多其他因素的影响。

调用 set_hook 一次就足以引发整个过程的恐慌。

其他恐慌宏程序

Rust 提供了一些额外的宏，这些宏可以无条件地引发恐慌，并且可以携带可选的格式字符串参数，就像 panic!() 那样。这些宏在恐慌消息中添加了不同的短前缀，但它们之间的真正区别在于对程序员来说的含义有何不同。

todo!(message...)


这是一个用于暂存你接下来要编写的代码的占位符。如果你在代码审查中看到这个标记，那很可能只是一个简单的错误；作者可能是在完成代码编写之后再请求进行评审的。请放心，这个提示信息只是用来提醒而已。 not yet implemented

unimplemented!(message...)

这看起来像是 todo!() 的某种表现，但似乎这种省略是有意为之。真正的警报信息应该是 not implemented 。

unreachable!(message...)

这是用于那些位于代码中的、无法被控制机制触及的位置的，比如在一个 for 循环之后，当你知道迭代器会一直产生值的时候。恐慌信息就是 internal error: entered unreachable code 。


关于 Rust 中的恐慌处理机制，我们的讨论就此结束。其实没什么好说的，因为普通的 Rust 代码并没有必要去处理恐慌情况。即使你使用了线程或 panic 钩子，所有的 panic 处理代码也往往集中在少数几个地方。期望程序中的每个函数都能预见并处理自己代码中的错误，这是不合理的。而由其他因素引起的错误则更是另当别论了。

结果


Rust 中不存在例外情况。那些可能失败的函数，其返回类型就会明确标明这一点：

fn get_weather(location: LatLng) -> Result<WeatherReport, io::Error>


Result 类型表示可能存在故障。当我们调用 get_weather() 函数时，它会返回一个成功结果 Ok(weather) ，其中 weather 是一个新的 WeatherReport 值；或者返回一个错误结果 Err(error_value) ，其中 error_value 是一个解释出错原因的 io::Error 信息。


由于存在 Rust 语言的特点，我们在调用这个函数时必须要编写一些错误处理代码。如果我们不对 Result 进行任何操作，就无法访问 WeatherReport 这个变量；而且，如果 Result 这个变量没有被使用，那么编译器会发出警告。


在第十章中，我们将了解标准库是如何定义 Result 的，以及如何定义自己类似的类型。目前，我们采用一种“实用指南”的方法，重点讨论如何使用 Result 来实现所需的错误处理功能。我们将探讨如何捕获、传递和报告错误，以及处理 Result 类型时常见的组织方式。

捕捉错误


处理 Result 问题最全面的方法，就是我们在第二章中介绍的方法：使用 match 表达式来进行处理。

match get_weather(hometown) {
    Ok(report) => {
        display_weather(hometown, &report);
    }
    Err(err) => {
        eprintln!("error querying the weather: {err}");
        schedule_weather_retry();
    }
}

这在 Rust 中相当于其他语言中使用的 try/catch 。当你想要直接处理错误时，就会使用这种方式，而不是将错误传递给调用者。

打印错误


有时候，处理错误的唯一方法就是将其输出到终端，然后继续前进。前面的例子展示了一种实现这一方法的方式：

eprintln!("error querying the weather: {err}");


标准库定义了几种错误类型，这些类型的名称都相当普通： std::io::Error 、 std::fmt::Error 、 std::str::Utf8Error 等。所有这些错误类型都实现了同一个接口—— std::error::Error trait。这意味着它们共享以下特性和方法：

println!() 等。

所有错误类型都支持 Display 和 Debug 格式说明符，因此可以与任何使用格式字符串的宏一起使用，包括 println!() 、 eprintln!() 、 format!() 和 panic!() 等。使用 {} 格式说明符打印错误时，通常只会显示简短的错误信息。或者，可以使用 {:?} 格式说明符来以 Debug 格式查看错误详情。虽然这种方式不太直观，但有时它能提供额外的技术信息。

// result of `eprintln!("error: {err}");`
error: No such file or directory (os error 2)

// result of `eprintln!("error: {err:?}");`
error: Os { code: 2, kind: NotFound, message: "No such file or directory" }
err.to_string()


返回一条错误消息，格式为 String 。这相当于 format!("{err}") 。

err.source()


如果发生了任何错误，那么 Option 就会返回导致 err 失败的根本错误。例如，网络问题可能导致银行交易失败，进而使你的船被收回。如果 err.to_string() 等于 "boat was repossessed" ，那么 err.source() 可能会返回关于交易失败的错误信息。该错误的 .to_string() 可能是 "failed to transfer $300 to United Yacht Supply" ，而其 .source() 则可能是包含有关导致这一问题的具体网络故障信息的 io::Error 。这个第三类错误就是根本原因，因此它的 .source() 方法会返回 None 。由于标准库只包含相当基础的功能，所以标准库返回的错误通常都是 None 。

即使打印出错误值，也无法同时打印出其来源信息。如果你希望确保能打印出所有可用的信息，请使用此功能：

use std::error::Error;
use std::io::{self, Write};

/// Dumps an error message to `stderr`.
///
/// If another error happens while building the error message or
/// writing to `stderr`, it is ignored.
fn print_error(mut err: &dyn Error) {
    let _ = writeln!(io::stderr(), "error: {err}");
    while let Some(source) = err.source() {
        let _ = writeln!(io::stderr(), "caused by: {source}");
        err = source;
    }
}


writeln! 宏的工作原理与 println! 相同，不过它会将数据写入用户指定的流中。在这里，我们将错误信息写入标准错误流 std::io::stderr 。我们可以使用 eprintln! 宏来实现同样的功能，但是当发生错误时， eprintln! 会引发恐慌。在 print_error 中，我们希望忽略在写入消息时出现的错误；关于为什么需要忽略这些错误，我们将在章节的后面部分进行说明。

大多数 Rust 错误类型并不包含堆栈跟踪信息，因为捕获堆栈跟踪的成本并不总是可以忽略的。不过，流行的 anyhow crate 提供了一个现成的错误类型，如果设置了 RUST_BACKTRACE ，那么这个错误类型就会包含堆栈跟踪信息。

误差传播


在我们尝试可能失败的事情的大多数情况下，我们并不希望立即捕获并处理错误。每处可能出现问题的地方都使用一条 10 行的 match 语句来处理错误，这样的做法会使得代码变得过于复杂。


相反，如果出现错误，我们希望让调用方自行处理这个问题。我们希望让错误能够沿着调用栈向上传递。


Rust 中有一个 ? 运算符可以用来执行这种操作。你可以将 ? 添加到任何表达式中，这样就能得到 Result 的结果，比如函数调用的结果：

let weather = get_weather(hometown)?;


? 的行为取决于该函数返回的是成功结果还是错误结果。

  • 如果成功的话，它会解包 Result ，以获取其中的成功值。这里的 weather 的类型并不是 Result<WeatherReport, io::Error> ，而仅仅是 WeatherReport 而已。

  • 在出现错误时，它会立即从包含它的函数中返回，并将错误结果传递给后续的调用链。为了确保这一点能够正常工作， ? 只能用于那些具有 Result 返回类型的函数中的 Result 。


? 运算符并没有什么神奇之处。你可以使用 match 表达式来表达同样的事情，不过这样表达起来会更冗长一些。

let weather = match get_weather(hometown) {
    Ok(success_value) => success_value,
    Err(err) => return Err(err),
};

这个操作符与 ? 操作符唯一的区别在于一些关于类型和处理器的细节问题。我们将在下一节中讨论这些细节。

人们很容易忘记，在程序中，出错的可能性其实是非常普遍的，尤其是在那些与操作系统交互的代码中。 ? 运算符有时会出现在函数的几乎每一行代码中。

use std::fs;
use std::io;
use std::path::Path;

fn move_all(src: &Path, dst: &Path) -> Result<(), io::Error> {
    for entry_result in src.read_dir()? {  // opening dir could fail
        let entry = entry_result?;         // reading dir could fail
        let dst_file = dst.join(entry.file_name());
        fs::rename(entry.path(), dst_file)?;  // renaming could fail
    }
    Ok(())  // phew!
}

? 与 Option 类型的用法也类似。在返回 Option 的函数中，你可以使用 ? 来展开一个值，并在遇到 None 的情况时提前返回结果：

// If reports.get() returns an Option<&WeatherReport>...
let weather = reports.get(hometown)?;
// ...then `weather` is a &WeatherReport.

结果分析方法

人们只能不断地传播错误而已。最终，总有一些地方会妥善处理这些错误。

我们已经展示了如何通过使用 match 表达式来实现这一功能，同时处理了 Err(err) => 分支中的错误。不过，在每种情况下都这样做可能会显得有些冗长，因此 Result 类型提供了一些针对常见错误处理模式的方法。这些方法的实现中都包含了 match 表达式。至于 Result 方法的完整列表，可以参考在线文档。这里列出的方法是我们最常用的那些。

result.is_ok(), result.is_err()


返回一个 bool ，用于表明 result 是成功的结果还是错误的结果。

result.ok()


如果成功，则返回成功值，以 Option<T> 的形式表示。如果 result 是成功结果，则返回 Some(success_value) ；否则，返回 None ，并忽略错误值。

result.err()


如果有的话，会返回错误值，以 Option<E> 的形式呈现。

result.unwrap_or(fallback)


如果 result 是成功的结果，则返回成功的值；否则，返回 fallback ，并丢弃错误值。

// A fairly safe prediction for Southern California.
const THE_USUAL: WeatherReport = WeatherReport::Sunny(72);

// Get a real weather report, if possible.
// If not, fall back on the usual.
let report = get_weather(los_angeles).unwrap_or(THE_USUAL);
display_weather(los_angeles, &report);


这是一个不错的替代方案，因为返回的类型是 T ，而不是 Option<T> 。当然，只有当存在合适的备用值时，这种方案才有效。

result.unwrap_or_else(fallback_fn)


情况是一样的，不过这里不是直接传递一个备用值，而是传递一个函数或闭包。这样做是为了避免在没有需要使用备用值的情况下，去计算它所带来的不必要的开销。只有当出现错误时，才会调用 fallback_fn 。

let report = get_weather(hometown)
    .unwrap_or_else(|_err| vague_prediction(hometown));


（第 14 章详细介绍了关于关闭操作的内容。）

result.unwrap()


如果 result 的结果是成功的，该方法也会返回成功的值。不过，如果 result 的结果是错误，该方法会抛出异常。这个方法有一定的用途，我们稍后会详细讨论。

result.expect(message)


这与 .unwrap() 相同，但你可以提供一个在出现异常情况时会被打印出来的消息。

result.map(convert_fn)

这种方法只会在 Result 的值是一个 Ok 值时才对其进行修改。这个参数通常是一个闭包，只有当结果为 Ok 时才会被调用。如果结果是 Err ，那么 map 会原封不动地返回它。

reqwest::blocking::get(url)             // do an HTTP request...
    .map(|response| response.status())  // ...but we only care about the status code


在这个例子中， reqwest::blocking::get(url) 返回了 Result<Response, reqwest::Error> 的值。我们使用 .map() 来将 Result<Response, reqwest::Error> 转换为 Result<StatusCode, reqwest::Error> 的形式。

result.map_err(convert_fn)


map_err 方法实际上是 map 的镜像版本。它只处理 Err 类型的值，因此结果的错误类型也会相应改变。这一点在处理多种类型的错误时非常有用，我们会在后面的章节中看到这一点。


最后，关于如何处理参考文献的方法如下： Result

result.as_ref()


将 Result<T, E> 转换为 Result<&T, &E> 。

result.as_mut()


这是相同的，只不过借用了一个可变的引用。返回类型为 Result<&mut T, &mut E> 。


这两种方法之所以有用，原因之一在于：除了 .is_ok() 和 .is_err() 之外，这里列出的所有方法都会使用它们所操作的 result 参数。也就是说，它们都是以值传递的方式接收 self 参数。有时候，能够在不破坏 result 内部数据的情况下访问其中的内容是非常方便的，而 .as_ref() 和 .as_mut() 正是为我们解决了这个问题。例如，假设你想调用 result.ok() ，但同时又需要保留 result 不变。这时就可以使用 result.as_ref().ok() ，它只是借用了 result 的参数，并返回了一个 Option<&T> 而不是 Option<T> 。

结果类型别名


有时候，你会看到 Rust 文档中有些内容并没有提及 Result 的错误类型。

fn remove_file(path: &Path) -> Result<()>


类型别名是一种类型名称的简写形式。模块通常会定义一种类型别名，以避免重复那些几乎被模块中每个函数都使用的错误类型。例如，标准库中的 std::io 模块包含这样一行代码：

pub type Result<T> = result::Result<T, Error>;

这定义了一个公共类型 std::io::Result<T> 。它是 Result<T, E> 的别名，但会将 std::io::Error 硬编码为错误类型。如果你编写 use std::io; ，那么 Rust 会将 io::Result<String> 理解为 Result<String, io::Error> 的简写形式。

当在线文档中出现类似 Result<()> 这样的标识符时，可以点击该标识符 Result 来查看所使用的类型别名，从而了解具体的错误类型。实际上，通常从上下文就能明确判断出错误类型。

处理多种错误类型


通常，会有不止一件事出错。假设我们只是从文本文件中读取数字：

use std::io::{self, BufRead};

/// Reads integers from a text file.
/// The file should have one number on each line.
fn read_numbers(file: &mut dyn BufRead) -> io::Result<Vec<i64>> {
    let mut numbers = vec![];
    for line_result in file.lines() {
        let line = line_result?;         // reading lines can fail
        numbers.push(line.parse()?);     // parsing integers can fail
    }
    Ok(numbers)
}

Rust 语言让我们遇到了编译错误：

error: `?` couldn't convert the error to `std::io::Error`
   |
 8 | fn read_numbers(file: &mut dyn BufRead) -> io::Result<Vec<i64>> {
   |                                            --------------------
   |                       expected `std::io::Error` because of this
...
12 |     numbers.push(line.parse()?);     // parsing integers can fail
   |                       -------^ the trait `From<ParseIntError>` is
   |                       |        not implemented for `std::io::Error`
   |                       |
   |                       this can't be annotated with `?` because
   |                       it has type `Result<_, ParseIntError>`
   |
   = note: the question mark operation (`?`) implicitly performs a
     conversion on the error value using the `From` trait


当读到第 11 章关于特性的部分时，这些错误信息的术语就会更加明了。目前，只需注意 Rust 正在提示 ? 运算符无法将 std::num::ParseIntError 值转换为 std::io::Error 类型。

这里的问题在于，从文件中读取一行数据并解析出一个整数会导致两种不同的错误类型。 line_result 的类型是 Result<String, std::io::Error> 。 line.parse() 的类型则是 Result<i64, std::num::Parse​IntError> 。我们的 read_numbers() 函数的返回类型只能处理 io::Error 类型的数据。Rust 试图通过将 ParseIntError 转换为 io::Error 来解决这个问题，但实际上并没有这样的转换方法，因此就会引发类型错误。

我们需要一种统一的错误类型。实现这一目标的办法是将所有其他错误手动转换为 std::io::Error 格式。

        let num = line
            .parse()
            .map_err(|err| io::Error::other(err))?;
        numbers.push(num);

只有当 line.parse() 返回错误时， .map_err() 方法才会调用该闭包。通过这种方式，我们可以将错误从 ParseIntError 类型转换为 io::Error 类型。因此，该方法最终会返回一个 Result<i64, std::io::Error> 类型的结果。之后，我们可以像使用常规的 ? 运算符一样来处理这个错误了。

在这种情况下，由于 io::Error::other 已经是一个接受错误作为参数的函数，因此我们不需要编写闭包。我们可以将其简化如下：

        let num = line.parse().map_err(io::Error::other)?;
        numbers.push(num);

不过，使用 .map_err() 进行调用仍然显得有些笨拙，而且文件中出现的数据错误也不属于我们通常所认为的 I/O 错误。如果我们过于频繁地使用这种技巧，代码就会变得混乱，而使用 io::Error 的方式也会变得相当具有误导性。Rust 生态系统已经提出了两种解决这一问题的方法。这两种方法都以开源的库形式实现。

一种通用错误类型：无论如何都是


anyhow 这个包定义了一个单一的错误类型 anyhow::Error ，该类型支持与所有错误类型的相互转换。我们必须将在 Cargo.toml 文件中添加这个包作为依赖项。

[dependencies]
anyhow = "1.0.102"

通过使用 anyhow ，我们无需调用 .map_err() 。我们只需将返回类型改为使用 anyhow::Result 类型别名即可，如下所示。代码中已有的 ? 运算符会自动将任何类型的错误转换为 anyhow::Error 类型，以满足需求。

fn read_numbers(file: &mut dyn BufRead) -> anyhow::Result<Vec<i64>> {
    ...
        let line = line_result?;      // converts io::Error to anyhow::Error
        numbers.push(line.parse()?);  // same for ParseIntError
    ...
}

使用 anyhow 并不是实现此功能的唯一方式。Rust 标准库中内置了类似的类型。所有实现了 std::error::Error 特性的类型都可以自动转换为 Box<dyn std::error::Error + Send + Sync + 'static> 类型。这种类型虽然名称有些复杂，但 dyn std::error::Error 代表了“任何错误”，而 + Send + Sync + 'static 则将其缩小到只能在线程之间传递的可靠类型。因此，用一行代码表示 anyhow 的近似形式可以如下：

type AnyError = Box<dyn std::error::Error + Send + Sync + 'static>;

不过， anyhow 有一些功能是这条简短的声明所没有提供的：

  • 打印 anyhow::Error 会自动打印出 source 的链接。

  • anyhow::bail!() 和 anyhow::ensure!() 宏提供了一种简便的方法来处理错误，无需声明新的类型。与 panic!() 和 assert!() 类似，它们也接受字符串格式化的参数，但并不会引发异常，而是直接返回一个错误结果。
  • 当创建一个 anyhow::Error 时，如果设置了 RUST_BACKTRACE 环境变量，那么它会自动捕获回溯信息。（不过需要注意的是，这种回溯只是捕获了错误转化为 anyhow 错误时的堆栈信息，而不是错误最初发生的位置。对于某些程序来说，捕获这些回溯信息会消耗大量资源，因此并不十分有用。可以通过设置 RUST_LIB_BACKTRACE=0 来禁用此功能。）


anyhow 这个 crate 的文档对这些功能有更详细的说明。


anyhow 方法的缺点在于，其返回类型无法明确表明调用者可能会遇到哪种类型的错误。因此，调用者必须做好应对各种可能出现的情况的准备。


如果你正在编写用于处理某种特定类型的错误的代码，并且希望处理这种错误，同时让其他错误继续传播出去，可以使用通用方法 err.downcast_ref::<T>() 。如果发生的正是你想要的那种错误类型，该方法会引用该错误的实例。

loop {
    match compile_project() {
        Ok(()) => return Ok(()),
        Err(err) => {
            if let Some(mse) = err.downcast_ref::<MissingSemicolonError>() {
                insert_semicolon_in_source_code(mse.file(), mse.line())?;
                continue;  // try again!
            }
            return Err(err);
        }
    }
}

anyhow 非常适合用于与 main 类似的代码，尤其是在可执行文件的顶层。但在库的公共 API 中使用它有一些缺点。首先，这实际上增加了用户的依赖负担，迫使他们在自己的代码库中处理 anyhow::Error 。其次，这会让用户难以识别实际发生的错误类型。当由 anyhow::bail! 或你使用的第三方 crate 引发的错误被返回时，用户无法将错误类型向下转型为具体的类型——没有一种公共类型能够明确指出错误的具体类型。用户只能像野蛮人一样对错误信息进行正则表达式处理。没人希望看到这种情况发生。最后，如果 anyhow 这个 crate 对其 API 进行了任何破坏性变更，用户就需要协调不同 crate 中对不兼容版本 anyhow 的使用，这简直是一场噩梦。不过，至少到目前为止，这种情况从未发生过。自 2019 年以来， anyhow 一直停留在 1.0 版本上，只发布向后兼容的更新版本。不过，通常建议在应用程序中使用 anyhow 版本，而不建议在库中使用。

定义自定义错误类型


与其在所有情况下都使用 anyhow::Error ，不如为公共 API 定义专门的错误类型。例如， reqwest HTTP 客户端库中有 reqwest::Error ，而用于访问 SQL 数据库的 sqlx 库中则有 sqlx::Error 、 regex 等错误类型。

我们还没有介绍用户自定义类型呢；这部分内容将在接下来的几章中讨论。不过，错误类型非常实用，所以这里我们先简单介绍一下。

对于我们的 read_numbers 函数，我们需要一种错误类型，该类型能够容纳 io::Error 或 ParseIntError 数据。在 Rust 语言中，这可以通过定义一个 enum 类型的变量来实现。

use std::io;
use std::num::ParseIntError;

#[derive(Debug)]
pub enum NumberFileError {
    Io(io::Error),
    Parse(ParseIntError),
}

为了使 ? 运算符能够发挥作用，我们必须定义如何将这两种类型分别转换为 NumberFileError 类型。

impl From<io::Error> for NumberFileError {
    fn from(err: io::Error) -> NumberFileError {
        NumberFileError::Io(err)
    }
}

impl From<ParseIntError> for NumberFileError {
    fn from(err: ParseIntError) -> NumberFileError {
        NumberFileError::Parse(err)
    }
}

这就足够了。再次将 read_numbers 的返回类型改为 Result<Vec<i64>, NumberFileError> ，就能使示例代码成功编译。不过，如果你希望错误类型也能被打印出来，就像标准错误类型那样，那么你就需要做一些额外的操作了。

use std::fmt::{self, Display, Formatter};

// Errors should be printable.
impl Display for NumberFileError {
    fn fmt(&self, f: &mut Formatter) -> fmt::Result {
        let msg = match self {
            NumberFileError::Io(_) => "error reading config file",
            NumberFileError::Parse(_) => "invalid data in config file",
        };
        write!(f, "{msg}")
    }
}

// Errors should implement the std::error::Error trait.
impl std::error::Error for NumberFileError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            NumberFileError::Io(err) => Some(err),
            NumberFileError::Parse(err) => Some(err),
        }
    }
}

不必理解这一行的每一个细节。所有那些陌生的语法在接下来的几章中都会得到解释。我们主要想说明的是，错误类型是可以手动编写的——这并不是什么神奇的事情，不过这需要编写大量的样板代码。 thiserror 这个包可以帮您生成大部分这样的代码。

[dependencies]
thiserror = "2.0.18"

通过使用 thiserror ，同样的错误类型可以在几行代码中实现：

#[derive(Debug, thiserror::Error)]
pub enum NumberFileError {
    #[error("error reading config file")]
    Io(#[from] io::Error),

    #[error("invalid data in config file")]
    Parse(#[from] ParseIntError),
}

有几个属性决定了 thiserror 如何实现这种新的错误类型：


  • #[derive(Debug, thiserror::Error)] 告诉 Rust，除了为这种类型提供的常规 Debug 格式外，我们还希望使用 thiserror::Error 派生宏来生成一些代码。Rust 编译器会为 Debug 生成代码，而 thiserror 库则负责为 Error 生成代码。（如果你愿意，可以使用 cargo expand 来查看生成的代码，具体方法请参考“调试宏”部分的描述。不过请注意，生成的代码通常看起来会有些奇怪，这一点的细节我们将在那一章中进行探讨。）

  • #[error(...)] 告诉 thiserror 我们希望每个变体在 Display 格式中如何呈现。这个字符串参数是一种格式字符串，可以访问错误对象中的各个字段。更多详细信息，请参考 thiserror 文档。

  • #[from] 告诉 thiserror 需要执行哪些类型转换操作，以及如何实现 source 方法。

你可以使用 thiserror 来定义某个包的公共错误类型，而无需让包的使用者了解 thiserror 的相关信息，或者需要将 thiserror 添加到他们自己的依赖项中。 thiserror 通过生成代码来完成所有的工作，而且它生成的代码都是你自己能够编写的。

处理那些“不可能发生”的错误


有时候，我们一眼就能看出某个错误是不可能发生的。例如，假设我们正在编写用于解析配置文件的代码，突然发现文件中的下一行是一个数字字符串。

if next_char.is_ascii_digit() {
    let start = current_index;
    current_index = skip_digits(line, current_index);
    let digits = &line[start..current_index];
    ...

我们希望将这串数字转换为实际的数值。有一种标准的方法可以做到这一点：

let num = digits.parse::<u64>();

现在的问题是： str.parse::<u64>() 方法返回的并不是 u64 类型的数据，而是 Result 类型的数据。这可能会导致错误，因为有些字符串并非数值类型。

"bleen".parse::<u64>()  // ParseIntError: invalid digit

不过，我们得知在这种情况之下， digits 完全由数字组成。那么我们应该怎么做呢？

如果我们正在编写的代码已经返回了一个 anyhow::Result ，那么我们可以加上一个 ? ，然后就无需再处理这个问题了。不过，如果发生了无法预料的错误，我们就不得不编写错误处理代码。在这种情况下，最好的选择是使用 .unwrap() 。这个 Result 方法会在结果为 Err 时触发 panic，但如果结果是 Ok ，它则只会返回成功的返回值。

let num = digits.parse::<u64>().unwrap();


这跟 ? 的情况类似，只不过如果我们的判断有误，确实会出现这种错误的话，那么我们就会感到恐慌了。

实际上，我们对这个具体情况的判断是错误的。如果输入的字符串长度足够长，那么这个数字就会太大，无法容纳在 u64 中。

"99999999999999999999".parse::<u64>()    // overflow error


不过，有时候 Result 的值确实无法作为错误来处理。例如，在第 18 章中，你会看到 Write 特性定义了一组用于文本和二进制输出的通用方法（如 .write() 等）。所有这些方法都返回 io::Result 类型的数据，但如果你正在写入 Vec<u8> 类型的数据，那么使用 .unwrap() 或 .expect(message) 也是可以接受的，这样就不需要使用 Result 了。

当错误所提示的情况极其严重或异常时，这些方法也非常有用——因为在这种情况下，恐慌正是我们处理问题的正确方式。

fn print_file_age(filename: &Path, last_modified: SystemTime) {
    let age = last_modified.elapsed().expect("system clock drift");
    ...
}


在这种情况下，只有当系统时间早于文件创建的时间时， .elapsed() 方法才可能出现错误。这种情况可能发生在文件刚刚被创建时，而程序运行时系统时钟被调整到了更早的时间。根据代码的用途，在这种情况下选择抛出异常是一个合理的决策，而不是继续处理错误或将错误传递给调用者。

忽略错误


有时候，我们干脆想完全忽略某个错误。例如，在我们的 print_error() 函数中，我们不得不处理这样一种不太可能出现的情况：打印错误反而引发了另一个错误。这种情况可能发生在 stderr 被连接到另一个进程时，而那个进程突然终止了。虽然我们试图报告的原始错误非常重要，但我们现在只想忽略 stderr 中的问题。不过，Rust 编译器还是提醒了我们关于未使用的 Result 值的警告。

writeln!(io::stderr(), "error: {err}");  // warning: unused result


这个惯用表达用于消除此警告： let _ = ... 

let _ = writeln!(io::stderr(), "error: {err}");  // ok, ignore result

处理 main() 函数中的错误


在大多数有 Result 出现的场景中，让错误信息直接显示给调用者是正确的做法。这就是为什么在 Rust 语言中 ? 只是一个单独的字符。正如我们所看到的，在某些程序中， ? 甚至会被连续使用在许多行代码中。

但是，如果你持续引入错误，最终这些错误会影响到 main() 。这时就必须采取措施来处理它们了。通常， main() 不能使用 ? ，因为它的返回类型不是 Result 。

fn main() {
    calculate_tides()?;  // error: can't pass the buck any further
}


处理 main() 中出现的错误最简单的方法就是使用 .expect() ：

fn main() {
    calculate_tides().expect("error");  // the buck stops here
}


如果 calculate_tides() 返回了错误结果，那么 .expect() 方法就会引发恐慌。在 main 线程中发生这种情况时，会输出一条错误信息，然后以非零退出代码结束程序。这大致就是预期的行为。我们一直都在使用这种机制来处理小型程序中的问题。这只是一个开始而已。

不过，错误信息看起来有点令人不安哦：

$ tidecalc --planet mercury
thread 'main' panicked at src/main.rs:2:23:
error: "moon not found"
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

错误信息在噪音中消失了。此外， RUST_BACKTRACE=1 在这种特殊情况下确实是个糟糕的建议。

不过，你也可以将 main() 的类型签名改为返回 Result 类型，这样就可以使用 ? 了：

fn main() -> Result<(), TideCalcError> {
    let tides = calculate_tides()?;
    print_tides(tides);
    Ok(())
}


main 函数可以返回任何实现了 std::process::Termination 特性的类型。这个特性包含一个 report() 方法，Rust 会在 main 函数返回后立即调用这个方法。对于 () 类型， report 方法不会执行任何操作，而是返回默认的退出码 0。而对于错误情况 Result ，它会打印出 Debug 格式的错误信息，并返回一个非零的退出码，表示发生了失败。

这会打印出稍微更美观的错误信息，不过仍然不太适合人类阅读：

$ tidecalc --planet mercury
Error: TideCalcError { error_type: NoMoon, message: "moon not found" }

如果你关心错误呈现的细节问题，那么自己报告错误是最有效的办法：没有其他方式可以替代这一点。

fn main() {
    if let Err(err) = calculate_tides() {
        print_error(&err);
        std::process::exit(1);
    }
}


此代码使用 if let 表达式，只有当调用 calculate_tides() 时返回错误结果时，才会打印错误信息。关于 if let 表达式的详细信息，请参见第 10 章。 print_error 函数包含在“打印错误”部分中。

现在，输出结果已经整齐有序了：

$ tidecalc --planet mercury
error: moon not found

为什么需要结果？


现在我们已经足够了解，知道 Rust 选择使用 Result 代替异常是为了实现什么。以下是该设计的关键点：

  • Rust 要求程序员在每一个可能出现错误的地方都要做出相应的决策，并将这些决策记录到代码中。这一点非常不错，因为否则的话，很容易因为疏忽而导致错误处理出错。

  • 最常见的做法是允许错误继续传播，这种处理方式只用了一个字符来表示： ? 。因此，错误传播的过程不会像在 C 语言和 Go 语言中那样让代码变得混乱。不过，这种机制仍然是可见的：你可以直接查看一段代码，就能一目了然地知道错误传播的位置。

  • 由于错误发生的可能性是每个函数返回类型的一部分，因此很明显哪些函数可能会失败，哪些则不会。如果你修改了一个可能出错的函数，那么你实际上改变了该函数的返回类型，因此编译器会提示你更新那些使用该函数的其他用户。

  • Rust 检查了 Result 的值是否被使用，因此你不能让错误意外地通过——这在 C 语言中是一个常见的错误。

  • 由于 Result 是一种数据类型，因此可以很容易地将成功和失败的结果存储在同一集合中。这使得处理部分成功的情形变得简单。例如，如果你正在编写一个从文本文件中读取数百万条记录的程序，而你需要一种方法来处理这样一种情况：虽然大多数操作能够成功执行，但总有一些操作会失败。你可以使用一个由 Result 构成的向量来在内存中表示这种情形。


其代价是，在使用 Rust 编程时，你不得不更加频繁地考虑和设计错误处理方案。与其他语言相比，Rust 在处理错误方面的做法更为严格。不过，对于系统编程来说，这种严格的处理方式还是值得的。
