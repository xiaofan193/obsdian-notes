不幸的是，并不是世界上所有的程序都是用 Rust 编写的。有许多重要的库和接口是用其他语言实现的，我们希望能够在我们的 Rust 程序中使用这些库和接口。Rust 的外部函数接口允许 Rust 代码调用用 C 语言编写的函数，在某些情况下，甚至还能调用用 C++编写的函数。由于大多数操作系统都提供 C 语言接口，因此 Rust 的外部函数接口使得我们能够直接访问各种底层功能。


在这一章中，我们将编写一个程序，该程序能够与 libgit2 库协同工作。 libgit2 是一个用于处理 Git 版本控制系统的 C 语言库。首先，我们将展示如何直接使用 Rust 语言中的 C 函数，并利用上一章中介绍的不安全特性。接着，我们将展示如何基于开源的 git2-rs 库来构建一个安全的接口，以访问 libgit2 库的功能。

我们假设您已经熟悉 C 语言，也了解 C 程序的编译和链接过程。使用 C++进行编程也是类似的。此外，我们还假设您对 Git 版本控制系统有一定的了解。

确实存在一些用于与多种语言进行通信的 Rust 接口库，包括 Python、JavaScript、Lua 和 Java 等语言。这里我们无法详细介绍这些接口，但归根结底，所有这些接口都是通过 C 语言的外挂函数接口来实现的。因此，无论你需要处理哪种语言，本章的内容都应该能为你提供一定的帮助。

寻找共同的数据表示方式


Rust 和 C 的共同基础是机器语言。因此，为了了解 Rust 的值对于 C 代码来说是什么样子，或者反过来，你需要考虑它们的机器级表示方式。在整本书中，我们都会展示值实际上在内存中是如何被表示的。所以你可能会注意到，C 和 Rust 的数据模型有很多共同点：例如，Rust 中的 usize 和 C 中的 size_t 是相同的，而且结构体在两种语言中本质上也是一样的概念。为了建立 Rust 和 C 类型之间的对应关系，我们将从基本类型开始，然后逐步深入到更复杂的类型。


由于 C 语言主要被用作系统编程语言，因此它在类型表示方面有着惊人的灵活性：一个 int 类型通常占用 32 位空间，但实际上也可以更长，甚至短至 16 位；C 中的 char 类型可以是带符号的，也可以是不带符号的；等等。为了应对这种多样性，Rust 的 std::ffi 模块定义了一组 Rust 类型，这些类型与某些 C 类型具有相同的表示方式（参见表 24-1）。这些类型包括基本整数类型和字符类型。

表 24-1. Rust 语言中的 std::ffi 类型
C 型 对应的 std::ffi type
short c_short
int c_int
long c_long
long long c_longlong
unsigned short c_ushort
unsigned, unsigned int c_uint
unsigned long c_ulong
unsigned long long c_ulonglong
char c_char
signed char c_schar
unsigned char c_uchar
float c_float
double c_double
void *, const void * *mut c_void, *const c_void


关于表 24-1 的一些说明：

  • 除了 c_void 之外，这里所有的 Rust 类型其实都是某种基本 Rust 类型的别名：例如， c_char 实际上就是 i8 或 u8 。

  • Rust 中的 bool 相当于 C 或 C++中的 bool 。

  • Rust 中的 32 位类型 char 并不相当于 wchar_t 类型，因为 wchar_t 类型的宽度和编码方式会因不同的实现而有所差异。C 语言中的 char32_t 类型更接近理想状态，但其编码方式仍可能无法确保与 Unicode 兼容。

  • Rust 中的原始类型 usize 和 isize 与 C 语言中的 size_t 和 ptrdiff_t 具有相同的表示方式。

  • 在 C 和 C++语言中，指针和引用对应的类型分别是 Rust 中的 raw pointer 类型，即 *mut T 和 *const T 。

  • 从技术上讲，C 标准允许实现中使用一些 Rust 语言中没有对应类型的表示方式：例如 36 位整数、有符号值的符号表示法等。实际上，在 Rust 被移植到的每一个平台上，所有常见的 C 语言整数类型在 Rust 中都有对应的实现。


为了定义与 C 结构体兼容的 Rust 结构体类型，可以使用 #[repr(C)] 属性。在结构体定义前使用 #[repr(C)] ，可以要求 Rust 以类似于 C 编译器处理相应 C 结构体类型的方式，在内存中布局结构体的各个字段。例如， libgit2 的 git2/errors.h 头文件定义了以下 C 结构体，用于描述之前报告的错误：

typedef struct {
    char *message;
    int klass;
} git_error;

你可以这样定义一种与 C 语言类似的 Rust 类型：

use std::ffi::{c_char, c_int};

#[repr(C)]
pub struct git_error {
    pub message: *const c_char,
    pub klass: c_int,
}


#[repr(C)] 属性只影响结构体本身的布局，而不影响其各个字段的表示方式。因此，为了与 C 语言的结构体匹配，每个字段也必须使用类似 C 语言的类型表示： char * 对应 char * ， int 对应 int ，以此类推。

在这个特定的案例中， #[repr(C)] 属性似乎并不会改变 git_error 的布局。实际上，用来排列指针和整数的方式并没有太多有趣的方法。不过，与 C 和 C++不同，Rust 会按照成员被声明的顺序在内存中分配空间，而 C 则保证成员的排列顺序与声明顺序一致。Rust 会重新排列字段的顺序以最小化结构的总大小，而零大小的类型则不会占用任何空间。 #[repr(C)] 属性告诉 Rust 遵循 C 语言对于该类型的规则。

你也可以使用 #[repr(C)] 来声明与 C 语言兼容的枚举类型，不过这一点并不被推荐。

#[repr(C)]
#[allow(non_camel_case_types)]
enum git_error_code {  // NOT recommended
    GIT_OK         =  0,
    GIT_ERROR      = -1,
    GIT_ENOTFOUND  = -3,
    GIT_EEXISTS    = -4,
    ...
}


这是非常危险的，因为 Rust 对枚举值的处理非常严格，而 C 语言则不是这样。在 C 语言中，将枚举值设置为 1、2 或 300000 并没有什么问题，无论这些值是否出现在 enum git_error_code 的定义中。而在 Rust 中，如果枚举值不符合 enum 声明中列出的任何值，那么这个值就是无效的。将这样的无效值从 C 语言代码传递到 Rust 中，属于未定义行为。（将无效的枚举值传递给 match 表达式，尤其容易引发问题。在派生类 Debug 的实现中，这种情况会隐式发生。但在 Rust 中，创建这样的无效值恰恰违背了 rustc 的假设；没有任何方法可以确保这种行为是安全的。）

更安全的做法是将 git_error_code 声明为 c_int 的别名，同时把枚举项定义为常量：

type git_error_code = c_int;

const GIT_OK: git_error_code = 0;
const GIT_ERROR: git_error_code = -1;
...

Bindgen 会自动应用这一解决方案。


在 Rust 和 C 之间传递字符串有点困难。在 C 语言中，字符串被表示为指向字符数组的指针，该数组以一个空字符作为结尾。而 Rust 则明确地存储字符串的长度，要么作为 String 结构的字段，要么作为胖引用 &str 的第二个参数。Rust 中的字符串并不以空字符结尾；实际上，它们可以包含其他字符，就像普通字符一样。


这意味着你不能将 Rust 字符串作为 C 字符串来使用：如果你向 C 代码传递一个指向 Rust 字符串的指针，它可能会误将某个嵌入式空字符视为字符串的结尾，或者一直搜索到不存在的空字符而陷入错误。另一方面，如果你能将一个 C 字符串作为 Rust 字符串来使用，那么只要该字符串的内容是格式正确的 UTF-8 编码，就是可以的。


这种情况实际上迫使 Rust 将 C 字符串视为与 String 和 &str 完全不同的类型。在 std::ffi 模块中， CString 和 CStr 类型代表了拥有权且可以借用到的以空字符结尾的字节数组。与 String 和 str 相比， CString 和 CStr 上的方法相当有限，仅适用于构造和操作这些类型。我们将在下一节中展示这些类型的实际用法。

声明外部函数和变量


extern 块用于声明那些位于其他库中的函数或变量，这些函数和变量最终会被链接到最终的 Rust 可执行程序中。例如，在大多数平台上，每个 Rust 程序都会链接到标准的 C 库。因此，我们可以告诉 Rust 关于 C 库的 strlen 函数的信息。

use std::ffi::c_char;

unsafe extern "C" {
    fn strlen(s: *const c_char) -> usize;
}

这样，Rust 就知道了函数的名称和类型，而函数的定义则会被放在后续的链接阶段处理。

Rust 认为，定义在 unsafe extern "C" 块内的函数采用 C 语言的习惯来传递参数和接受返回值。这些函数被定义为 unsafe 函数。对于 strlen 来说，这样的定义是正确的：因为这确实是一个 C 语言函数，而 C 语言的规定要求传入的参数是指向正确终止的字符串的指针。然而，Rust 无法强制执行这一要求。（几乎任何接受原始指针的函数都必须是 unsafe 类型的：安全的 Rust 可以从任意整数创建原始指针，而解引用这样的指针会导致未定义的行为。）

通过使用这个 extern 块，我们可以像调用其他 Rust 函数一样调用 strlen 。不过，它的类型会表明它是一个“游客”函数。

use std::ffi::CString;

let rust_str = "I'll be back";
let null_terminated = CString::new(rust_str).unwrap();
unsafe {
    assert_eq!(strlen(null_terminated.as_ptr()), 12);
}


CString::new 函数会创建一个以空字符结尾的 C 字符串。首先，它会检查其参数中是否包含空字符，因为空字符无法被存储在 C 字符串中。如果发现了空字符，就会返回错误（因此需要使用 unwrap 来处理结果）。否则，会在字符串末尾添加一个空字节，然后返回包含最终字符的 CString 字符串。


CString::new 的代价取决于你传递的是哪种类型的数据。只要传递的数据实现了 Into<Vec<u8>> 接口，就可以使用它。当传递 &str 时，系统会进行分配和复制操作；因为转换为 Vec<u8> 后，会创建一个堆分配的内存副本，供向量使用。而当值传递 String 时，系统只会消耗字符串本身，并占用相应的缓冲区空间。因此，除非在追加空字符时导致缓冲区需要重新调整大小，否则这种转换根本不需要复制文本或分配内存。就像 &[u8] 和 &str 一样， &CStr 也可以作为字面量来使用，就像 c"Hello, world." 一样。

CString 对 CStr 进行了解引用操作，而 CStr 中的 as_ptr 方法返回了一个指向字符串起始位置的 *const c_char 指针。这正是 strlen 所期望的类型。在示例中， strlen 沿着字符串向下查找，找到了 CString::new 放置的那个空字符，然后返回了该字符的长度，以字节数表示。

你也可以在 extern 块中声明全局变量。POSIX 系统有一个名为 environ 的全局变量，用于存储进程的环境变量值。在 C 语言中，它的声明方式如下：

extern char **environ;

在 Rust 语言中，你会这样写：

use std::ffi::{CStr, c_char};

unsafe extern "C" {
    static environ: *mut *mut c_char;
}

要打印环境的第一个元素，可以编写如下代码：

unsafe {
    if !environ.is_null() && !(*environ).is_null() {
        let var = CStr::from_ptr(*environ);
        println!("first environment variable: {}", var.to_string_lossy());
    }
}


在确认 environ 具有第一个元素之后，代码会调用 CStr::from_ptr 来构建一个 CStr ，该 CStr 会借用 environ 的内容。 to_string_lossy 方法返回一个 Cow<str> ：如果 C 字符串包含格式正确的 UTF-8 编码，那么 Cow 会将其内容作为 &str 来借用，而不会包含终止的空字节。否则， to_string_lossy 会在堆中复制文本，用官方的 Unicode 替换字符 � 来替换格式不正确的 UTF-8 序列，然后从中构建一个属于自己的 Cow 。无论哪种情况，最终结果都实现了 Display 的接口，因此可以使用 {} 格式参数来打印它。

使用库中的函数


要使用某个库提供的函数，可以在包含该库名称的 extern 块前添加 #[link] 标签。例如，以下是一个调用 libgit2 的初始化和关闭方法的程序，它不会执行其他任何操作：

use std::ffi::c_int;

#[link(name = "git2")]
unsafe extern "C" {
    pub fn git_libgit2_init() -> c_int;
    pub fn git_libgit2_shutdown() -> c_int;
}

fn main() {
    unsafe {
        git_libgit2_init();
        git_libgit2_shutdown();
    }
}


unsafe extern "C" 块像之前一样声明了 extern 函数。 #[link(name = "git2")] 属性在项目中留下了一条注释，指出当 Rust 生成最终的可执行文件或共享库时，应该链接到 git2 库。Rust 使用系统链接器来构建可执行文件；在 Unix 系统上，这一操作会在链接命令参数中传递 -lgit2 参数；而在 Windows 系统上，则会传递 git2.LIB 参数。


在这个示例中，如果你想在自己的机器上尝试运行这个程序，那么你就需要自己构建 libgit2 。我们使用的是 libgit2 版本 1.8.1。要编译 libgit2 ，你需要安装 CMake 构建工具和 Python 语言支持；我们使用的 CMake 版本为 3.28.3，Python 版本为 3.12.3。


构建 libgit2 的完整步骤可以在其官方网站上找到。不过，这些步骤相当简单，因此我们在这里只介绍核心内容。在 Linux 系统中，假设你已经将库的源代码解压到了/home/jimb/libgit2-1.8.1目录下。

$ cd /home/jimb/libgit2-1.8.1
$ mkdir build
$ cd build
$ cmake ..
$ cmake --build .


在 Linux 系统中，这会生成一个共享库/home/jimb/libgit2-1.8.1/build/libgit2.so​.⁠1.8.1，同时会生成一系列指向该库的符号链接，其中包含一个名为 libgit2.so 的符号链接。在 MacOS 系统中，结果类似，但库文件的名称变为 libgit2.dylib。


在 Windows 系统中，操作也很简单。假设你已经将源代码解压到 C:\Users\JimB\libgit2-1.8.1 这个目录下。接下来，在 Visual Studio 的命令行界面中执行以下操作：

> cd C:\Users\JimB\libgit2-1.8.1
> mkdir build
> cd build
> cmake -A x64 ..
> cmake --build .


这些命令与在 Linux 上使用的命令相同。不过，当你第一次运行 CMake 时，必须指定 64 位版本，以匹配你的 Rust 编译器。如果你已经安装了 32 位的 Rust 工具链，那么可以在第一个 cmake 命令中省略 -A x64 标志。这样会生成两个文件：一个导入库文件 git2.LIB，以及一个动态链接库文件 git2.DLL。这两个文件都位于 C:\Users\JimB\libgit2-1.8.1\build\Debug 目录下。（其余的指令适用于 Unix 系统，不过 Windows 系统的设置有所不同。）

在另一个目录中创建 Rust 程序：

$ cd /home/jimb
$ cargo new --bin git-toy
    Creating binary (application) `git-toy` package


将之前显示的代码复制到 src/main.rs 文件中。当然，如果你尝试构建这个项目，Rust 系统根本不知道该去哪里找到 libgit2 这个代码所在的位置。

$ cd git-toy
$ cargo run
   Compiling git-toy v0.1.0 (/home/jimb/git-toy)
error: linking with `cc` failed: exit status: 1
  |
  = note: rust-lld: error: unable to find library -lgit2
          collect2: error: ld returned 1 exit status


error: could not compile `git-toy` (bin "git-toy") due to 1 previous error


你可以通过编写构建脚本来指定 Rust 程序在何处查找库文件。该脚本需要告诉 Cargo 在链接命令中添加库文件的搜索路径。Cargo 会解析构建脚本的输出以获取此类信息，因此构建脚本只需将正确的信息输出到标准输出即可。关于构建脚本的更多信息，请参阅“构建脚本”部分。


要创建你的构建脚本，请在与 Cargo.toml 文件相同的目录中创建一个名为 build.rs 的文件，并添加以下内容：

fn main() {
    println!(r"cargo:rustc-link-search=native=/home/jimb/libgit2-1.8.1/build");
}


这对 Linux 系统来说是正确的路径选择；而在 Windows 系统中，你需要将路径改为 C:\Users\JimB\libgit2-1.8.1\build\Debug 而不是 native= 。（为了简化示例，我们省略了一些细节；在实际的应用程序中，应避免在构建脚本中使用绝对路径。我们在本节的末尾引用了相关文档，其中详细说明了如何正确地实现这一操作。）

现在，你几乎可以运行这个程序了。在 macOS 系统上，它可能会立即运行；而在 Linux 系统上，你可能会看到类似以下的提示：

$ cargo run
   Compiling git-toy v0.1.0 (/home/jimb/git-toy)
    Finished `dev` profile [unoptimized + debuginfo] target(s)
     Running `target/debug/git-toy`
target/debug/git-toy: error while loading shared libraries:
libgit2.so.25: cannot open shared object file: No such file or directory

这意味着，虽然 Cargo 成功地将可执行文件与库文件关联起来了，但在运行时它并不知道共享库位于何处。在 Windows 系统中，系统会弹出一个对话框来提示这种错误。而在 Linux 系统中，则需要设置 LD_LIBRARY_PATH 环境变量来指定共享库的路径。

$ export LD_LIBRARY_PATH=/home/jimb/libgit2-1.8.1/build:$LD_LIBRARY_PATH
$ cargo run
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.0 secs
     Running `target/debug/git-toy`

在 macOS 操作系统上，你可能需要将 DYLD_LIBRARY_PATH 替换为其他字符。

在 Windows 系统中，您需要设置 PATH 环境变量。

> set PATH=C:\Users\JimB\libgit2-1.8.1\build\Debug;%PATH%
> cargo run
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.0 secs
     Running `target/debug/git-toy`
>


当然，在部署的应用程序开发中，你通常会希望避免为了找到某个库的代码而不得不设置环境变量。一种替代方案是将 C 库静态链接到你的项目中。这样，库的文件会被复制到项目的.rlib 文件中，与项目中的 Rust 代码的文件和元数据一起存放。最终，所有这些文件都会参与最终的链接过程。


关于 Cargo 如何支持构建脚本以及与系统库的连接的相关详细信息，请参阅 Cargo 的在线文档。文档中介绍了如何避免在构建脚本中使用绝对路径，如何控制编译选项，以及如何使用诸如 pkg-config 之类的工具等。 git2-rs 这个库还提供了一些很好的示例，可以模仿其构建脚本来处理一些复杂的场景。

对 libgit2 的简陋接口


如何正确使用 libgit2 这一工具，可以归结为两个问题：

  • 在 Rust 语言中，要使用 libgit2 函数需要什么条件呢？

  • 我们该如何打造一个安全的 Rust 接口来使用它们呢？


我们将逐一处理这些问题。在这一部分，我们会编写一个程序，这个程序实际上就是一个由非惯用的 Rust 代码构成的巨大代码块。这些代码反映了在不同语言混合使用时所必然产生的类型系统和惯例上的冲突。我们将其称为“原始接口”。虽然这段代码看起来很混乱，但它确实展示了使用 libgit2 进行 Rust 编程时需要遵循的所有步骤。

在下一节中，我们将构建一个安全的接口来与 libgit2 交互，从而利用 Rust 的类型系统，同时遵守 libgit2 对其用户所规定的规则。幸运的是， libgit2 是一个设计得非常出色的 C 语言库，因此 Rust 的安全要求所引发的问题都有相当不错的解决方案。我们可以构建一个符合 Rust 惯用模式的接口，而无需使用 unsafe 中的任何函数。


对于原始接口，该程序将需要比之前更多的函数和类型。因此，将 extern 块移入单独的模块中是合理的做法。我们将在 git-toy/src 目录下创建一个名为 raw.rs 的文件，其内容如下：

#![allow(non_camel_case_types)]

use std::ffi::{c_int, c_char, c_uchar};

#[link(name = "git2")]
unsafe extern "C" {
    pub fn git_libgit2_init() -> c_int;
    pub fn git_libgit2_shutdown() -> c_int;
    pub fn giterr_last() -> *const git_error;

    pub fn git_repository_open(
        out: *mut *mut git_repository,
        path: *const c_char,
    ) -> c_int;
    pub fn git_repository_free(repo: *mut git_repository);

    pub fn git_reference_name_to_id(
        out: *mut git_oid,
        repo: *mut git_repository,
        reference: *const c_char,
    ) -> c_int;

    pub fn git_commit_lookup(
        out: *mut *mut git_commit,
        repo: *mut git_repository,
        id: *const git_oid,
    ) -> c_int;

    pub fn git_commit_author(commit: *const git_commit) -> *const git_signature;
    pub fn git_commit_message(commit: *const git_commit) -> *const c_char;
    pub fn git_commit_free(commit: *mut git_commit);
}

#[repr(C)]
pub struct git_repository {
    _private: [u8; 0],
}

#[repr(C)]
pub struct git_commit {
    _private: [u8; 0],
}

#[repr(C)]
pub struct git_error {
    pub message: *const c_char,
    pub klass: c_int,
}

pub const GIT_OID_RAWSZ: usize = 20;

#[repr(C)]
pub struct git_oid {
    pub id: [c_uchar; GIT_OID_RAWSZ],
}

pub type git_time_t = i64;

#[repr(C)]
pub struct git_time {
    pub time: git_time_t,
    pub offset: c_int,
}

#[repr(C)]
pub struct git_signature {
    pub name: *const c_char,
    pub email: *const c_char,
    pub when: git_time,
}


这里的每一项都是基于 libgit2 自己的头文件中的声明而设计的。例如，libgit2-1.8.1/include/git2/repository.h 文件就包含了这样的声明：

extern int git_repository_open(git_repository **out, const char *path);

此函数试图打开位于 path 的 Git 仓库。如果一切顺利，它会创建一个 git_repository 对象，并将指向该对象的指针存储到 out 所指向的位置中。相应的 Rust 声明如下：

pub fn git_repository_open(
    out: *mut *mut git_repository,
    path: *const c_char,
) -> c_int;


libgit2 公共头文件将 git_repository 类型定义为一种不完整的结构体类型的 typedef：

typedef struct git_repository git_repository;

由于这种类型的详细信息属于库的私有部分，因此公共头文件永远不会定义 struct git_repository 宏。这样一来，库的使用者就无法自行创建这种类型的实例。在 Rust 中，与不完整结构体类型相对应的一种可能是这样的：

#[repr(C)]
pub struct git_repository {
    _private: [u8; 0],
}


这是一种结构体类型，其中包含一个空数组。由于 _private 字段并不指向任何具体的值，因此这种类型的值无法在模块外部进行构造。这很合适，因为 C 类型只允许由 libgit2 字段进行构造，并且只能通过原始指针来操作这种类型。


手动编写较长的 extern 代码块可能会是一件麻烦的事情。如果你正在为复杂的 C 语言库编写 Rust 接口，可以考虑使用 bindgen 这个包。该包提供了一些功能，你可以利用这些功能在构建脚本中自动解析 C 语言头文件，并生成相应的 Rust 代码声明。我们在这里没有空间展示 bindgen 的实际用法，但 bindgen 在 crates.io 上的页面包含了其文档的链接。


接下来，我们将彻底重写 main.rs 文件。首先，我们需要声明 raw 这个模块。

mod raw;

根据 libgit2 的约定，可能出错的函数会返回一个整数代码。成功时，该代码的值为正数或零；失败时，则值为负数。如果发生错误， giterr_last 函数会返回一个指向 git_error 结构的指针，该结构包含了关于出错原因的详细信息。 libgit2 拥有这个结构，因此我们不需要自己释放它，但它可能会被下一个库调用覆盖。一个完善的 Rust 接口应该使用 Result 函数，但目前，我们想直接使用 libgit2 函数，所以我们将自己实现处理错误的函数。

use std::ffi::{CStr, c_int};

fn check(activity: &'static str, status: c_int) -> c_int {
    if status < 0 {
        unsafe {
            let error = &*raw::giterr_last();
            println!(
                "error while {activity}: {} ({})",
                CStr::from_ptr(error.message).to_string_lossy(),
                error.klass,
            );
            std::process::exit(1);
        }
    }

    status
}

我们将使用这个函数来检查 libgit2 次调用的结果，具体方式如下：

check("initializing library", raw::git_libgit2_init());

这里使用了与之前相同的 CStr 方法： from_ptr 用于从 C 字符串构建 CStr ，而 to_string_lossy 则将其转化为 Rust 语言可以打印出的格式。

接下来，我们需要一个函数来打印出每个提交的详细信息。

unsafe fn show_commit(commit: *const raw::git_commit) {
    // SAFETY: Lifetimes of `name` and `email` are tied to `commit`.
    // The commit message is cloned and non-UTF-8 data is removed.
    unsafe {
        let author = raw::git_commit_author(commit);

        let name = CStr::from_ptr((*author).name).to_string_lossy();
        let email = CStr::from_ptr((*author).email).to_string_lossy();
        println!("{name} <{email}>\n");

        let message = raw::git_commit_message(commit);
        println!("{}", CStr::from_ptr(message).to_string_lossy());
    }
}

当获得一个指向 git_commit 的指针后， show_commit 会调用 git_commit_author 和 git_commit_message 函数来获取它需要的信息。这两个函数的使用方式遵循一种约定，具体细节可以在 libgit2 的文档中找到说明。

如果一个函数以对象作为返回值，那么该函数就是一个获取器；此时对象的生命周期会与父对象绑定在一起。

在 Rust 语言中， author 和 message 是从 commit 中借来的变量。因此， show_commit 不需要自己释放这些变量，但在 commit 被释放之后，它必须不再持有这些变量。由于这个 API 使用的是原始指针，Rust 不会检查这些指针的生命周期。如果我们不小心创建了悬空指针，可能直到程序崩溃才会被发现。

前面的代码中，这些字段被假定为存储 UTF-8 文本，但这并不总是正确的做法。Git 也允许使用其他编码方式。要正确解析这些字符串，可能需要使用 encoding crate 这个符号。为了简洁起见，我们在这里就不详细讨论这些问题了。

我们程序的 main 函数如下实现：

use std::ffi::CString;
use std::mem::MaybeUninit;
use std::ptr;

fn main() {
    let path = std::env::args()
        .nth(1)
        .expect("usage: git-toy PATH");
    let path = CString::new(path)
        .expect("path contains null characters");

    unsafe {
        check("initializing library", raw::git_libgit2_init());

        let mut repo = ptr::null_mut();
        check(
            "opening repository",
            raw::git_repository_open(&mut repo, path.as_ptr()),
        );

        let c_name = c"HEAD";
        let oid = {
            let mut oid = MaybeUninit::uninit();
            check(
                "looking up HEAD",
                raw::git_reference_name_to_id(oid.as_mut_ptr(), repo, c_name.as_ptr()),
            );
            oid.assume_init()
        };

        let mut commit = ptr::null_mut();
        check(
            "looking up commit",
            raw::git_commit_lookup(&mut commit, repo, &oid),
        );

        show_commit(commit);

        raw::git_commit_free(commit);

        raw::git_repository_free(repo);

        check("shutting down library", raw::git_libgit2_shutdown());
    }
}

这部分代码主要用于处理路径参数，并初始化相关库，这些功能我们之前已经见过。接下来的新代码是这样的：

let mut repo = ptr::null_mut();
check(
    "opening repository",
    raw::git_repository_open(&mut repo, path.as_ptr()),
);

调用 git_repository_open 试图打开指定路径下的 Git 仓库。如果成功，它会为该仓库分配一个新的 git_repository 对象，并设置 repo 指向该对象。Rust 会隐式地将引用转换为原始指针，因此在这里传递 &mut repo 时，就能得到 *mut *mut git_repository 所期望的结果。

这再次展示了另一种在 libgit2 中使用的约定（来自 libgit2 文档）：

通过第一个参数作为指针指向指针的方式返回的对象，属于调用者所拥有，调用者有责任释放这些对象。

在 Rust 语言中，像 git_repository_open 这样的函数会将新值的所有权传递给调用者。

接下来，让我们看看用于获取仓库当前主干提交对象哈希值的代码：

let oid = {
    let mut oid = MaybeUninit::uninit();
    check(
        "looking up HEAD",
        raw::git_reference_name_to_id(oid.as_mut_ptr(), repo, c_name.as_ptr()),
    );
    oid.assume_init()
};


git_oid 类型用于存储对象标识符——一个 160 位的哈希码。Git 在内部以及其用户接口中都会使用这个标识符来标识不同的提交、文件的各个版本等。对 git_reference_name_to_id 的调用就是用来获取当前 "HEAD" 提交的对象标识符的。


我们可以要求 Rust 为我们提供未初始化的内存。不过，随时读取未初始化的内存是一种不确定的行为。因此，Rust 提供了一种抽象机制，即 MaybeUninit ，来方便我们使用这种内存。 MaybeUninit<T> 会告诉编译器为类型 T 预留一些内存，但在你确认可以安全地操作这些内存之前，不要去访问它们。虽然这些内存由 MaybeUninit 拥有，但编译器会避免一些可能导致不确定行为的优化操作，即使你的代码中没有任何显式的未初始化内存访问操作。


MaybeUninit 提供了一个方法 as_mut_ptr() ，该方法会返回一个指向可能被未初始化的内存的指针 *mut T 。通过将这个指针传递给一个需要初始化内存的外层函数，然后再调用 MaybeUninit 中的 unsafe 方法 assume_init ，就可以避免未定义行为的发生。这样无需额外的开销来初始化内存，同时又能确保值能够被正确初始化。不过 assume_init 这个方法并不安全，因为在不确定内存是否已初始化的情况下直接调用它，会导致未定义行为的发生。


在这种情况下，这是安全的，因为 git_reference_name_to_id 已经初始化了 MaybeUninit 所拥有的内存。我们也可以使用 MaybeUninit 来初始化 repo 和 commit 变量，但由于这些变量只是简单的单字类型，所以我们直接将它们初始化为 null 即可。

let mut commit = ptr::null_mut();
check(
    "looking up commit",
    raw::git_commit_lookup(&mut commit, repo, &oid),
);


main 函数的其余部分应该是不需要解释的。该函数会调用之前定义的 show_commit 函数，释放对提交和仓库对象的占用，然后关闭库。

与 libgit2 的安全接口交互方式


libgit2 的原始接口是一个不安全的典型例子：虽然按照我们的了解，这种接口是可以被正确使用到的，但 Rust 语言无法强制执行这些规则。为这样的库设计安全的 API 意味着需要明确所有这些规则，然后找到方法将任何违规情况转化为类型检查或借用检查的错误。

以下是该程序所使用的功能的规则，由 libgit2 给出：

  • 在调用任何其他库函数之前，必须先调用 git_libgit2_init 。在调用 git_libgit2_shutdown 之后，不得再使用任何库函数。

  • 所有传递给 libgit2 函数的参数都必须被完全初始化，输出参数除外。

  • 当调用失败时，传递给调用函数的输出参数会保持未初始化的状态，因此不得使用这些参数的值。

  • 一个 git_commit 对象指的是它所依赖的 git_repository 对象，因此前者不能超越后者存在时间。（这一点在 libgit2 文档中没有明确说明；我们是根据接口中某些函数的存在来推断出来的，然后通过阅读源代码进行了验证。）

  • 同样地， git_signature 总是从指定的 git_commit 中借用而来的，而且前者绝不能超过后者的有效期。（文档确实提到了这种情况。）

  • 与某个提交相关的信息、作者的姓名以及电子邮件地址都是从提交信息中借用而来的，这些元素在提交信息被释放后不得再次被使用。

  • 一旦某个 libgit2 对象被释放后，就绝对不能再使用它了。

实际上，你可以创建一个基于 Rust 的接口来与 libgit2 进行交互，该接口能够强制执行所有这些规则，这可以通过 Rust 的类型系统来实现，也可以通过内部管理细节来实现。

在开始之前，让我们先对项目进行一下结构调整。我们希望创建一个 git 模块，该模块能够导出安全接口；而之前程序的原始接口则作为该模块的私有子模块。

整个源代码树看起来会是这样的：

├── Cargo.toml
├── build.rs
└── src/

    └── git/
        ├── mod.rs
        └── raw.rs


根据我们在“将模块分离到单独的文件”这一章节中讲解的规则， git 模块的源代码位于 git/mod.rs 目录下，而其 git::raw 子模块的源代码则位于 git/raw.rs 目录下。


我们再次需要完全重写 main.rs 文件。首先应该声明一下 git 这个模块。

mod git;


然后，我们需要创建名为“git”的子目录，并将 raw.rs 文件移入该子目录中。

git 模块需要声明其 raw 子模块。文件 src/git/mod.rs 中必须包含以下内容：

在接下来的部分中，我们将需要使用来自 libc crate 的一些函数，因此必须在 Cargo.toml 文件中添加相关依赖项。完整的文件内容现在如下：

现在我们已经重新组织了模块结构，接下来让我们考虑一下错误处理的问题。即使是 libgit2 的初始化函数也可能返回错误代码，因此在我们开始之前，需要先解决这个问题。在 Rust 中，一个符合惯用的接口应该包含一个 Error 类型，该类型能够捕获错误代码、错误消息以及来自 giterr_last 的详细信息。一个合适的错误类型必须实现常见的 Error 、 Debug 和 Display 特性。此外，该类型还需要一个 Result 类型，该类型使用 Error 类型作为基础。以下是在 src/git/mod.rs 中的相关定义：

use std::error;
use std::fmt;
use std::result;

#[derive(Debug)]
pub struct Error {
    code: i32,
    message: String,
    class: i32,
}

impl fmt::Display for Error {
    fn fmt(&self, f: &mut fmt::Formatter) -> result::Result<(), fmt::Error> {
        // Displaying an `Error` simply displays the message from libgit2.
        self.message.fmt(f)
    }
}

impl error::Error for Error {}

pub type Result<T> = result::Result<T, Error>;

为了验证从原始库调用中获得的结果，该模块需要一个能够将 libgit2 的返回代码转换为 Result 的函数。

use std::ffi::{CStr, c_int};

fn check(code: c_int) -> Result<c_int> {
    if code >= 0 {
        return Ok(code);
    }

    unsafe {
        let error = raw::giterr_last();

        // libgit2 ensures that (*error).message is always non-null and null
        // terminated, so this call is safe.
        let message = CStr::from_ptr((*error).message)
            .to_string_lossy()
            .into_owned();

        Err(Error {
            code,
            message,
            class: (*error).klass,
        })
    }
}


现在，我们可以开始处理 libgit2 的初始化了。安全的接口会提供一个 Repository 类型的对象，用于表示一个开放的 Git 仓库，该类型包含用于解析引用、查询提交信息等功能。在 git/mod.rs 文件中，这样定义 Repository ：

/// A Git repository.
pub struct Repository {
    // This must always be a pointer to a live `git_repository` structure.
    // No other `Repository` may point to it.
    raw: *mut raw::git_repository,
}


Repository 的 raw 字段不是公开的。由于只有该模块中的代码可以访问 raw::git_repository 指针，因此确保该模块的使用方式正确，就能保证该指针始终被正确使用。

如果唯一能够创建 Repository 的方法就是成功打开一个新的 Git 仓库，那么就可以确保每个 Repository 都指向不同的 git_repository 对象。

use std::path::Path;
use std::ptr;

impl Repository {
    pub fn open<P: AsRef<Path>>(path: P) -> Result<Repository> {
        ensure_initialized();

        let path = path_to_cstring(path.as_ref())?;
        let mut repo = ptr::null_mut();
        unsafe {
            check(raw::git_repository_open(&mut repo, path.as_ptr()))?;
        }
        Ok(Repository { raw: repo })
    }
}

由于使用这个安全接口进行任何操作的唯一方式都是从一个 Repository 值开始，而 Repository::open 则是通过调用 ensure_initialized 来启动的，因此我们可以肯定 ensure_initialized 会在任何 libgit2 函数之前被调用。其定义如下：

fn ensure_initialized() {
    static ONCE: std::sync::Once = std::sync::Once::new();
    ONCE.call_once(|| {
        unsafe {
            check(raw::git_libgit2_init())
                .expect("initializing libgit2 failed");
            assert_eq!(libc::atexit(shutdown), 0);
        }
    });
}

extern "C" fn shutdown() {
    unsafe {
        check(raw::git_libgit2_shutdown())
            .expect("shutting down libgit2 failed");
    }
}


std::sync::Once 类型有助于以线程安全的方式执行初始化代码。只有第一个线程调用 ONCE.call_once 时，才会执行指定的闭包。之后，无论是此线程还是其他任何线程的调用都会阻塞，直到第一个线程完成执行后，才会立即返回，而不会再次执行闭包。一旦闭包执行完毕，调用 ONCE.call_once 就非常简洁了，只需要对存储在 ONCE 中的标志进行原子性加载即可。

在上面的代码中，初始化闭包调用了 git_libgit2_init ，并检查了结果。它只是稍微延迟了一下，而是使用 expect 来确保初始化成功，而不是试图将错误传递回调用者。


在“Unwinding”一文中，我们提到当恐慌事件跨越语言边界时，Rust 的运行时会立即终止进程。 atexit 对 shutdown 的调用就属于这种跨语言边界的情况。因此，如果 shutdown 发生恐慌，那么就没有机会在堆栈的更高层级上捕获这个恐慌了。Rust 提供了一种替代的 ABI，称为 "C-unwind" ，它规定了在将恐慌传递到 Rust 代码之前，如何以 C 语言进行异常处理。在这种情况下，无法使用 "C-unwind" ，因为 atexit 之后没有 Rust 代码来捕获这个恐慌。


Repository 的原始指针始终指向一个活跃存在的 git_repository 对象。这意味着，关闭一个仓库的唯一方法就是删除拥有该仓库的 Repository 值。

impl Drop for Repository {
    fn drop(&mut self) {
        unsafe {
            raw::git_repository_free(self.raw);
        }
    }
}


Repository::open 方法使用一个名为 path_to_cstring 的私有函数，该函数有两个定义——一个适用于类 Unix 系统，另一个适用于 Windows 系统。

use std::ffi::CString;

#[cfg(unix)]
fn path_to_cstring(path: &Path) -> Result<CString> {
    // The `as_bytes` method exists only on Unix-like systems.
    use std::os::unix::ffi::OsStrExt;

    Ok(CString::new(path.as_os_str().as_bytes())?)
}

#[cfg(windows)]
fn path_to_cstring(path: &Path) -> Result<CString> {
    // Try to convert to UTF-8. If this fails, libgit2 can't handle the path
    // anyway.
    match path.to_str() {
        Some(s) => Ok(CString::new(s)?),
        None => {
            let message = format!(
                "Couldn't convert path '{}' to UTF-8",
                path.display(),
            );
            Err(message.into())
        }
    }
}


libgit2 接口使得这段代码有些复杂。在所有平台上， libgit2 都接受以空字符结尾的 C 字符串形式的路径。在 Windows 系统中， libgit2 会认为这些 C 字符串中的内容都是格式正确的 UTF-8 编码，并会将它们转换为 Windows 系统实际使用的 16 位路径格式。这种方法通常是可以工作的，但并不理想。Windows 允许使用不符合格式要求的文件名，因此这些文件名无法用 UTF-8 编码表示。如果你有这样的文件，那么就无法将文件名传递给 libgit2 了。

在 Rust 中，文件系统路径的正确表示形式是一个 std::path::Path 。这种表示方式经过精心设计，能够处理在 Windows 或 POSIX 系统上可能出现的任何路径。这意味着，在 Windows 系统上，存在 Path 这样的数值，这些数值无法被传递给 libgit2 ，因为它们不是格式正确的 UTF-8 编码。因此，虽然 path_to_cstring 的行为并不理想，但在当前 libgit2 的接口条件下，这确实是我们能做到的最佳解决方案。

刚才提到的两个 path_to_cstring 定义都依赖于对我们 Error 类型的转换操作。 ? 运算符就是执行这些转换的，而 Windows 版本则直接调用了 .into() 函数。这些转换其实并不复杂：

impl From<String> for Error {
    fn from(message: String) -> Error {
        Error {
            code: -1,
            message,
            class: 0,
        }
    }
}

// NulError is what `CString::new` returns if a string
// has embedded zero bytes.
impl From<std::ffi::NulError> for Error {
    fn from(e: std::ffi::NulError) -> Error {
        Error {
            code: -1,
            message: e.to_string(),
            class: 0,
        }
    }
}

接下来，让我们来探讨如何将 Git 引用转换为对象标识符。由于对象标识符只是一个 20 字节的哈希值，因此将其暴露在安全的 API 中是完全可行的。

/// The identifier of some sort of object stored in the Git object
/// database: a commit, tree, blob, tag, etc. This is a wide hash of the
/// object's contents.
pub struct Oid {
    pub raw: raw::git_oid,
}

我们将在 Repository 中添加一种方法来执行查找操作：

use std::ffi::c_char;
use std::mem::MaybeUninit;

impl Repository {
    pub fn reference_name_to_id(&self, name: &str) -> Result<Oid> {
        let name = CString::new(name)?;
        unsafe {
            let oid = {
                let mut oid = MaybeUninit::uninit();
                check(raw::git_reference_name_to_id(
                    oid.as_mut_ptr(),
                    self.raw,
                    name.as_ptr() as *const c_char,
                ))?;
                oid.assume_init()
            };
            Ok(Oid { raw: oid })
        }
    }
}

虽然当查找失败时 oid 未被初始化，但这个函数通过遵循 Rust 的 Result 机制来确保调用者永远无法看到未初始化的值：要么调用者得到一个已正确初始化的 Oid 值的 Ok ，要么就得到一个空值 Err 。

接下来，该模块需要一种从仓库中检索提交记录的方法。我们将定义一个 Commit 类型，如下所示：

use std::marker::PhantomData;

pub struct Commit<'repo> {
    // This must always be a pointer to a usable `git_commit` structure.
    raw: *mut raw::git_commit,
    _marker: PhantomData<&'repo Repository>,
}


在“Example: RefWithFlag”中，我们使用了 PhantomData 字段来告诉 Rust，即使该类型表面上并不包含任何引用，也将其视为包含了一个具有特定生命周期的引用。 Commit 类型也需要进行类似的处理。在这种情况下， _marker 字段的类型是 PhantomData<&'repo Repository> ，这意味着 Rust 应该将 Commit<'repo> 视为包含一个对 Repository 的引用，而该 Repository 又指向另一个 Repository 。

查询某个提交记录的方法如下：

impl Repository {
    pub fn find_commit(&self, oid: &Oid) -> Result<Commit<'_>> {
        let mut commit = ptr::null_mut();
        unsafe {
            check(raw::git_commit_lookup(&mut commit, self.raw, &oid.raw))?;
        }
        Ok(Commit {
            raw: commit,
            _marker: PhantomData,
        })
    }
}


这如何与 Commit 的生命周期相关联呢？根据“省略生命周期参数”中的规则， find_commit 的签名并未包含相关引用的生命周期信息。如果我们明确写出这些生命周期，完整的签名将会是：

fn find_commit<'repo, 'id>(&'repo self, oid: &'id Oid) -> Result<Commit<'repo>>

这正是我们想要的：Rust 将返回的 Commit 视为是从 self 那里借来的东西，而 Repository 则相当于那个“借款对象”。

当 Commit 被释放时，必须释放其 raw::git_commit ：

impl Drop for Commit<'_> {
    fn drop(&mut self) {
        unsafe {
            raw::git_commit_free(self.raw);
        }
    }
}

从 Commit 处，你可以借用一个 Signature （包括姓名和电子邮件地址），以及提交信息的文本：

impl Commit<'_> {
    pub fn author(&self) -> Signature<'_> {
        unsafe {
            Signature {
                raw: raw::git_commit_author(self.raw),
                _marker: PhantomData,
            }
        }
    }

    pub fn message(&self) -> Option<&str> {
        unsafe {
            let message = raw::git_commit_message(self.raw);
            char_ptr_to_str(self, message)
        }
    }
}

这是 Signature 类型的内容：

pub struct Signature<'text> {
    raw: *const raw::git_signature,
    _marker: PhantomData<&'text str>,
}


git_signature 对象总是从其他地方获取文本；具体来说， git_commit_author 返回的签名文本就是从 git_commit 那里获取的。因此，我们的安全 Signature 类型包含一个 PhantomData<&'text str> ，这样就能让 Rust 认为其中包含一个寿命为 'text 的 &str 。就像之前一样， Commit::author 能够正确地将返回给 Signature 的 'text 寿命与 Commit 的寿命联系起来，而无需我们编写任何代码。 Commit::message 方法同样对持有提交消息的 Option<&str> 执行相同的操作。


Signature 包含了用于获取作者姓名和电子邮件地址的方法：

impl Signature<'_> {
    /// Returns the author's name as a `&str`,
    /// or `None` if it is not well-formed UTF-8.
    pub fn name(&self) -> Option<&str> {
        unsafe {
            char_ptr_to_str(self, (*self.raw).name)
        }
    }

    /// Returns the author's email as a `&str`,
    /// or `None` if it is not well-formed UTF-8.
    pub fn email(&self) -> Option<&str> {
        unsafe {
            char_ptr_to_str(self, (*self.raw).email)
        }
    }
}

上述方法都依赖于一个私有的实用函数 char_ptr_to_str ：

/// Tries to borrow a `&str` from `ptr`, given that `ptr` may be null or
/// refer to ill-formed UTF-8. The result gets a lifetime as if it were
/// borrowed from `_owner`.
///
/// Safety: if `ptr` is non-null, it must point to a null-terminated C
/// string that is both safe to access and whose contents are not modified
/// for at least as long as the lifetime of `_owner`.
unsafe fn char_ptr_to_str<T>(_owner: &T, ptr: *const c_char) -> Option<&str> {
    if ptr.is_null() {
        None
    } else {
        unsafe {
            CStr::from_ptr(ptr).to_str().ok()
        }
    }
}

参数 _owner 的值从未被使用过，但它的存在时间是真实的。如果让这个函数签名中的存在时间变得明确的话，我们就可以这样表述了：

fn char_ptr_to_str<'o, T: 'o>(
    _owner: &'o T,
    ptr: *const c_char,
) -> Option<&'o str>


CStr::from_ptr 函数返回的是一个生命周期完全无限制的 &CStr 对象，因为它是从一个已解引用的原始指针中借用来的。生命周期无限制的对象几乎总是存在不准确的情况，因此最好尽早对其进行约束。通过引入 _owner 参数，Rust 能够将其生命周期与返回值的类型关联起来，这样调用方就能获得一个更加有约束作用的引用。


最后，我们为所有需要的功能提供了安全的接口。在 src/main.rs 中，新的 main 函数已经被大大简化，看起来就像真正的 Rust 代码一样。

fn main() {
    let path = std::env::args_os()
        .nth(1)
        .expect("usage: git-toy PATH");

    let repo = git::Repository::open(&path)
        .expect("opening repository");

    let commit_oid = repo
        .reference_name_to_id("HEAD")
        .expect("looking up 'HEAD' reference");

    let commit = repo
        .find_commit(&commit_oid)
        .expect("looking up commit");

    let author = commit.author();
    println!(
        "{} <{}>\n",
        author.name().unwrap_or("(none)"),
        author.email().unwrap_or("none"),
    );

    println!("{}", commit.message().unwrap_or("(none)"));
}


在这一章中，我们从那些无法提供太多安全保障的简单接口，发展到了一种能够保护潜在风险的 API。当发现 API 违反了其契约时，就会引发 Rust 类型错误。这样一来，就形成了一个 Rust 可以确保其被正确使用的接口。在很大程度上，我们让 Rust 执行的规则，其实正是 C 和 C++程序员自己也会施加的那些规则。让 Rust 比 C 和 C++更严格的原因，并不是因为这些规则本身过于复杂，而是因为这些规则的执行方式既机械又全面。

结论

Rust 并非一种简单的编程语言。它的设计目标是将两个截然不同的世界融合在一起。这是一种现代编程语言，从一开始就注重安全性；同时，它还具备诸如闭包和迭代器等便捷特性。不过，Rust 旨在让你能够掌控运行于该语言之上的机器的所有原始能力，同时尽可能减少运行时的开销。

这种语言的特性正是为了达成这些目标而设计的。Rust 能够很好地弥补大部分差距，通过安全的代码实现这一目标。它的借用检查器和零成本抽象技术让你尽可能接近底层硬件，同时不会带来未定义的行为风险。当这些功能还不够时，或者当你需要利用现有的 C 语言代码时，安全的代码和外部函数接口就派上了用场。不过，语言不仅仅提供这些不安全的功能，我们的目标始终是利用这些不安全的功能来构建安全的 API。我们对 libgit2 所做的就是如此。Rust 团队对 Box 、 Vec 以及其他集合、通道等模块所做的也是类似的工作：标准库里充满了安全的抽象概念，而它们背后则有一些不安全的代码在运作。

一种具有 Rust 特性的语言，或许并不注定会成为最简单的工具。但 Rust 确实具备安全性、高效性、并发性以及实用性。可以利用 Rust 来构建庞大、快速、安全且强大的系统，从而充分发挥硬件的全部潜力。使用 Rust 可以让软件变得更加优秀。
