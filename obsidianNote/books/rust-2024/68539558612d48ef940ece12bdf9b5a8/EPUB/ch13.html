这一章介绍了我们所说的“实用特性”。这些特性是从标准库中提取出来的多种特性，它们对 Rust 语言的编写方式产生了重要影响。要想编写符合语言习惯的代码，并为你的软件包设计出用户能够认可的公共接口，就必须熟悉这些特性。

这些特性中的一些是 Rust 语言本身就具备的。例如，实现了 Drop 特性的类型在值被释放时会自动触发一个特殊的操作。这一点对于占用堆内存的类型（ String 、 Vec ）或系统资源的类型（ File 、 TcpStream ）来说非常重要。同样， Deref 特性使得智能指针类型可以表现得像引用，这样每次使用 Box 或 Rc 时都可以避免不必要的代码重复编写。Rust 编译器了解这些特性，并会隐式地使用它们。

放下


当某个值的拥有者消失时，我们说该值被“释放”了。值的释放意味着释放该值所拥有的其他值、堆内存以及系统资源。值的释放发生在多种情况下：当变量超出作用域时；在表达式语句结束时；当删除向量中的元素时；等等。

在大多数情况下，Rust 能够自动处理值的丢失问题。例如，假设你定义了以下类型：

struct Appellation {
    name: String,
    nicknames: Vec<String>,
}


Appellation 对象拥有用于存储字符串内容的内存空间，同时还有用于保存向量元素的缓冲区。每当 Appellation 对象被销毁时，Rust 会自动处理所有这些清理工作，无需您进行任何额外的编码操作。不过，如果您愿意，可以通过实现 std::ops::Drop 特质来定制 Rust 如何释放您的类型的值：

trait Drop {
    fn drop(&mut self);
}


在 Rust 中，某种实现方式类似于 C++中的析构函数，或者其他语言中的终结器。当某个值被销毁时，如果该值实现了 std::ops::Drop 接口，Rust 会调用其 drop 方法。之后，Rust 会继续像平常一样销毁该值所拥有的所有字段或元素。这种对 drop 方法的隐式调用是调用该方法的唯一方式；如果你试图直接调用该方法，Rust 会将其视为一个错误。

因为 Rust 在释放字段或元素之前会先调用 Drop::drop 方法，所以该方法接收到的值始终是完全初始化的。对于我们的 Appellation 类型，实现 Drop 方法可以充分利用其字段的功能。

impl Drop for Appellation {
    fn drop(&mut self) {
        print!("Dropping {}", self.name);
        if !self.nicknames.is_empty() {
            print!(" (AKA {})", self.nicknames.join(", "));
        }
        println!();
    }
}

鉴于这种实施方式，我们可以写出如下内容：

{
    let mut a = Appellation {
        name: "Zeus".to_string(),
        nicknames: vec![
            "cloud collector".to_string(),
            "king of the gods".to_string(),
        ],
    };

    println!("before assignment");
    a = Appellation {
        name: "Hera".to_string(),
        nicknames: vec![],
    };
    println!("at end of block");
}

当我们把第二个 Appellation 赋值给 a 时，第一个 Appellation 就会被丢弃；而当我们离开 a 的作用域时，第二个 Appellation 也会被丢弃。这段代码会输出如下结果：

before assignment
Dropping Zeus (AKA cloud collector, king of the gods)
at end of block
Dropping Hera

由于我们的 std::ops::Drop 在 Appellation 中的实现只是简单地打印一条消息，那么究竟是如何清理其内存的呢？ Vec 类型实现了 Drop 接口，它会释放每个元素所占用的内存，并释放那些由堆分配的内存缓冲区。 String 在内部使用 Vec<u8> 来保存文本数据，因此 String 不需要自己实现 Drop 接口；它可以让 Vec 负责释放这些字符所占用的内存。同样的原理也适用于 Appellation 值：当其中一个值被释放时，实际上是由 Vec 实现的 Drop 接口来负责释放每个字符串的内容，以及释放存储这些元素的缓冲区。至于存储 Appellation 值本身的内存，它也有一个拥有者，可能是某个局部变量或某种数据结构，这个拥有者负责释放该内存。

如果某个变量的值被移到了其他地方，导致该变量在超出作用域时处于未初始化的状态，那么 Rust 不会尝试删除该变量：因为该变量已经没有任何值可以删除了。

这个原则即使在变量的值已经发生变化的情况下仍然适用，这取决于控制流程的走向。在这种情况下，Rust 通过一种不可见的标志来跟踪变量的状态，以确定是否需要更新该变量的值。

let p;
{
    let q = Appellation {
        name: "Cardamine hirsuta".to_string(),
        nicknames: vec![
            "shotweed".to_string(),
            "bittercress".to_string(),
        ],
    };
    if complicated_condition() {
        p = q;
    }
}
println!("Sproing! What was that?");


根据 complicated_condition 的返回值， true 或 false 中的哪一个将会拥有 Appellation ，而另一个则仍然处于未初始化的状态。 Appellation 最终属于哪个变量，决定了它是在 println! 之前还是之后被丢弃——因为 q 在 println! 之前就离开了作用域，而 p 则是在 println! 之后才离开作用域。虽然一个变量可以被移动到不同的位置，但 Rust 只会在一次的情况下丢弃一个变量。

通常来说，除非你需要定义一个需要管理资源的类型，否则不需要实现 std::ops::Drop 。例如，在 Unix 系统中，Rust 的标准库内部使用了以下类型来表示操作系统文件描述符：

struct FileDesc {
    fd: c_int,
}


FileDesc 中的 fd 字段表示的是在程序结束时需要关闭的文件描述符的编号； c_int 是 i32 的别名。标准库对 FileDesc 的实现如下： Drop 

impl Drop for FileDesc {
    fn drop(&mut self) {
        let _ = unsafe { libc::close(self.fd) };
    }
}

在这里， libc::close 是 C 语言库中 close 函数的 Rust 命名形式。Rust 代码只能在 unsafe 代码块内调用 C 语言函数，因此这里使用了这种命名方式来表示库中的函数。

如果一个类型实现了 Drop ，那么它就不能同时实现 Copy 特性。如果某个类型属于 Copy 类型，这意味着简单的字节级复制就足以生成该值的独立副本。不过，通常情况下，对同一份数据多次调用 drop 方法是会犯错的。

标准的序曲包含一个用于删除某个值的函数，该值被标记为 drop 。不过，这个函数的实现其实并不复杂：

fn drop<T>(_x: T) {}


换句话说，它接收参数时是以值的形式进行的，从调用者那里获取参数的值，然后并不对这个值进行任何处理。就像其他变量一样，Rust 在变量超出作用域时会释放该变量所存储的值。

尺寸


固定大小的类型是指其各个值在内存中都具有相同的大小。在 Rust 中，几乎所有的类型都是固定大小的：每个 u64 类型需要 8 个字节，每个 (f32, f32, f32) 元组需要 12 个字节。甚至枚举类型也有固定的大小：无论实际存在哪种枚举值，枚举类型总是会占用足够的内存来保存其最大值的空间。虽然 Vec<T> 类型拥有一个可以动态分配大小的堆内存缓冲区，但 Vec 值本身是指向该缓冲区的指针，因此其大小是固定的。所以 Vec<T> 类型也有固定的大小。


所有固定大小的类型都实现了 std::marker::Sized 特征。这个特征没有相关的方法或关联的类型。Rust 会自动为所有适用该特征的类型实现这个特征；你无法自行实现它。 Sized 的唯一用途是作为类型变量的绑定：像 T: Sized 这样的绑定要求 T 必须是一个在编译时就能知道大小的类型。这种特征被称为标记特征，因为 Rust 语言本身使用它们来标记某些类型，使其具有特定的特性。


不过，Rust 中也有一些动态大小的类型，这些类型的数值大小并不固定。例如，字符串切片类型 str （注意，如果没有 & 的话）就是动态大小的。而字符串字面量 "diminutive" 和 "big" 则是对 str 切片的引用，这两个切片分别占用 10 字节和 3 字节的存储空间。如图 13-1 所示，数组切片类型如 [T] （同样，如果没有 & 的话）也是动态大小的；比如 &[u8] 这样的共享引用，可以指向任何大小的 [u8] 切片。


在 Rust 中，另一种常见的动态大小类型是指针对象类型 dyn 。如我们在“使用 dyn”部分所解释的， dyn 类型可以指向任何实现了特定 trait 的值。例如， &dyn std::io::Write 和 Box<dyn std::io::Write> 类型是指向实现了 Write trait 的值的指针。这个对象可能是文件、网络套接字，或者某种你自己定义的类型，而你需要实现 Write trait 来定义这种类型。由于实现 Write trait 的类型数量无限，因此 dyn Write 类型就是动态大小的类型；其值的尺寸可以是多种不同的大小。


变量或参数不能具有动态大小的类型。我们只能通过像 &str 或 Box<dyn Write> 这样的指针来处理动态大小类型的数值，而这些指针本身却是固定大小的。如图 13-1 所示，指向动态大小值的指针总是具有较大的宽度，即两个字宽；指向某个切片的指针也包含了该切片的长度信息；而指向特征对象的指针则还包含了一个 vtable 指针。


指向切片的指针和指向 trait 对象的指针是对称匹配的。在这两种情况下，类型都缺乏使用所需的信息：Rust 在不知道 [u8] 的长度的情况下无法对其进行索引，同样，在不知道 dyn Write 的实际类型的情况下，也无法调用其上的方法。在这两种情况下，胖指针都负责填补类型中缺失的信息，携带了长度或 vtable 指针。那些被省略的静态信息被动态信息所替代。

由于动态大小的类型存在诸多限制，大多数泛型类型变量应该被限制为 Sized 类型的变量。实际上，这种限制是 Rust 中默认的设定：当你使用 struct S<T> { ... } 时，Rust 会理解为 struct S<T: Sized> { ... } 类型。如果你不想以这种方式限制 T 类型，就必须明确声明放弃此限制，即使用 struct S<T: ?Sized> { ... } 类型。 ?Sized 语法则专门用于这种情况，它的含义是“不一定就是 Sized 类型”。

将某个类型参数标记为 T: ?Sized ，在那些总是通过引用或其他指针来处理该类型值的通用代码中是合理的。例如，如果你写 struct S<T: ?Sized> { b: Box<T> } ，那么 Rust 会允许你写 S<str> 和 S<dyn Write> ，此时盒子会成为一个较大的指针；而写 S<i32> 和 S<String> 时，盒子则只是一个普通的指针。

标准的 PartialEq 特征也是具有 ?Sized 绑定的通用代码的另一个例子：

trait PartialEq<Rhs = Self>
where
    Rhs: ?Sized,
{
    fn eq(&self, other: &Rhs) -> bool;
    fn ne(&self, other: &Rhs) -> bool {
        !self.eq(other)
    }
}


尽管存在这些限制，但动态大小的类型设计使得 Rust 的类型系统能够更流畅地运行。在阅读标准库文档时，你可能会偶尔看到类型变量上带有 ?Sized 的绑定；这通常意味着该类型只是被指向了某个对象，从而让相关代码能够使用切片、特征对象以及普通值。而当类型变量带有 ?Sized 的绑定时，人们通常认为它的大小并不明确：它可能是 Sized ，也可能不是。

除了切片和结构体对象之外，还有一种具有动态大小类型的结构。结构类型的最后一个字段（但仅最后一个字段）可以具有动态大小，而这样的结构体本身也具有动态大小。例如， Rc<T> 这种引用计数指针在内部实际上是一个指向私有类型 RcBox<T> 的指针，该类型同时存储了引用计数以及 T 数据。下面是对 RcBox 的简化定义：

struct RcBox<T: ?Sized> {
    ref_count: usize,
    value: T,
}


value 字段是 T 所指向的地址； Rc<T> 对该字段进行引用计数操作； Rc<T> 则是指向该字段的指针。 ref_count 字段保存着引用计数信息。


真正的 RcBox 只是标准库的一个实现细节，并不适用于公开使用。不过，假设我们使用的是上述定义。你可以将 RcBox 与 Sized 类型结合使用，比如与 RcBox<String> 结合，最终会得到 Sized 结构类型。或者，你可以将其与动态尺寸类型结合使用，比如与 RcBox<dyn std::fmt::Display> 结合（其中 Display 是那些可以通过 println! 及类似宏进行格式化的类型的特征）； RcBox<dyn Display> 则是一种动态尺寸的结构类型。

你不能直接创建一个具有 RcBox<dyn Display> 值的对象。相反，你需要先创建一个普通大小的 RcBox 对象，且该对象的 value 类型需要实现 Display 接口，例如 RcBox<String> 这样的类型。然后，Rust 允许你将引用 &RcBox<String> 转换为更长的引用 &RcBox<dyn Display> ：

let boxed_lunch: RcBox<String> = RcBox {
    ref_count: 1,
    value: "lunch".to_string(),
};

use std::fmt::Display;
let boxed_displayable: &RcBox<dyn Display> = &boxed_lunch;

在将值传递给函数时，这种转换是隐式的，因此你可以将一个 &RcBox<String> 传递给那个期望接收 &RcBox<dyn Display> 参数的函数：

fn display(boxed: &RcBox<dyn Display>) {
    println!("For your enjoyment: {}", &boxed.value);
}

display(&boxed_lunch);


这将产生如下输出：

For your enjoyment: lunch

克隆


std::clone::Clone 特征适用于那些能够复制自身的类型。 Clone 的定义如下：

trait Clone: Sized {
    fn clone(&self) -> Self;
    fn clone_from(&mut self, source: &Self) {
        *self = source.clone();
    }
}


clone 方法应该创建一个独立的 self 的副本并返回它。由于该方法的返回类型为 Self ，而函数可能不会返回动态大小的类型，因此 Clone 特征本身扩展了 Sized 特征：这相当于限制了实现中的 Self 类型只能为 Sized 。


clone_from 方法会将 self 复制到一个新的副本 source 中。而 clone_from 的默认实现方式是直接克隆 source ，然后再将克隆后的对象移动到 *self 中。这种方法通常都是有效的，但对于某些类型的数据，其实有更快速的实现方式可以达到相同的效果。例如，假设 s 和 t 都是 String 类型的对象。那么 s = t.clone(); 语句需要先克隆 t ，然后丢弃旧的 s 值，最后将克隆后的对象移动到 s 中。这样只需要一次内存分配和一次释放操作。但如果原始对象 s 所使用的内存缓冲区有足够的空间来存储 t 的内容，那么就不需要进行任何分配或释放操作了——只需将 t 的文本复制到 s 的缓冲区中，并调整其长度即可。在通用代码中，只要有可能，就应该使用 clone_from 来实现优化过的实现方式。

如果你的 Clone 实现只是将 clone 应用于类型的每个字段，然后从这些字段构建出一个新的值，而 clone_from 的默认定义也足够完善，那么 Rust 会自动完成这一操作：只需在类型定义上方添加 #[derive(Clone)] 即可。

在标准库中，几乎每一种适合复制的类型都实现了 Clone 接口。像 bool 和 i32 这样的基本类型也是如此。而像 String 、 Vec<T> 和 HashMap 这样的容器类型同样实现了该接口。不过，有一些类型并不适合复制，比如 std::sync::Mutex ；这些类型没有实现 Clone 接口。还有一些类型如 std::fs::File 可以复制，但如果操作系统缺乏必要的资源，复制操作可能会失败；这类类型没有实现 Clone 接口，因为 clone 接口要求必须始终可靠执行。相反， std::fs::File 提供了一个 try_clone 方法，该方法返回一个 std::io::Result<File> 对象，该对象可以报告失败情况。

副本


在第四章中，我们解释了对于大多数类型来说，赋值操作实际上是复制值，而不是移动值本身。这种复制值的方式使得跟踪所拥有的资源变得更加简单。不过，在“复制类型：移动的例外情况”这一节中，我们指出了一个例外：那些并不拥有任何资源的简单类型，在赋值操作时，实际上只是复制了源值，而不是移动值本身，从而使源值保持未初始化的状态。


当时，我们对 Copy 的具体含义保持模糊不清，但现在我们可以告诉您：如果一个类型实现了 std::marker::Copy 标记特质，那么它就属于 Copy 类型。该特质的定义如下：

trait Copy: Clone {}

这对于你自己的类型来说，实现起来确实很容易：

impl Copy for MyType {}

但是，由于 Copy 是一种在语言中具有特殊意义的标记类型，Rust 允许某个类型仅通过浅层字节级复制来实现 Copy 。而那些需要管理其他资源的类型，比如堆内存缓冲区或操作系统句柄之类的对象，则无法实现 Copy 。

任何实现了 Drop trait 的类型都不可能是 Copy 类型的。在 Rust 中，如果某个类型需要特殊的清理操作，那么它也必然需要特殊的复制操作，因此不可能是 Copy 类型的。


在创建类型 Copy 之前，请仔细考虑一下。虽然这样做使得该类型更易于使用，但也会对其实现提出严格的要求。隐式复制方式也可能带来较高的性能开销。我们在《复制类型：Moves 规则的例外情况》一文中详细介绍了这些因素。

Deref 和 DerefMut


你可以通过实现 std::ops::Deref 和 std::ops::DerefMut 特性来指定像 * 和 . 这样的解引用运算符在你的类型上的行为。像 Box<T> 和 Rc<T> 这样的指针类型实现了这些特性，因此它们可以像 Rust 内置的指针类型一样使用。例如，如果你有一个 Box<Complex> 的值 b ，那么 *b 就会指向 b 所指向的 Complex 值，而 b.re 则指向该值的实际组件。如果上下文分配或借入了对被引用对象的可修改的引用，Rust 会使用 DerefMut 特性（“可修改解引用”）；否则，仅需要只读访问，此时就会使用 Deref 特性。

这些特征定义如下：

trait Deref {
    type Target: ?Sized;
    fn deref(&self) -> &Self::Target;
}

trait DerefMut: Deref {
    fn deref_mut(&mut self) -> &mut Self::Target;
}


deref 和 deref_mut 方法将 self 参数以引用方式接收，并返回对 Self::Target 的引用。 Target 类型应该是指 Self 所包含、拥有或引用的某个对象；对于 Box<Complex> 来说， Target 类型就是 Complex 。注意， DerefMut 继承自 Deref ：如果你可以解引用某个对象并对其进行修改，那么当然也可以借用其共享引用。由于这些方法返回的是与 &self 具有相同生命周期的引用，因此 self 在返回的引用存在期间仍然保持借用状态。


Deref 和 DerefMut 这些特性还有另一个作用。由于 deref 会接收 &Self 的引用，然后返回 &Self::Target 的引用，因此 Rust 能够自动将前者类型的引用转换为后者类型的引用。换句话说，如果插入一个 deref 调用会导致类型不匹配，Rust 会自动为你完成这一操作。实现 DerefMut 特性后，可变引用的转换也能得到支持。这些特性被称为“解引用强制转换”：一种类型被“强制”转换为另一种类型的行为。

虽然这些“去引用强制式”操作并非无法自行编写出来的东西，但它们确实更加方便实用。

  • 如果你有一些 Rc<String> 值 r ，想要对它们应用 String::find 操作，只需编写 r.find('?') 而不是 (*r).find('?') 即可。这样，方法调用会隐式借用 r ，而 &Rc<String> 会被转换为 &String ，因为 Rc<T> 实现了 Deref<Target = T> 的功能。


  • 你可以在 String 值的对象上使用如 split_at 这样的方法，尽管 split_at 是 str 切片类型的方法，因为 String 实现了 Deref<Target = str> 的功能。无需再重新实现 str 的所有方法，因为你可以将 &str 从 &String 中派生出来。

  • 如果你有一个字节向量 v ，想要将其传递给需要一个字节切片参数的函数 &[u8] ，你可以直接将 &v 作为参数传递，因为 Vec<T> 实现了 Deref<Target = [T]> 的功能。


如果需要的话，Rust 会连续应用多个解引用操作。例如，利用之前提到的解引用操作，你可以直接将 split_at 应用于 Rc<String> ，因为 &Rc<String> 可以解引用为 &String ，而 &String 又可以解引用为 &str ，进而访问到拥有 split_at 方法的 &str 。

例如，假设你拥有以下类型：

struct Selector<T> {
    /// Elements available in this `Selector`.
    elements: Vec<T>,

    /// The index of the "current" element in `elements`. A `Selector`
    /// behaves like a pointer to the current element.
    current: usize,
}

为了让 Selector 如文档注释所声明的那样起到注释的作用，你必须为该类型实现 Deref 和 DerefMut 功能。

use std::ops::{Deref, DerefMut};

impl<T> Deref for Selector<T> {
    type Target = T;
    fn deref(&self) -> &T {
        &self.elements[self.current]
    }
}

impl<T> DerefMut for Selector<T> {
    fn deref_mut(&mut self) -> &mut T {
        &mut self.elements[self.current]
    }
}

在这些实现的基础上，你可以这样使用 Selector ：

let mut s = Selector {
    elements: vec!['x', 'y', 'z'],
    current: 2,
};

// Because `Selector` implements `Deref`, we can use the `*` operator to
// refer to its current element.
assert_eq!(*s, 'z');

// Assert that 'z' is alphabetic, using a method of `char` directly on a
// `Selector`, via deref coercion.
assert!(s.is_alphabetic());

// Change the 'z' to a 'w', by assigning to the `Selector`'s referent.
*s = 'w';

assert_eq!(s.elements, ['x', 'y', 'w']);


Deref 和 DerefMut 这两个特性旨在用于实现智能指针类型，比如 Box 、 Rc 和 Arc 等。这些类型可以作为某事物的“拥有版本”，同时也会以引用方式被频繁使用，就像 Vec<T> 和 String 可以作为 [T] 和 str 的“拥有版本”一样。不过，我们并不应该仅仅为了让 Target 类型的方法能够自动出现在 Deref 和 DerefMut 上而实现这两个类型，就像 C++中的基类的方法会自动出现在子类中一样。这种做法并不总是能如预期般工作，一旦出现问题，可能会让人感到困惑。

这些去引用约束存在一个需要注意的地方：它可能会导致一些混淆。Rust 使用这些约束来解决类型冲突，但并不能用于满足类型变量的约束条件。例如，以下代码运行起来是完全正常的：

let s = Selector {
    elements: vec!["good", "bad", "ugly"],
    current: 2,
};

fn show_it(thing: &str) {
    println!("{thing}");
}
show_it(&s);


不过，如果你将 show_it 转换为一个通用函数，那么 Rust 就不再具备协作性了：

use std::fmt::Display;

fn show_generic<T: Display>(thing: T) {
    println!("{thing}");
}

show_generic(&s);

Rust 抱怨说：

error: `Selector<&str>` doesn't implement `std::fmt::Display`
   |
41 |     show_generic(&s);
   |     ------------  ^ unsatisfied trait bound
   |     |
   |     required by a bound introduced by this call
   |
help: the trait `std::fmt::Display` is not implemented for `Selector<&str>`
   |
 7 | struct Selector<T> {
   | ^^^^^^^^^^^^^^^^^^
   = note: required for `&Selector<&str>` to implement `std::fmt::Display`
note: required by a bound in `show_generic`
   |
35 |  fn show_generic<T: Display>(thing: T) {
   |                     ^^^^^^^ required by this bound in `show_generic`
help: consider dereferencing here
   |
41 |     show_generic(&*s);
   |                   +

这可能会让人感到困惑：如何使得一个函数具有通用性时还会引入错误呢？确实， Selector<&str> 并没有实现 Display 的功能，但它引用了 &str ，而 &str 显然实现了 Display 的功能。


为了解决这个问题，你可以使用 as 运算符来明确说明强制操作的细节：

show_it_generic(&s as &str);

或者，正如编译器所建议的，你可以使用 &* 来强制进行类型转换。

show_it_generic(&*s);

默认设置


某些类型具有相当明显的默认值：例如，默认的向量或字符串为空，默认的数字为零，默认的 Option 相当于 None ，等等。像这样的类型可以实现 std::default::Default 特性。

trait Default {
    fn default() -> Self;
}


default 方法只是返回一个新的 Self 类型的值。 String 对 Default 的实现非常直接明了：

impl Default for String {
    fn default() -> String {
        String::new()
    }
}

Rust 中的所有集合类型—— Vec 、 HashMap 、 BinaryHeap 等——都实现了 Default 接口。此外，还有 default 方法，该方法返回一个空集合。当你需要创建一个集合，但希望让调用者自行决定要创建哪种类型集合时，这种方法非常有用。例如， Iterator trait 的 partition 方法可以将迭代器产生的数值分成两个集合，并通过一个闭包来决定每个数值应该属于哪个集合。

use std::collections::HashSet;
let squares = [4, 9, 16, 25, 36, 49, 64];
let (powers_of_two, impure): (HashSet<i32>, HashSet<i32>) =
    squares.iter().partition(|&n| n & (n - 1) == 0);

assert_eq!(powers_of_two.len(), 3);
assert_eq!(impure.len(), 4);


|&n| n & (n-1) == 0 的闭包通过一些特殊的处理来识别 2 的幂次数字，而 partition 则利用这些数字生成两个 HashSet 。不过， partition 并不局限于 HashSet 类型；你可以将其用于生成任何你想要的集合，只要该集合类型实现了 Default 接口，就可以从一个空集合开始，然后通过 Extend<T> 向集合中添加 T 元素。 String 实现了 Default 和 Extend<char> 接口，因此你可以这样编写：

let (upper, lower): (String, String) =
    "Great Teacher Onizuka".chars().partition(|&c| c.is_uppercase());
assert_eq!(upper, "GTO");
assert_eq!(lower, "reat eacher nizuka");


Default 的另一个常见用途是为结构体生成默认值，这些结构体包含大量参数，而其中大多数参数通常不需要进行更改。例如， glium 这个包提供了对强大且复杂的 OpenGL 图形库的 Rust 绑定支持。 glium::DrawParameters 结构体包含 24 个字段，每个字段都控制着 OpenGL 渲染图形时的不同细节。 glium draw 函数需要一个 DrawParameters 结构体作为参数。由于 DrawParameters 实现了 Default ，因此你可以创建一个这样的结构体作为参数传递给 draw ，只需指定那些需要修改的字段即可。

let params = glium::DrawParameters {
    line_width: Some(0.02),
    point_size: Some(0.02),
    ..Default::default()
};

target.draw(..., &params).unwrap();

这行代码调用了 Default::default() ，用于创建一个 DrawParameters 值，该值的所有字段都使用了默认值进行初始化。然后，通过 .. 语法对结构体进行构造，创建一个新的结构体，其中 line_width 和 point_size 字段的值发生了改变。现在，你可以将这个新创建的结构体传递给 target.draw 。

如果某种类型 T 实现了 Default ，那么标准库会自动为 Rc<T> 、 Arc<T> 、 Box<T> 、 Cell<T> 、 RefCell<T> 、 Cow<T> 、 Mutex<T> 和 RwLock<T> 实现 Default 。例如，类型 Rc<T> 的默认值是指向类型 T 的默认值的 Rc 。

如果元组类型中的所有字段类型都实现了 Default 功能，那么整个元组类型也将会实现这一功能，此时元组将默认存储每个字段的默认值。


你可以通过使用 #[derive(Default)] 来实现对枚举类型的自动赋值操作，只需用 #[default] 标记默认变体即可：

#[derive(Default)]
enum Background {
    #[default]
    Empty,
    Color(Color),
    Image(PathBuf),
}

如果默认模板中有任何字段，这些字段也必须实现 Default 的功能。

AsRef 和 AsMut


当一个类型实现了 AsRef<T> ，这意味着你可以高效地从它那里借用 &T 。 AsMut 则对应于可变的引用。它们的定义如下：

trait AsRef<T: ?Sized> {
    fn as_ref(&self) -> &T;
}

trait AsMut<T: ?Sized> {
    fn as_mut(&mut self) -> &mut T;
}

例如， Vec<T> 实现了 AsRef<[T]> 的功能，而 String 则实现了 AsRef<str> 的功能。你还可以将 String 的内容作为字节数组来使用，因此 String 也实现了 AsRef<[u8]> 的功能。

AsRef 通常用于使函数的参数类型更加灵活。例如， std::fs::File::open 函数可以这样声明：

fn open<P: AsRef<Path>>(path: P) -> Result<File>


open 真正想要的是 &Path ，即表示文件系统路径的类型。但是，有了这样的签名， open 就可以接受任何可以借用 &Path 的对象——也就是说，任何实现了 AsRef<Path> 的对象。这类类型包括 String 和 str ，还有操作系统接口字符串类型 OsString 和 OsStr ，当然还有 PathBuf 和 Path ；完整的列表请参阅库文档。正是这一点使得你可以将字符串字面量传递给 open 。

let dot_emacs = std::fs::File::open("/home/jimb/.emacs")?;


标准库中的所有文件系统访问函数都采用这种方式接受路径参数。对于调用者来说，这种效果类似于 C++中重载函数的行为；不过，Rust 在确定哪些参数类型是可接受的方面采用了不同的方法。


但這肯定不是全部情況。字符串字面量屬于 &str 類型，而實現了 AsRef<Path> 類型的類別則是 str 類型，而且還缺少 & 這個屬性。正如我们在“Deref 和 DerefMut”中所述，Rust 並不會嘗試解構來滿足類型變量的限制，因此這些解構方法在此處也無法使用。

幸运的是，标准库已经包含了这种通用实现：

impl<T, U> AsRef<U> for &T
where
    T: AsRef<U> + ?Sized,
    U: ?Sized,
{
    fn as_ref(&self) -> &U {
        (*self).as_ref()
    }
}

换句话说，对于任何类型 T 和 U ，如果满足 T: AsRef<U> 的条件，那么 &T: AsRef<U> 也满足该条件：只需遵循引用顺序，然后像之前一样进行操作。特别地，由于满足 str: AsRef<Path> 的条件，因此 &str: AsRef<Path> 也满足该条件。从某种意义上说，这是一种在检查类型变量的 AsRef 约束时实现有限形式解引用强制的方式。

你可能认为，如果一个类型实现了 AsRef<T> ，那么它也应该实现 AsMut<T> 。然而，在某些情况下，这种假设并不适用。例如，我们已经提到 String 实现了 AsRef<[u8]> ；这是合理的，因为每个 String 都包含一个字节缓冲区，可以用来存储二进制数据。但是 String 还保证了那些字节确实是格式正确的 UTF-8 编码的 Unicode 文本。如果 String 实现了 AsMut<[u8]> ，那么调用者就可以随意修改 String 中的字节，这样一来，我们就无法再相信 String 是格式正确的 UTF-8 编码了。只有在这种修改给定的 T 不会违反该类型的不变式的情况下，一个类型才应该实现 AsMut<T> 。

虽然 AsRef 和 AsMut 的实现相当简单，但提供通用的引用转换特性可以避免需要大量复杂的特定转换机制。在可能的情况下，应避免定义自己的 AsFoo 特性，而是直接实现 AsRef<Foo> 的功能。

借来又借来……


std::borrow::Borrow 特性与 AsRef 类似：如果一个类型实现了 Borrow<T> ，那么它的 borrow 方法可以高效地从该类型中借用 &T 。不过 Borrow 有一些额外的限制：一个类型只有在以与所借用类型相同的哈希和比较方式时，才需要实现 Borrow<T> 。（Rust 并不强制执行这一限制，但这只是该特性的文档说明。）因此， Borrow 在处理哈希表或树中的键值时非常有用，或者在处理需要被哈希或比较值的场景时也非常有价值。

这种区别在从 String 处进行借用时非常重要。例如， String 实现了 AsRef<str> 、 AsRef<[u8]> 和 AsRef<Path> 的功能，但这三个目标类型通常会有不同的哈希值。只有 &str 的切片可以保证与对应的 String 具有相同的哈希值，因此 String 只实现了 Borrow<str> 的功能。

Borrow 的定义与 AsRef 的相同；只是名称已经发生了变化：

trait Borrow<Borrowed: ?Sized> {
    fn borrow(&self) -> &Borrowed;
}

Borrow 的设计目的是通过通用的哈希表和其他关联集合类型来解决特定问题。例如，假设有一个 std::collections​::HashMap<String, i32> ，它将字符串映射到数字上。该表的键是 String ；每个条目都对应一个键。那么，在查找该表中条目的方法签名应该是什么样的呢？下面是初步的尝试：

impl<K, V> HashMap<K, V>
where
    K: Eq + Hash,
{
    fn get(&self, key: K) -> Option<&V> { ... }
}

这很合理：要查询某个条目，就必须提供与该表对应的键。不过在这种情况下， K 实际上就是 String ；这样的签名会导致每次调用 get 时都需要传递一个 String 值，这显然是一种浪费。实际上，我们只需要一个对键的引用即可。

impl<K, V> HashMap<K, V>
where
    K: Eq + Hash,
{
    fn get(&self, key: &K) -> Option<&V> { ... }
}

这稍微好一些了，不过现在你需要将密钥以 &String 的形式传递。所以，如果你想查找一个固定的字符串，就必须这样写：

hashtable.get(&"twenty-two".to_string())


这太荒谬了：它会在堆内存中分配一个大小为 String 的缓冲区，然后将文本复制到该缓冲区中。不过，之后它又从该缓冲区中借用数据，将其传递给 get ，最后又将其丢弃掉。

这样的实现应该足以应对任何需要哈希和比较的数据类型。例如， &str 这样的类型应该完全足够使用。这就是最终的版本，也是标准库中所包含的内容。

impl<K, V> HashMap<K, V>
where
    K: Eq + Hash,
{
    fn get<Q>(&self, key: &Q) -> Option<&V>
    where
        K: Borrow<Q>,
        Q: Eq + Hash + ?Sized,
    { ... }
}

换句话说，如果你可以借用某个条目的键作为 &Q ，那么生成的引用就会像该键本身一样进行哈希运算和比较。因此， &Q 显然应该是一种可行的键类型。由于 String 实现了 Borrow<str> 和 Borrow<String> 的功能，所以 get 的最终版本允许根据需求将 &String 或 &str 作为键来使用。


标准库提供了通用的实现方式，使得每一种类型都可以从自身这个实现中获取引用： T: Borrow<T> 。这样就能确保 &K 始终是一个合适的类型，用于查询 HashMap<K, V> 中的条目。


BorrowMut 特性相当于 Borrow ，用于表示可修改的引用。

trait BorrowMut<Borrowed: ?Sized>: Borrow<Borrowed> {
    fn borrow_mut(&mut self) -> &mut Borrowed;
}


对于 Borrow 所描述的那些期望，同样也适用于 BorrowMut 。

从……到……


std::convert::From 和 std::convert::Into 这些特性代表了那种消耗一个类型的值并返回另一个类型值的转换操作。而 AsRef 和 AsMut 这些特性则是从另一个类型中借用一个引用。 From 和 Into 则负责获取参数的值，对其进行处理，然后再将处理后的结果返还给调用者。

他们的定义非常对称：

trait Into<T>: Sized {
    fn into(self) -> T;
}

trait From<T>: Sized {
    fn from(other: T) -> Self;
}

标准库会自动完成每种类型到其自身的简单转换：每一种类型 T 都能实现到 From<T> 和 Into<T> 的转换。

虽然这些特征只是提供了两种实现同一件事的方法，但它们适用于不同的用途。

通常你会使用 Into 来使你的函数能够在接受的参数方面更加灵活。例如，如果你这样写：

use std::net::Ipv4Addr;

fn ping<A>(address: A) -> std::io::Result<bool>
where
    A: Into<Ipv4Addr>,
{
    let ipv4_address = address.into();
    ...
}

那么， ping 不仅可以接受一个 Ipv4Addr 作为参数，还可以接受一个 u32 或 [u8; 4] 数组作为参数，因为这两种类型都恰好实现了 Into<Ipv4Addr> 的功能。（有时候，将 IPv4 地址视为一个 32 位的值，或者将其视为 4 字节的数组是很有用的。）因为 ping 只知道 address 实现了 Into<Ipv4Addr> ，所以在调用 into 时不需要指定具体的类型；只有一种类型可能是可行的，所以类型推断会自动为你完成这一工作。

就像上一节中的 AsRef 一样，这种效果类似于 C++中函数重载的情况。有了 ping 的定义，我们就可以进行这样的调用了：

println!("{:?}", ping(Ipv4Addr::new(23, 21, 68, 141)));  // pass an Ipv4Addr
println!("{:?}", ping([66, 146, 219, 98]));              // pass a [u8; 4]
println!("{:?}", ping(0xd076eb94_u32));                  // pass a u32

不过， From 特性则扮演着不同的角色。 from 方法实际上是一个通用构造函数，它可以根据某个单一值来生成某个类型的实例。例如，而不是让 Ipv4Addr 拥有名为 from_array 和 from_u32 的两个方法，它只是实现了 From<[u8;4]> 和 From<u32> 方法，这样我们就能这样编写代码：

let addr1 = Ipv4Addr::from([66, 146, 219, 98]);
let addr2 = Ipv4Addr::from(0xd076eb94_u32);


只要实现得当，标准库会自动实现相应的 Into 特性。当定义自己的类型时，如果它包含单参数构造函数，那么应该将这些构造函数实现为 From<T> 类型的实例；Rust 能够轻松地将你的转换代码从 From 格式转换为 Into 格式。

因为 from 和 into 这两种转换方法会直接处理其参数，所以这些转换过程可以复用原始值的资源来构建新的转换结果。例如，假设你这样编写代码：

let text = "Beautiful Soup".to_string();
let bytes: Vec<u8> = text.into();

将 Into<Vec<u8>> 应用于 String 的过程，实际上只是将 String 中的堆缓冲区直接作为返回的向量元素的缓冲区使用，而无需进行任何分配或复制文本的操作。这再次证明了移动操作在实现高效算法时的重要作用。


不过，便宜的转换并不在 Into 和 From 的合同中有所涉及。而 AsRef 和 AsMut 的转换预计会较为便宜。 From 和 Into 的转换则可能需要对价值内容进行分配、复制或其他处理。例如， String 实现了 From<&str> 的功能，它将字符串切片内容复制到新的、由堆内存分配的内存缓冲区中。而 std::collections::BinaryHeap<T> 则实现了 From<Vec<T>> 的功能，它根据自身的算法要求对元素进行排序和重新整理。


? 运算符使用了 From 和 Into 来辅助清理那些可能会以多种方式失败的函数中的代码。在需要的时候，它会自动将特定的错误类型转换为更通用的错误类型。


例如，想象这样一个系统：它需要读取二进制数据，并将其中一部分数据从十进制数字转换为 UTF-8 文本格式。这意味着需要使用 str::from_utf8 和 FromStr 这两种实现方式来处理 i32 数据，而这两种实现方式可能会返回不同类型的错误。假设我们使用第 7 章中描述的 anyhow::Error 类型，那么 ? 运算符就可以完成转换工作了。

fn parse_i32_bytes(b: &[u8]) -> anyhow::Result<i32> {
    Ok(str::from_utf8(b)?.parse::<i32>()?)
}

像大多数错误类型一样， Utf8Error 和 ParseIntError 也实现了 std::error::Error 特征。而 anyhow 提供了一个通用的 From impl 方法，可以将任何实现了 std::error::Error 的对象转换为 anyhow::Error 类型。实际上， ? 会自动使用这个方法来完成转换。

// (code from the `anyhow` crate)
impl<E> From<E> for Error
where
    E: std::error::Error + Send + Sync + 'static,
{
    fn from(error: E) -> Self {
        let backtrace = ...;
        Error::construct_from_std(error, backtrace)
    }
}

这样，原本应该是一个相当复杂的函数，包含两条 match 语句，现在就变成了一行代码而已。

在 From 和 Into 被添加到标准库之前，Rust 代码中的许多功能都需要通过特定的转换方法和构造来实现，这些方法和构造都是针对特定类型设计的。 From 和 Into 则将这些惯例标准化了，这样当用户已经熟悉这些惯例时，就可以更轻松地使用各种类型。其他库以及语言本身也可以借鉴这些惯例，作为一种规范化的编码方式来处理转换问题。

From 和 Into 是绝对可靠的属性——它们的 API 设计要求转换操作不会失败。不过，许多转换情况其实比这更复杂。例如，像 i64 这样的大整数可以存储比 i32 更大的数字；而像 2_000_000_000_000i64 这样的数字转换为 i32 时，如果没有一些额外的信息作为辅助，结果往往并不理想。进行简单的位运算时，如果忽略前 32 位的数据，得到的结果往往不符合我们的期望。

let huge = 2_000_000_000_000i64;
let smaller = huge as i32;
println!("{smaller}");  // -1454759936


处理这种情况有很多方法。根据具体情况，采用“包装”转换方式可能是合适的。另一方面，像数字信号处理和控制系统这样的应用通常可以使用“饱和”转换方式，即把大于最大可能值的数字限制在该最大值以内。

TryFrom 和 TryInto


由于不清楚这种转换到底会如何表现，Rust 并没有为 i32 到 From<i64> 之间的转换实现相应的功能，也没有实现任何会丢失信息的数值类型之间的转换。相反， i32 实现了 TryFrom<i64> 的功能。 TryFrom 和 TryInto 是 From 和 Into 的“有缺陷的兄弟”，它们的实现方式也是类似的；而 TryFrom 的实现意味着 TryInto 也已经被实现了。

他们的定义比 From 和 Into 的定义要复杂一些。

pub trait TryFrom<T>: Sized {
    type Error;
    fn try_from(value: T) -> Result<Self, Self::Error>;
}

pub trait TryInto<T>: Sized {
    type Error;
    fn try_into(self) -> Result<T, Self::Error>;
}


try_into() 方法返回了一个 Result 的值。因此，我们可以选择在异常情况下采取什么行动，比如选择一个数值太大、无法容纳在结果类型中的数值。

// Saturate on overflow, rather than wrapping
let smaller: i32 = huge.try_into().unwrap_or(i32::MAX);

如果我们还想处理负面情况，可以使用 Result 中的 unwrap_or_else() 方法：

let smaller: i32 = huge.try_into().unwrap_or_else(|_|{
    if huge >= 0 {
        i32::MAX
    } else {
        i32::MIN
    }
});

对于自己的类型来说，实现有误差的转换也很简单。 Error 类型可以根据具体的需求，设计得简单或复杂。在这里，标准库使用了一个空结构体，仅用于表示发生了错误，因为唯一可能的错误就是溢出。而对于更复杂的类型之间的转换，则可能需要返回更多信息。

impl TryInto<LinearShift> for Transform {
    type Error = TransformError;

    fn try_into(self) -> Result<LinearShift, Self::Error> {
        if !self.normalized() {
            return Err(TransformError::NotNormalized);
        }
        ...
    }
}


当 From 和 Into 所表示的类型需要进行简单类型转换时， TryFrom 和 TryInto 则通过 Result 提供的灵活错误处理功能，进一步提升了 From 和 Into 转换的简洁性。这四种特性可以结合起来使用，从而在一个软件包中处理多种类型的关联问题。

拥有房产


如果给定一个引用，那么通常用来获取该引用所指向对象的副本的方法是调用 clone ，前提是该类型实现了 std::clone::Clone 的功能。但是，如果你想要克隆一个 &str 或 &[i32] 呢？你可能希望得到一个 String 或 Vec<i32> 作为克隆后的对象，不过 Clone 的定义并不允许这种情况：根据定义，克隆一个 &T 总是会返回一个 T 类型的值，而 str 和 [u8] 是动态大小的，它们甚至都不是函数可以返回的类型。


std::borrow::ToOwned 特性提供了一种更宽松的方法，可以将引用转换为已拥有的价值：

trait ToOwned {
    type Owned: Borrow<Self>;
    fn to_owned(&self) -> Self::Owned;
}


与 clone 不同， Self 必须返回与 Self 完全一致的结果。而 to_owned 则可以返回任何你从 &Self 中借来的内容。 Owned 类型必须实现 Borrow<Self> 接口。你可以从 Vec<T> 中借用 &[T] ，因此 [T] 可以实现 ToOwned<Owned = Vec<T>> 接口。只要 T 实现了 Clone 接口，我们就能将切片中的元素复制到向量中。同样地， str 实现了 ToOwned<Owned = String> 接口， Path 实现了 ToOwned<Owned = PathBuf> 接口，以此类推。

在工作中借贷与持有资产：谦逊的牛仔


在利用 Rust 编程时，需要充分考虑所有权相关的问题。例如，一个函数应该是通过引用方式还是值方式接收参数。通常我们可以选择其中一种方式，参数的类型则反映了我们的选择。但在某些情况下，我们可能在程序运行之前无法决定是使用引用还是拥有所有权； std::borrow::Cow 类型（表示“在写入时克隆”）提供了一种实现这一需求的方法。

其定义如下所示：

enum Cow<'a, B: ?Sized>
where
    B: ToOwned,
{
    Borrowed(&'a B),
    Owned(<B as ToOwned>::Owned),
}


要么借用对 B 的共享引用，要么拥有某个可以从中借用此类引用的对象。由于 Cow 实现了 Deref 接口，因此可以像对待对 B 的共享引用一样来调用其方法：如果 Cow 是 Owned ，那么它就借用了对所拥有对象的共享引用；而如果 Cow 是 Borrowed ，那么它就直接提供自己持有的引用。


你也可以通过调用对象的 to_mut 方法来获取对该对象值的可变引用。该方法返回的是 &mut B 类型的值。如果 Cow 实际上就是 Cow::Borrowed ，那么 to_mut 只需调用引用对象的 to_owned 方法来获取该对象的副本，然后将 Cow 转换为 Cow::Owned 类型，从而获取对新值的可变引用。这就是类型名称所代表的“写入时克隆”行为。


Cow 的一个常见用途是返回静态分配的字符串常量或计算得出的字符串。例如，假设你需要将一个错误枚举值转换为一条消息。大多数情况下，可以使用固定的字符串来处理这种情况，但有些情况则需要包含一些额外的数据到消息中。你可以这样使用 Cow<'static, str> ：

use std::borrow::Cow;
use std::path::PathBuf;

fn describe(error: &Error) -> Cow<'static, str> {
    match *error {
        Error::OutOfMemory => "out of memory".into(),
        Error::StackOverflow => "stack overflow".into(),
        Error::MachineOnFire => "machine on fire".into(),
        Error::Unfathomable => "machine bewildered".into(),
        Error::FileNotFound(ref path) => {
            format!("file not found: {}", path.display()).into()
        }
    }
}

这段代码的实现中，使用了 Cow 对 Into 的调用来构建各种值。在这条 match 语句的大多数分支中，都会返回一个 Cow::Borrowed ，该值指向一个静态分配的字符串。不过，当遇到 FileNotFound 这种变体时，我们就会使用 format! 来构造一个包含给定文件名的消息。这条 match 语句的这一分支最终会生成一个 Cow::Owned 值。

对于那些不需要更改值的 describe 调用者来说，可以直接将 Cow 视为 &str 进行处理。

println!("Disaster has struck: {}", describe(&error));

那些确实需要自有资产的人可以轻松获得这样的资产：

let mut log: Vec<String> = Vec::new();
...
log.push(describe(&error).into_owned());


使用 Cow 可以帮助 describe 及其调用者在必要时再进行处理。
