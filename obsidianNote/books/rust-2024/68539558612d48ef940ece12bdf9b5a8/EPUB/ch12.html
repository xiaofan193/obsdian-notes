#[derive(Clone, Copy, Debug)]
struct Complex<T> {
    /// Real portion of the complex number

我们可以像处理其他内置数字类型一样，使用 Rust 中的 + 和 * 运算符来对 Complex 个数字进行加法和乘法运算。

z = z * z + c;


你可以通过实现一些内置特性，让自定义类型也能支持算术运算以及其他运算符的操作。这种机制被称为运算符重载，其效果与 C++、C#、Python 和 Ruby 中的运算符重载类似。

算术运算和位运算器


在 Rust 语言中，表达式 a + b 实际上是 std::ops::Add::add(a, b) 的简写形式，它指的是对标准库中的 Add trait 的 add 方法的调用。如果你导入了这个 trait，就可以将其视为普通的方法调用，即 a.add(b) 。

use std::ops::Add;

assert_eq!(4.125f32.add(5.75), 9.875);
assert_eq!(10.add(20), 10 + 20);

Rust 标准数值类型都实现了 std::ops::Add 接口。为了让表达式 a + b 能够适用于 Complex 类型的值， num crate 也为 Complex 实现了这一接口。类似地，其他运算符也都有相应的实现： a * b 是 std::ops::Mul::mul(a, b) 的简写形式， std::ops::Neg 则涵盖了 - 这种前缀否定运算符等。

这是 std::ops::Add 的定义：

trait Add<Rhs = Self> {
    type Output;
    fn add(self, rhs: Rhs) -> Self::Output;
}

换句话说， Add<T> 这个特性指的是能够向自身添加 T 的值。例如，如果你想让你的类型能够加上 i32 和 u32 的值，那么你的类型就必须实现 Add<i32> 和 Add<u32> 这两个功能。这个特性的类型参数 Rhs 默认值为 Self ，因此当你需要对同类型的两个值进行加法运算时，可以直接使用 Add 来表示这种操作。而相关的类型 Output 则代表了加法运算的结果。

例如，为了能够将 Complex<i32> 的值相加， Complex<i32> 必须实现 Add<Complex<i32>> 的功能。因为我们要将自己的类型添加给自己，所以只需写成 Add 即可。

use std::ops::Add;

impl Add for Complex<i32> {
    type Output = Complex<i32>;
    fn add(self, rhs: Self) -> Self {
        Complex {
            re: self.re + rhs.re,
            im: self.im + rhs.im,
        }
    }
}


当然，我们不必分别为 Complex<i32> 、 Complex<f32> 、 Complex<f64> 等参数实现专门的代码。所有的定义在类型方面都是相同的，因此只要我们处理的复杂组件本身支持加法运算，那么我们就可以编写一个通用的实现来涵盖所有这些情况。

use std::ops::Add;

impl<T> Add for Complex<T>
where
    T: Add<Output = T>,
{
    type Output = Self;
    fn add(self, rhs: Self) -> Self {
        Complex {
            re: self.re + rhs.re,
            im: self.im + rhs.im,
        }
    }
}


通过定义 where T: Add<Output = T> ，我们将 T 限制为可以相互相加的类型，从而得到另一个 T 值。这种限制是合理的，但我们可以进一步放宽限制： Add 特性并不要求 + 的两个操作数具有相同的类型，也不限制结果的类型。因此，在最通用的实现中，左操作数和右操作数可以独立变化，最终得到由加法运算产生的任意类型 Complex 值。

use std::ops::Add;

impl<L, R> Add<Complex<R>> for Complex<L>
where
    L: Add<R>,
{
    type Output = Complex<L::Output>;
    fn add(self, rhs: Complex<R>) -> Self::Output {
        Complex {
            re: self.re + rhs.re,
            im: self.im + rhs.im,
        }
    }
}

然而，在实践中，Rust 往往避免支持混合类型的操作。由于我们的类型参数 L 必须实现 Add<R> 的功能，因此 L 和 R 通常也会是同一种类型。而对于 L 来说，由于它只能实现一种类型，所以实际上并没有太多其他类型的选择。因此，这种最通用的版本可能并不会比之前更有效的简单通用定义更有用。


Rust 中内置的算术和位运算操作符分为三类：一元运算符、二元运算符以及复合赋值运算符。在每一类中，这些运算符及其相关方法都具有相同的形式，因此我们将分别介绍每种类型的示例。

单目运算符


除了“去引用运算符” * 之外，Rust 还有两个可以自定义使用的一元运算符，如表 12-2 所示。关于这些运算符的详细信息，我们将在后续章节中单独讨论。


表 12-2. 一元运算符的内建特性
特征名称 表达 等效方法调用
std::ops::Neg -x Neg::neg(x)
std::ops::Not !x Not::not(x)

这些特征的定义很简单：

trait Neg {
    type Output;
    fn neg(self) -> Self::Output;
}

trait Not {
    type Output;
    fn not(self) -> Self::Output;
}

对一个数进行取负，实际上就是对每个组成部分都取负。下面是我们对 Complex 类型的值进行取负的一般实现方式：

use std::ops::Neg;

impl<T> Neg for Complex<T>
where
    T: Neg<Output = T>,
{
    type Output = Complex<T>;
    fn neg(self) -> Complex<T> {
        Complex {
            re: -self.re,
            im: -self.im,
        }
    }
}

复合赋值运算符


复合赋值表达式类似于 x += y 或 x &= y 这样的表达式：它包含两个操作数，对这些操作数执行某种操作，比如加法或位运算，然后将结果重新赋值给左操作数。在 Rust 语言中，复合赋值表达式的值始终为 () ，而不是存储的原始值。

trait AddAssign<Rhs = Self> {
    fn add_assign(&mut self, rhs: Rhs);
}

如果 x 没有实现 AddAssign ，那么 x += y 就会成为一个错误；Rust 不会回退到 x = x + y 。

对于我们的 Complex 类型， AddAssign 的通用实现方式很简单：

use std::ops::AddAssign;

impl<T> AddAssign for Complex<T>
where
    T: AddAssign<T>,
{
    fn add_assign(&mut self, rhs: Complex<T>) {
        self.re += rhs.re;
        self.im += rhs.im;
    }
}


复合赋值运算符的内置类型与对应的二进制运算符内置类型是完全独立的。实现 std::ops::Add 并不会自动实现 std::ops::AddAssign 的功能；如果你希望 Rust 允许你的类型作为 += 运算符的左手操作数，那么你必须自己实现 AddAssign 功能。

等效性比较


Rust 中的平等运算符 == 和 != ，实际上是 std::cmp::PartialEq 特质中 eq 和 ne 方法的简写形式。

assert_eq!(x == y, x.eq(&y));
assert_eq!(x != y, x.ne(&y));


这就是 std::cmp::PartialEq 的定义。目前可以忽略掉那个奇怪的 where Rhs: ?Sized 绑定；我们将在“Sized”部分详细解释它。

trait PartialEq<Rhs = Self>
where
    Rhs: ?Sized,
{
    fn eq(&self, other: &Rhs) -> bool;
    fn ne(&self, other: &Rhs) -> bool {
        !self.eq(other)
    }
}

请注意， ne 方法有一个默认的定义。很可能你永远找不到任何需要自己实现 ne 的好理由。任何使用 != 的人都会认为 x != y 的意思就是 x 不是 == 对 y ，而这就是默认定义的含义。因此，以下就是 Complex 的完整实现：

impl<T: PartialEq> PartialEq for Complex<T> {
    fn eq(&self, other: &Complex<T>) -> bool {
        self.re == other.re && self.im == other.im
    }
}


换句话说，对于任何可以进行比较相等的组件类型 T ，都可以对 Complex<T> 进行类似的比较。假设我们在某个地方也已经实现了对 Complex 的比较，那么我们现在就可以这样写：

let x = Complex { re: 3, im: 4 };
let y = Complex { re: 0, im: 1 };
assert_eq!(x * y, Complex { re: -4, im: 3 });


PartialEq 的实现几乎总是采用这种方式：它将左操作数的每个字段与右操作数的对应字段进行比较。这种写法可能会比较繁琐，而相等是比较常见的操作，因此当需要使用相等操作时，Rust 会自动生成 PartialEq 的实现。只需在类型定义的 derive 属性中添加 PartialEq 即可。

#[derive(Clone, Copy, Debug, PartialEq)]
struct Complex<T> {
    ...
}

Rust 自动生成的实现方式与我们手工编写的代码本质上是相同的，可以逐字段对比每种类型。Rust 还能为 enum 类型的实现提供 PartialEq 的派生类型。当然， struct 或 enum 中的每个字段本身也必须实现 PartialEq 的功能。

与算术运算和位运算特性不同，后者的是值传递操作数，而 PartialEq 则是引用传递。这意味着比较非 Copy 类型的值时，比如 String 、 Vec 或 HashMap 等，不会使这些值被移动，这一点非常重要，因为否则就会带来麻烦。

let s = "d\x6fv\x65t\x61i\x6c".to_string();
let t = "\x64o\x76e\x74a\x69l".to_string();
assert!(s == t);  // s and t are only borrowed...

// ... so they still have their values here.
assert_eq!(format!("{s} {t}"), "dovetail dovetail");


你们可能会好奇，为什么这个特性被称为 PartialEq 。要解释这一点，就需要先了解一下浮点数的那些奇怪行为。

等式特性（或：相等与 NaN 的比较）


我们已经提到了关于 PartialEq trait 的一个规则，所有的实现都应该遵循这一点：

  • x != y 应该返回与 !(x == y) 完全相同的结果。

Rust 并不强制执行这一规则。你可以手动实现 eq 和 ne 这两种操作，随心所欲地使用它们。虽然违反这一规则不会导致未定义的行为，但肯定会让用户感到困惑，而程序员之间的误解则可能导致错误产生。

因此， PartialEq 特性不仅仅是一系列方法的集合。它还包括了两种方法，再加上上述规则——这代表了 PartialEq 实现方式对其用户所承诺的良好行为。


传统数学中对等价关系的定义，其中“相等”就是一种等价关系，该定义还包括另外三条规则。对于任意的两个值 x 和 y ，满足以下规则即可构成等价关系：

  • 如果 x == y 为真，那么 y == x 也必定为真。换句话说，改变等式两边的顺序并不会影响最终结果。

  • 如果 x == y 等于 y == z ，那么必然也有 x == z 等于 y == z 的情况。对于任何一组数值，如果每一个数值都等于下一个数值，那么链中的每个数值都直接等于其他所有数值。平等具有传染性——一种可以传递的特质。

  • 始终要确保 x == x 是真的。


最后一个要求可能看起来太过明显，无需特意提及，但实际上这正是问题所在。在 Rust 中， f32 和 f64 都是符合 IEEE 标准的浮点数值。根据这一标准，像 0.0/0.0 这样的表达式，以及那些没有对应值的表达式，必然会产生特殊的“非数字”值，通常被称为 NaN 值。此外，该标准还规定，NaN 值必须被视为与所有其他值都不相等——包括它自身。例如，该标准要求所有以下行为都必须得到满足：

let nan: f64 = 0.0 / 0.0;
assert!(nan.is_nan());
assert_eq!(nan == nan, false);
assert_eq!(nan != nan, true);

此外，任何与 NaN 值进行的比较都会返回 false 结果：

assert_eq!(nan < nan, false);
assert_eq!(nan > nan, false);
assert_eq!(nan <= nan, false);
assert_eq!(nan >= nan, false);


因此，虽然 Rust 中的 == 运算符满足前两个等价关系的条件，但当用于 IEEE 浮点数值时，它显然不满足第三个条件。这种等价关系被称为“部分等价关系”。所以，Rust 为 == 运算符的内置特质提供了 PartialEq 这个名称。如果你编写的是那些仅使用 PartialEq 作为类型参数的通用代码，你可以假设前两个条件是成立的，但你不能假设数值总是等于它们自身。


避免在通用代码中出现这种问题的唯一方法，就是排除那些存在此类异常值的类型。Rust 为此提供了 std::cmp::Eq 特性。 Eq 表示完全等价关系：如果一个类型实现了 Eq ，那么该类型中的每一个值 x 都必须是 true 。实际上，几乎每个实现了 PartialEq 的类型都应该同时实现 Eq ； f32 和 f64 是标准库中唯一既满足 PartialEq 又不满足 Eq 类型的类型。


标准库将 Eq 定义为 PartialEq 的扩展，并没有添加任何新的方法。

trait Eq: PartialEq<Self> {}

这个特性本身并没有什么独立的功能，只有那些由“超级特性” PartialEq<Self> 所暗示的功能。 Eq 实际上不过是由 PartialEq 加上一条额外的规则构成的。因此，实现它非常简单：

impl<T: Eq> Eq for Complex<T> {}

甚至这一行代码也可以被推导出来：

#[derive(Clone, Copy, Debug, Eq, PartialEq)]
struct Complex<T> {
    ...
}

在通用类型上的派生实现可能会依赖于类型参数。使用 derive 属性后， Complex<i32> 会实现 Eq ，因为 i32 确实实现了 Eq ；而 Complex<f32> 只会实现 PartialEq ，因为 f32 没有实现 Eq 。

如果你在一个类型中使用 Eq ，而该类型的值并不等于自身，那么这种情况不会导致未定义的行为。但是，其他依赖于 Eq 的代码，包括标准库中的功能，比如 HashMap ，可能会表现出奇怪的行为，并导致荒谬的结果。

有序比较


Rust 为有序比较运算符 < 、 > 、 <= 和 >= 定义了统一的行为规范，这些运算符都归属于同一个特征类 std::cmp::PartialOrd 。

trait PartialOrd<Rhs = Self>: PartialEq<Rhs>
where
    Rhs: ?Sized,
{
    fn partial_cmp(&self, other: &Rhs) -> Option<Ordering>;

    fn lt(&self, other: &Rhs) -> bool { ... }
    fn le(&self, other: &Rhs) -> bool { ... }
    fn gt(&self, other: &Rhs) -> bool { ... }
    fn ge(&self, other: &Rhs) -> bool { ... }
}

请注意， PartialOrd<Rhs> 扩展了 PartialEq<Rhs> ：只有那些可以进行相等比较的类型，才能进行有序比较。

在 PartialOrd 中，唯一需要你自己实现的方法是 partial_cmp 。当 partial_cmp 返回 Some(o) 时，那么 o 就表示 self 与 other 之间的关系：

enum Ordering {
    Less,       // self < other
    Equal,      // self == other
    Greater,    // self > other
}

但是，如果 partial_cmp 返回 None ，那就意味着 self 和 other 之间是不存在顺序关系的： neither 大于另一个，也并不相等。在 Rust 的所有基本类型中，只有浮点数值之间的比较会返回 None ：具体来说，当将 NaN 值与其他任何数值进行比较时，结果会返回 None 。


与其他二进制运算符一样，要比较两种类型的值 Left 和 Right ， Left 必须实现 PartialOrd<Right> 接口。像 x < y 或 x >= y 这样的表达式实际上是对 PartialOrd 方法的简写形式，如表 12-5 所示。


表 12-5. 排序比较运算符及 PartialOrd 方法
表达 等效方法调用 默认定义
x < y PartialOrd::lt(&x, &y) x.partial_cmp(&y) == Some(Less)
x > y PartialOrd::gt(&x, &y) x.partial_cmp(&y) == Some(Greater)
x <= y PartialOrd::le(&x, &y) matches!(x.partial_cmp(&y), Some(Less | Equal))
x >= y PartialOrd::ge(&x, &y) matches!(x.partial_cmp(&y), Some(Greater | Equal))

就像之前的例子一样，表格中的代码假设 std::cmp::PartialOrd 和 std::cmp::Ordering::* 都在范围内。

如果一个类型是完全有序的，也就是说 partial_cmp 永远不会返回 None ，那么这种类型就可以实现更严格的标准 std::cmp::Ord 特性。

trait Ord: Eq + PartialOrd<Self> {
    fn cmp(&self, other: &Self) -> Ordering;

    fn max(self, other: Self) -> Self ...
    fn min(self, other: Self) -> Self ...
    fn clamp(self, lo: Self, hi: Self) -> Self ...
}

这里的 cmp 方法只是返回了一个 Ordering ，而不是像 partial_cmp 那样返回 Option<Ordering> 。 cmp 总是会声明其参数要么相等，要么按顺序排列。几乎所有实现了 PartialOrd 的类型都应该实现 Ord 。在标准库中， f32 和 f64 是违反这一规则的例外。同样，就像 Eq 一样，这种情况也是由于 NaN 值导致的。

Ord 提供了三种额外的方法，这些方法的默认实现都很简单：

  • a.max(b) 返回 a 和 b 这两个值中较大的一个。
  • a.min(b) 返回两个值中较小的一个。
  • a.clamp(lo, hi) 为值 a 设置了上下界限。也就是说，它返回的是介于 lo 到 hi 之间的、最接近 a 的值。如果 hi < lo 的值超出这些界限，则操作会崩溃。


那些实现了 Ord 功能的类型也是可以进行排序的。正如我们在第 16 章中所看到的，标准库中有一些与排序相关的功能：对切片进行二分查找、使用 B 树和二叉堆等。所有这些功能都只适用于那些实现了 Ord 功能的类型。

#[derive(Debug, PartialEq)]
struct Interval<T> {
    lower: T,  // inclusive
    upper: T,  // exclusive
}

你希望将这种值的排序方式定义为部分有序：如果一个区间完全位于另一个区间之前，那么这两个区间就是有序的，且不会存在重叠。如果有两个不相等的区间有重叠部分，那么这两个区间就是无序的：每一侧中的某个元素会小于另一侧的某个元素。而两个相等的区间则视为相同的值。以下对 PartialOrd 的实现就符合这些规则：

use std::cmp::{Ordering, PartialOrd};

impl<T: PartialOrd> PartialOrd<Interval<T>> for Interval<T> {
    fn partial_cmp(&self, other: &Interval<T>) -> Option<Ordering> {
        if self == other {
            Some(Ordering::Equal)
        } else if self.lower >= other.upper {
            Some(Ordering::Greater)
        } else if self.upper <= other.lower {
            Some(Ordering::Less)
        } else {
            None
        }
    }
}

随着该实现的完成，你可以编写如下代码：

assert!(Interval { lower: 10, upper: 20 } <  Interval { lower: 20, upper: 40 });
assert!(Interval { lower: 7,  upper: 8  } >= Interval { lower: 0,  upper: 1  });
assert!(Interval { lower: 7,  upper: 8  } <= Interval { lower: 7,  upper: 8  });

// Overlapping intervals aren't ordered with respect to each other.
let left  = Interval { lower: 10, upper: 30 };
let right = Interval { lower: 20, upper: 40 };
assert!(!(left < right));
assert!(!(left >= right));

由于这不是一个完整的订单，所以我们只实现了 PartialOrd 的功能，而没有实现 Ord 的功能。因此，如果我们想要对区间向量进行排序，仅仅调用 .sort() 是无效的。我们必须明确指定排序顺序。例如，如果按照上限进行排序，可以使用 sort_by_key 来实现：

intervals.sort_by_key(|i| i.upper);


Interval<i32> 没有实现 Ord 的功能，但我们的排序键 ( i.upper ，它是一个 i32 ) 却可以。关于排序的更多信息，请参考“排序与搜索”部分。

索引和 IndexMut


最后，你可以通过实现 std::ops::Index 和 std::ops::IndexMut 特性来指定像 a[i] 这样的索引表达式在你的类型上如何工作。 a[i] 通常是 *std::ops::Index::index(&a, i) 的简写形式。当 a[i] 被赋值或可修改地借用时，它就变成了 *std::ops::IndexMut::index_mut(&mut a, i) 的简写形式。

trait Index<Idx> {
    type Output: ?Sized;
    fn index(&self, index: Idx) -> &Self::Output;
}

trait IndexMut<Idx>: Index<Idx> {
    fn index_mut(&mut self, index: Idx) -> &mut Self::Output;
}

请注意，这些特性将索引表达式的类型作为参数来使用。你可以用单个 usize 来索引某个切片，从而指向单个元素，因为切片实现了 Index<usize> 接口。不过，你也可以使用类似 a[i..j] 的表达式来引用子切片，因为子切片同样实现了 Index<Range<usize>> 接口。这个表达其实是 Index<Range<usize>> 的简写形式。

*std::ops::Index::index(&a, std::ops::Range { start: i, end: j })

Rust 中的 HashMap 和 BTreeMap 集合可以通过键来进行索引。以下示例的最后一行是有效的，因为 HashMap<&str, i32> 实现了 Index<&str> 的功能：

use std::collections::HashMap;
let mut m = HashMap::new();
m.insert("十", 10);
m.insert("百", 100);
m.insert("千", 1000);
m.insert("万", 1_0000);
m.insert("億", 1_0000_0000);

assert_eq!(m["十"], 10);

这一主张相当于：

assert_eq!(*std::ops::Index::index(&m, "十"), 10);


Index 特征所关联的类型 Output 规定了索引表达式生成的类型。对于我们的 HashMap ， Index 实现的 Output 类型就是 i32 。


IndexMut 特性扩展了 Index ，它拥有一个 index_mut 方法，该方法接受一个可变的引用指向 self ，并返回一个指向 Output 值的可变引用。当索引表达式出现在需要该特性的上下文中时，Rust 会自动选择使用 index_mut 。例如，假设我们编写如下代码：

let mut desserts =
    vec!["Howalon".to_string(), "Soan papdi".to_string()];
desserts[0].push_str(" (fictional)");
desserts[1].push_str(" (real)");

因为 push_str 方法是对 &mut self 进行操作，所以最后这两行代码相当于：

use std::ops::IndexMut;
(*IndexMut::index_mut(&mut desserts, 0)).push_str(" (fictional)");
(*IndexMut::index_mut(&mut desserts, 1)).push_str(" (real)");


IndexMut 的一个局限性是，按照设计，它必须返回一个可修改的引用值。这就是为什么不能使用像 m["十"] = 10; 这样的表达式来向 HashMap m 中插入值：首先，表格需要为 "十" 创建一个默认值的条目，然后返回一个对该条目的可修改引用。不过，并非所有类型都有合适的默认值，而且有些默认值可能非常昂贵；如果创建了一个这样的默认值，却因为赋值操作而立即被丢弃，那将是一种浪费。


索引最常见的用途是用于整理资料。例如，假设我们正在处理位映射图像，就像在第二章的曼德布罗特集绘图程序中创建的那些图像。回想一下，我们的程序中包含过类似的代码：

pixels[row * bounds.0 + column] = ...;

如果有一个类似二维数组的 Image<u8> 类型就好了，这样我们就可以直接访问像素，而不需要编写所有的算术运算了。

image[row][column] = ...;

为此，我们需要定义一个结构体：

struct Image<P> {
    width: usize,
    pixels: Vec<P>,
}

impl<P: Default + Copy> Image<P> {
    /// Creates a new image of the given size.
    fn new(width: usize, height: usize) -> Image<P> {
        Image {
            width,
            pixels: vec![P::default(); width * height],
        }
    }
}

以下是符合要求的 Index 和 IndexMut 的实现方式：

impl<P> std::ops::Index<usize> for Image<P> {
    type Output = [P];
    fn index(&self, row: usize) -> &[P] {
        let start = row * self.width;
        &self.pixels[start..start + self.width]
    }
}

impl<P> std::ops::IndexMut<usize> for Image<P> {
    fn index_mut(&mut self, row: usize) -> &mut [P] {
        let start = row * self.width;
        &mut self.pixels[start..start + self.width]
    }
}

当你对 Image 进行索引操作时，你会得到一个像素切片；而对该切片进行索引后，你就会得到一个单独的像素点。


请注意，当我们使用 image[row][column] 时，如果 row 超出了数组的边界，那么我们的 index 方法就会尝试访问超出范围的 self.pixels ，从而导致程序崩溃。这就是 Index 和 IndexMut 方法的预期行为：当检测到越界访问时，程序会触发崩溃，就像在数组、切片或向量中超出边界进行索引时一样。

其他运营商


在 Rust 中，并非所有运算符都可以被重载。目前，用于进行错误检查的 ? 运算符仅能与 Result 以及少数其他标准库类型配合使用。不过，目前正在努力将这一特性扩展到用户自定义类型上。同样，逻辑运算符 && 和 || 也仅适用于布尔值。 .. 和 ..= 运算符总是会创建一个表示范围边界的结构体； & 运算符总是会采用引用传递方式；而 = 运算符则总是会进行值移动或复制操作。这些运算符都无法被重载。


解引用运算符 *val ，以及用于访问字段和调用方法的点运算符，比如 val.field 和 val.method() ，可以通过 Deref 和 DerefMut 这些特性来重载。关于这些特性的详细信息，将在下一章中介绍。（我们在这里没有提及它们，因为这些特性不仅仅只是对几个运算符进行了重载而已。）


Rust 不支持对函数调用运算符进行重载操作。因此，当你需要一个可调用的值时，通常只需要创建一个闭包即可。我们会在第 14 章中解释这一点是如何工作的，并且会讨论 Fn 、 FnMut 和 FnOnce 这些特殊特性。
